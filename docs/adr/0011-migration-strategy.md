# 0011. Миграции базы — только вперёд

- **Статус:** принято 2026-09-25; изменено 2026-10-05 (Р1.5): провал миграции
  на данных откладывает файл, копия — одна на обновление.
- **Подробнее:** `tasks-v0.2.md`, эпик B, B3; `docs/decisions.md` — «B3:
  миграции» и 2026-10-05 «Р1.5»; `docs/work/r1-5.md`; код —
  `core/library/src/db/migrations/`, `db/backup.rs`, `db/connection.rs`.

## Контекст

С v0.2 библиотека живёт в SQLite внутри Rust-ядра. Схема будет меняться с
каждой волной, а база пользователя обязана пережить каждое обновление. При
этом у приложения нет сервера и нет Play-консоли: сломанная миграция на
телефоне — это молчаливая потеря библиотеки, о которой узнают из issue.

Первая редакция (2026-09-25) на провале миграции оставляла базу как есть и
отдавала ошибку. Ревью v0.2 (находка 5) показало цену: файл цел, но
приложение не открывается ни на одном запуске, пока не выйдет исправленная
версия; то же — если копия перед миграцией не снялась из-за места или порчи.

## Решение

- **Только вперёд.** Версия схемы — `PRAGMA user_version`. Миграция — шаг
  `N → N+1` в реестре `MIGRATIONS`: версии подряд с единицы, это проверяет
  тест. Отката нет. База новее кода (пользователь поставил старую версию
  приложения) — ошибка «downgrade is not supported». Файл при этом не
  трогается и не выбрасывается.
- **Каждая миграция — в своей транзакции.** Она может менять и схему, и
  данные: `apply` — функция на Rust, не только SQL. Упала — транзакция
  откатывается, файл остаётся целым на предыдущей версии. Дальше решает
  причина:
  - **сбой среды** (место, ввод-вывод, блокировка, права) — ошибка открытия,
    файл не трогается, следующий запуск повторит. Новая база упёрлась бы в
    то же место, а отложенный файл его бы и занял;
  - **ошибка на данных** — файл базы, бывшей до этого открытия, вместе с
    `-wal`/`-shm` переименовывается в `<база>.migration-failed-<мс>`, база
    создаётся заново. Пользовательское возвращает журнал, каталог — скан;
    приложение узнаёт об этом как о восстановленной базе, номер и имя
    миграции — в логе. Это и есть «откат на бэкап» плана (§17.4): отложенный
    файл — база до упавшего шага, база до обновления — в копии `.bak-…`;
  - **ошибка на базе, созданной этим же открытием**, — ошибка открытия с
    номером и именем миграции: откладывать нечего.

  Отвергнуто: вернуть копию на место (та же миграция упадёт снова);
  откладывать файл при любой ошибке (нехватка места выбросила бы здоровую
  базу).
- **Перед обновлением непустой базы — одна копия.** `VACUUM INTO` во
  временный `<база>.bak.tmp` (застарелый удаляется до), затем
  переименование в `<база>.bak-<мс>-v<версия при открытии>`: оборванная
  копия — ни при ошибке, ни при убитом процессе — копией не считается.
  Копия целостная и в режиме WAL. Промежуточные версии выводятся из неё тем
  же кодом, поэтому копия одна на открытие, а не на миграцию; хранятся три
  последние — три обновления. Новой базе копия не нужна (найдено в D1, когда
  появилась вторая миграция). Копия не снялась: порча — карантин (ниже),
  остальное (место, путь) — предупреждение в лог, миграции идут без копии.
- **Выпущенная миграция заморожена.** `m0001_initial` — начальная схема;
  её и любую выпущенную миграцию не правят. Изменение схемы — новая
  миграция в конце реестра.
- **Эталон на каждую выпущенную версию схемы.**
  `core/library/tests/fixtures/db/v<N>.db` делает
  `cargo run -p plinth-library --example make_db_fixture`, один раз при
  выпуске версии. `tests/migrations.rs` открывает каждый эталон текущим
  кодом с полной проверкой целостности и сверяет данные: треки, лайки,
  счётчики, порядок плейлиста. Другой тест требует, чтобы эталон был у
  каждой версии от 1 до текущей.
- **Порча, найденная при миграции или копии, — та же порча**, что и при
  открытии (B2.3): файл уходит в карантин, база создаётся заново.

## Последствия

- Обновление приложения не может молча обнулить библиотеку и не запирает
  её. Ошибкой открытия кончаются только база новее кода, сбой среды и провал
  миграции на только что созданной базе. Прежний файл и копия до обновления
  лежат рядом: из них данные можно достать вручную или следующей версией с
  исправленной миграцией.
- Ошибочная миграция, проскочившая CI, обходится каждому пересборкой из
  журнала и пересканом, а не отказом запуска. Сторож — эталоны: каждый
  обязан открыться без восстановления.
- Откатить приложение на версию назад нельзя, если между ними менялась
  схема. Для pre-release это приемлемо; F-Droid и GitHub Releases откат и не
  предлагают.
- **Запасной выход у проекции журнала.** Таблицы `track_user`, плейлистов,
  истории и склеек — отражение журнала (C3). Если их миграция слишком
  сложна, проекцию можно удалить и собрать заново из журнала. Каталог тоже
  пересобирается сканом. Незаменимое живёт в журнале, не в базе, — поэтому
  стратегия «только вперёд» безопасна.
- Каждая версия схемы добавляет в репозиторий бинарный эталон (сотни КБ).
  `.gitattributes` помечает `*.db` как бинарные.
- Место: три копии базы рядом с ней — с трёх последних обновлений; при
  50 000 треков это десятки мегабайт. Отложенные `.corrupt-*` и
  `.migration-failed-*` — тоже полные копии, их пока никто не чистит
  (кандидат в Р1.11). Если станет заметно, копии можно сжимать или хранить
  меньше.
