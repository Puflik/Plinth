# 0007. Журнал — источник правды, база — его проекция

- **Статус:** принято 2026-09-25; изменено 2026-10-05 (Р1.4): снимок, который
  не читается, откладывается, журнал начинается заново из базы; дополнено
  2026-10-06 (Р1.2): перенесённый файл узнаёт скан, журнал не пишется;
  2026-10-10 (Р1.7): паспорт в журнале догоняет теги каталога после скана.
- **Подробнее:** `plan.md` 17.4 и 4.3; `tasks-v0.2.md`, эпик C, C2–C3;
  `docs/decisions.md` — «C2–C3: журнал и проекция»; `docs/work/r1-4.md`,
  `docs/work/r1-2.md`, `docs/work/r1-7.md`; код —
  `core/sync/src/journal/`; библиотека CRDT — [ADR 0006](0006-crdt-library.md),
  миграции — [ADR 0011](0011-migration-strategy.md).

## Контекст

Лайки, плейлисты и история незаменимы. SQLite может испортиться, пропасть
при переустановке или получить неудачную миграцию. План (17.4) делает
журнал CRDT источником правды, а базу — производной, которую можно собрать
заново. Журнал растёт всю жизнь приложения. Он обязан влезать в Auto Backup
(25 МБ), а в v1.5 он же синхронизирует устройства. Ошибка границы дорога в
обе стороны. Важное только в базе теряется при первой порче. Лишнее в журнале
раздувает его, и он перестаёт влезать в бэкап.

## Решение

**Граница.**

| В журнале — незаменимое | Только в базе — пересобирается | Никогда в журнале |
|---|---|---|
| Лайки, оценки | Каталог: треки, версии, источники, артисты, альбомы — скан и провайдеры | Локальные пути и URI — привязаны к устройству |
| Плейлисты и записи с дробной позицией | Нормализованные поля, индексы | Токены аккаунтов — утекут при синхронизации |
| История прослушиваний — факты | Счётчик и «последнее прослушивание» — выводятся из истории | Кэш, состояния загрузок |
| Решения о склейке | Обложки, отпечатки | Настройки устройства — папки, вывод звука, стартовый экран (DataStore) |
| Подписки, чёрный список, синхронизируемые настройки | | |

- **Счётчик не хранится.** Проекция выводит его из истории по правилу
  Last.fm (`PlayEvent::counts`): засчитано, если прослушано не меньше
  половины трека или 4 минут; треки короче 30 с не считаются. Правило
  можно поменять, счётчики пересчитает пересборка.
- **Паспорт трека — следующий шаг границы (D1/C4).** Идентификаторы каталога
  не выводятся из тегов (B1). После переустановки скан выдаст трекам новые
  ID, и ссылки журнала повиснут. Поэтому в журнал ляжет паспорт трека, на
  который есть пользовательские данные: название, артист, длительность,
  MBID. Скан и восстановление сопоставят с ним файлы и возьмут ID из
  журнала. Это новый вид записи, формат менять не придётся.
  Теги правят и вне приложения: скан обновляет их в каталоге, и паспорт,
  написанный по старым, перестаёт узнавать трек после переустановки. Поэтому
  после каждого скана ядро приводит паспорта треков с данными к каталогу
  (Р1.7) — той же записью `Describe`.

**Запись: сначала журнал, потом база.**

- Операция ([`Op`]) ложится в документ одной транзакцией `yrs`, её
  обновление — кадром в хвост файла с `fsync`. Затем одна транзакция SQLite
  пишет изменение и метку «какое состояние журнала отражено»:
  идентификатор журнала и номер операции.
- Метка базы совпала с журналом до операции — применяется одна операция.
  Не совпала (сбой между журналом и базой, база новая или восстановленная) —
  проекция пересобирается целиком. При старте то же делает `catch_up`.
- Операция без последствий в журнал не пишется. Ссылка на то, чего нет
  (переименовать несуществующий плейлист), — ошибка до правки: у транзакции
  `yrs` нет отката.

**Документ.** Корни — только плоские именованные `map` и `array`. Вложенный
`map` на сущность, созданный параллельно на двух устройствах, затирается
целиком.

- Множества — лайки, подписки, чёрный список: добавление побеждает
  параллельное удаление.
- Регистры — оценка, плейлист, запись плейлиста, настройка: действует
  последняя запись по ключу. Параллельные записи `yrs` разводит одинаково
  на всех устройствах — по своему правилу, не по времени.
- Прослушивания и решения о склейке только дописываются.
- Порядок в плейлисте — позиция записи. Параллельная перестановка одного
  трека не размножает его (находка C1).
- Удаление плейлиста удаляет и его записи. Запись, добавленная параллельно
  в удаляемый плейлист, остаётся в журнале без плейлиста, и проекция её
  пропускает. Параллельное переименование возвращает плейлист, но без
  удалённых записей.

**Формат.**

- Запись — двоичная: версия схемы, устройство, время, поля сущности.
  Идентификаторы — 16 байт, числа — varint. Схема растёт только
  дописыванием полей в конец: старый код читает известное начало.
- Файлы:
  - `snapshot` — update v2 и CRC32;
  - `tail` — кадры update v1 транзакций с CRC32; длинный хвост
    сворачивается в снимок.

  Файл новее кода — ошибка открытия, файл не перезаписывается.
- Идентификатор клиента `yrs` — новый при каждом открытии, как в Yjs.
  Постоянный автор операции — `DeviceId` в записи.
- Размер: 10 000 событий, из них 85 % — прослушивания со всеми фактами.
  Снимок — 966 КБ, хвост до сворачивания — 1,17 МБ. До 25 МБ Auto Backup —
  около 260 тыс. событий, это ≈ 14 лет при 50 прослушиваниях в день.

## Последствия

- Порча базы не теряет пользовательского. Файл уходит в карантин (B2.3), и
  `catch_up` пересобирает проекцию. Это DoD эпика C, есть тест.
- Сложную миграцию таблиц проекции можно заменить пересборкой (ADR 0011).
- Приложение пишет пользовательское только через журнал
  (`record_and_project`). Репозитории таблиц проекции публичны для
  проекции и тестов, но вызывать их мимо журнала — ошибка.
- Журнал в 1,8 раза тяжелее прототипа C1: прослушивание несёт все факты.
  Если он начнёт подходить к лимиту, есть два рычага: убрать устройство из
  записи прослушивания (16 байт из ~110) и сжать старую историю.
- Слияние чужого журнала (C4, v1.5) ведёт к пересборке проекции целиком.
  Инкрементальная проекция чужих обновлений — в v1.5, если пересборка
  станет заметной.
- План (10) велит один раз спросить пользователя при параллельном
  переименовании. Для этого понадобятся события слияния `yrs` — это задача
  v1.5, сейчас побеждает правило `yrs`.
- Запись журнала на диск не удалась — операция остаётся в памяти, следующая
  кладёт всё снимком.
- Снимок, который не читается (сумма не сошлась, обрезан, `yrs` не
  разбирает), — ошибка `Journal::open`, файл не тронут. Ядро такой снимок
  откладывает рядом (`snapshot.damaged-<мс>`) и начинает журнал заново — с
  тем пользовательским, что показывает база: это единственная полная копия
  на телефоне, а пустой журнал её тут же стёр бы пересборкой. У установки
  новое имя: копия в папке, записанная до порчи, становится чужой — её не
  перезапишут, а недостающее из неё вернёт восстановление (C4). Снимок новее
  приложения — по-прежнему ошибка открытия (Р1.4).
- Файл перенесли, переименовали, у карты сменилось имя тома — его узнаёт сам
  скан, а не перепривязка (Р1.2). Пропавший файл каталога и новый файл с тем
  же паспортом — один трек: остаются ID трека и источника, дата добавления.
  Журнал не пишется: путей в нём нет, а ID не изменился. Паспорта сравнивает
  одна функция для скана и перепривязки. Копию, снятую, пока оригинал на
  месте, скан за перенос не принимает: два живых файла одной песни сведёт
  идентичность v0.3.
- Паспорт в журнале не отстаёт от тегов каталога дольше одного скана (Р1.7):
  после скана треки с данными, у которых изменились название, исполнитель,
  альбом, длительность или MBID, описываются заново одной правкой журнала;
  не изменилось ничего — журнал не пишется. Сравнивается состояние, а не итог
  скана, поэтому оборванное обновление доводит следующий скан. Варианты
  провайдера (`sources`) при этом не сравниваются — их ведёт
  `record_and_project` при действии над сетевым треком. Когда устройств
  станет несколько (v1.5), одна песня с разными тегами на двух из них будет
  перезаписывать паспорт по очереди: понадобится правило — метка времени или
  владелец паспорта.
