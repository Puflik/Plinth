## Цель

Ядро открывается сразу и на двадцатом запуске: плановая `integrity_check`
уходит с пути открытия и идёт после него, в фоне, на своём соединении только
для чтения. Найденная порча не теряется: метка рядом с базой заставляет
следующее открытие отложить файл и собрать базу заново — как сейчас при порче,
найденной на открытии.

## Решение

| Где | Сейчас | Станет |
|---|---|---|
| `Database::open(…, Scheduled)` на запуске 20, 40, … | полная `integrity_check` на открытии, экран ждёт | не проверяет, только отмечает `Opened::integrity_due` |
| `Database::open(…, Now)` | проверка на открытии | без изменений (тесты, эталоны) |
| после открытия ядра | — | Kotlin зовёт `Core::check_integrity()` в фоне; проверяет `Database::check_file` на своём соединении только для чтения, замок ядра не берётся |
| проверка нашла порчу | на открытии: карантин сразу | метка `<база>.damaged` с причиной; ядро работает дальше; следующее открытие — файл в карантин (`.corrupt-<мс>`), база заново, лайки из журнала |
| проверка не смогла прочесть (нет файла, занято, ввод-вывод) | — | ошибка, метки нет |
| метка есть, а базы нет | — | метка снимается, открытие обычное |

1. **Проверка уходит с открытия.** `IntegrityCheck::Scheduled` теперь значит
   «по расписанию, не на открытии»: `open_checked` её не делает, а
   `Opened::integrity_due` = `Scheduled` и `due(launch)`. `Now` проверяет на
   открытии, как прежде (`integrity_due: false`); `Skip` — никогда. `due` и
   `CHECK_EVERY_LAUNCHES` прежние.
2. **Проверка рядом — `Database::check_file(path)`.** Своё соединение
   `SQLITE_OPEN_READ_ONLY | SQLITE_OPEN_NO_MUTEX`, `busy_timeout` 5 с, затем
   `problems()`:
   - пусто — `Healthy`;
   - строки — `Damaged { reason }`, строки через `"; "`; ошибка с
     `is_corruption` — `Damaged`, причина — текст ошибки (на испорченных
     страницах `integrity_check` падает именно так);
   - иначе — `Err(CoreError::storage(…))` с кодом SQLite, без текста ошибки
     (в нём бывает путь, §17.3); метки нет.

   При `Damaged` — метка `<база>.damaged` с причиной (`fs::write`). Не
   записалась — `Err` с `ErrorKind`: «порча найдена, метка не записана». В
   саму базу проверка не пишет ничего.
3. **Метка на открытии.** `Database::open` первым делом, при любом
   `IntegrityCheck`:
   - метка есть и файл есть — причина из метки (пусто или не читается —
     `integrity check found damage`), **метка удаляется**, затем
     `replace(path, "corrupt", причина)`;
   - метка не удалилась — `log::warn!` (`ErrorKind`) и обычное открытие без
     замены: иначе метку нашла бы и новая база, и та откладывалась бы на
     каждом запуске;
   - метка есть, файла нет — метка удаляется, открытие обычное.

   Порядок «метка, потом карантин»: обрыв между ними оставит испорченную базу
   без метки — её найдёт следующая плановая проверка. Обратный порядок мог бы
   отложить новую здоровую базу.
4. **FFI.** `Core` помнит путь к базе и `integrity_due` из `Opened`
   (`AtomicBool`). `Core::check_integrity()`: флаг уже снят (`swap(false)`) —
   `NotDue` без чтения файла; иначе — `Database::check_file`. `Damaged` —
   `log::warn!` с причиной: «damage found; the database is replaced on the next
   open». Замки ядра (`state`, `scan`) не берутся: другие вызовы идут, пока
   идёт проверка. За ядро — не больше одной проверки.
5. **Kotlin.** `CoreInitializer`: после удачного `open()`, в той же корутине,
   — `core.checkIntegrity()`. В лог — сколько шло открытие (`core opened in N
   ms`) и проверка (`integrity check: healthy in N ms` / `integrity check:
   damage found in N ms; the library is rebuilt on the next launch`);
   `NOT_DUE` — молча; отказ — `AppLog.w`, не в `errors`. Человеку сейчас
   ничего не говорим: на следующем открытии он увидит «Библиотека
   восстановлена» по уже существующему пути.

Отвергнуто:

- `quick_check` на открытии: дешевле, но тот же проход по файлу на пути
  открытия (на телефоне — сотни миллисекунд), и ловит меньше.
- Менять базу сразу, в той же сессии: подмена `State.db` под замком при
  идущем скане, сигналы Kotlin о новом каталоге и пользовательском — много
  нового ради редкого случая. Следующее открытие чинит существующим путём;
  до него сессия идёт на повреждённой базе, как сегодня между проверками, а
  пользовательское пишется сперва в журнал.
- Поток Rust, запущенный из `Core::open`: живёт дольше ядра, колбэк логгера
  зовётся из чужого потока, тесту нечего дождаться. Фоновую работу и так
  ведёт Kotlin.
- WorkManager «в простое»: может не прийти никогда, нужна новая обвязка.
- Пауза перед проверкой: другие вызовы её не ждут (своё соединение, без
  замка). Вводить, если замер на телефоне покажет помеху первому экрану.
- Метка в `meta`: это запись в повреждённую базу; файл рядом надёжнее.

## Инварианты

- `Database::open` не читает файл целиком ни при каком `IntegrityCheck`,
  кроме `Now`.
- `check_file` в базу не пишет — соединение только для чтения; пишет только
  метку.
- Ошибка чтения при проверке — не порча: метки нет, файл не тронут.
- Метка → следующее открытие откладывает файл целиком (с `-wal`/`-shm`) в
  `.corrupt-<мс>` и создаёт базу заново; метка снята до карантина. Дальше —
  обычные открытия: новая база метку не наследует, одна метка — не больше
  одной замены.
- `check_integrity` не берёт замки ядра; за ядро — не больше одной проверки;
  не в свою очередь — `NotDue` без чтения файла.
- Журнал не трогается; после замены пользовательское возвращает `catch_up`,
  каталог — скан.
- В логах и текстах ошибок нет путей (§17.3).
- Прежние тесты не меняются: `Now` и `due` прежние (`connection.rs`,
  `tests/migrations.rs`, `core/sync/tests/rebuild.rs`, `session.rs`).

## Остановиться и написать, если

- защищённый тест кажется неверным; нужен файл вне «Менять»; проверки упали
  дважды подряд;
- SQLite ведёт себя иначе, чем в «Контексте»: порча не `DatabaseCorrupt`,
  соединение только для чтения не открывается рядом с основным
  (`SQLITE_READONLY_*`, `BUSY`);
- для `check_integrity` нужен замок ядра или новое поле в `StartupReport`;
- кажется, что человеку надо что-то показать сейчас, а не на следующем
  открытии, — это решение, не код.

## Риски, принятые сознательно

- Найденная порча чинится на следующем запуске: эту сессию человек работает с
  повреждённой базой, как сегодня между проверками. Пользовательское
  пишется сперва в журнал.
- Проверка, оборванная вместе с процессом, — следующая через 20 запусков.
- Метка не удалилась — замены нет до следующей плановой проверки.
- Проверка в фоне читает весь файл: на большой базе — секунды CPU и чтения раз
  в 20 запусков, параллельно первому экрану. Если помешает — пауза (см.
  «Отвергнуто»).
- `.corrupt-*` никто не чистит (кандидат в Р1.11).
