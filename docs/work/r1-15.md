## Цель

Скан отмечает файл пропавшим (`missing`, `gone`) только когда **знает**, что
его нет. Если файл просто не увидели — карту ещё проверяют после загрузки или
вставки, на записи папки вышла осечка чтения — он остаётся каким был: не
недоступным, не вернувшимся и не кандидатом на сведение перенесённых (Р1.2).
Вынутая карта по-прежнему отмечается недоступной.

## Решение

### Принцип

«Не знаю» отличается от «нет». Файлы под тремя источниками «не знаю» не
пропали и не вернулись: доступность, источник, трек и отметка скана остаются
как были, сведению перенесённых они недоступны.

1. папка, которую не прочесть (`Walk::unreadable`) — есть, не меняется;
2. запись папки, которую обход не смог прочесть (`Walk::unseen`) — **новое**;
3. том, который система знает, но ещё не отдала (`Volumes::pending`) — **новое**.

«Вынутая карта» — том, которого нет **ни в `ready`, ни в `pending`**, — и корень,
отданный как готовый, но которого нет на диске (`missing_roots`): их файлы
пропали, как раньше. Различить вынутую карту и ещё не смонтированную может
только система, ядро не может, поэтому второй список приходит от Kotlin.

### 1. Обход — `walker.rs`

`Walk` получает поле (сигнатура дословно; `#[derive(Default)]` остаётся, так что
`Walk { .., ..Walk::default() }` в чужих тестах собирается):

```rust
/// Пути, которые обход не смог прочесть: запись папки (файл или папка — если
/// не прочёлся даже тип, неизвестно) и всё под ней. Без разделителя в конце.
/// Файлы здесь не пропали: о них ничего не известно.
pub unseen: Vec<String>,
```

`visit` больше ничего не теряет молча:

| что случилось | что делает обход |
|---|---|
| итератор записей отдал `Err` (имя неизвестно, остаток листинга ненадёжен) | папка `dir` — в `unreadable` (один раз за обход, с разделителем в конце, как сейчас); запись пропущена, обход папки продолжается |
| `entry.file_type()` — `Err` | путь записи — в `unseen` (она может быть и папкой); дальше по записи не идти |
| имя не UTF-8 | как сейчас: пропуск (такого файла в каталоге быть не может) |
| аудиофайл, `entry.metadata()` — `Err` | путь записи — в `unseen` |

`metadata()` по-прежнему зовётся **только у аудиофайлов**: лишних системных
вызовов в обходе не появляется. Путь — `entry.path().to_string_lossy()`, то же
выражение, что у `FoundFile::uri`: так он совпадает с `local_uri` каталога. В лог —
одна строка `warn` **на папку**: сколько записей не прочлось и первая ошибка (не
строка на запись: папка, где не прочлась каждая запись, дала бы тысячи строк).

### 2. Сравнение — `diff.rs`

Файл `uri` неизвестен, если он лежит в папке из `unreadable` (как сейчас) **или**
равен пути из `unseen`, либо лежит под ним. Граница — целый сегмент пути:
`a.mp3.bak` не «под» `a.mp3`, `dirx` не «под» `dir`. Неизвестный файл не
попадает ни в `missing`, ни в `gone`; в `added`, `changed`, `returned`,
`unchanged` его нет и подавно (его не видел обход).

Поиск по `unseen` — **не перебор** списка на каждый файл: набор строк, а для
файла проверяются он сам и его родители по границам разделителя
(`MAIN_SEPARATOR`). Папка, где не прочлась каждая запись, даёт десятки тысяч
путей, а каталог — десятки тысяч файлов; перебор дал бы квадрат ровно тогда, когда
карта и так больна (тест `a_folder_where_every_entry_failed_costs_one_pass`).
Сигнатура `diff(known, walk)` не меняется.

### 3. Тома — `scan/mod.rs`

```rust
/// Тома одного скана.
#[derive(Debug, Default, Clone, PartialEq, Eq)]
pub struct Volumes {
    /// Корни смонтированных томов — их обходит скан.
    pub ready: Vec<PathBuf>,
    /// Корни томов, которые система знает, но ещё не отдала: карту проверяют
    /// после загрузки или вставки. Скан их не обходит и о файлах на них ничего
    /// не решает. Том, который есть и в `ready`, обходится как готовый.
    pub pending: Vec<PathBuf>,
}

pub fn scan_volumes(
    db: &dyn DbAccess,
    volumes: &Volumes,
    config: &FolderConfig,
    reader: &dyn TagReader,
    progress: Progress<'_>,
    now: Timestamp,
) -> Result<ScanReport, CoreError>;
```

`Volumes` и `scan_volumes` — `pub` в `plinth_library::scan`. Нынешний
`scan(db, roots, config, reader, progress, now)` **остаётся с той же сигнатурой**
(около сорока вызовов в тестах) и становится вызовом `scan_volumes` с
`Volumes { ready: roots.to_vec(), pending: Vec::new() }`.

`scan_volumes` делает то, что делал `scan`, и перед `diff` дописывает в
`walked.unseen` корни `pending`: без разделителя в конце (`/storage/1234-ABCD/` и
`/storage/1234-ABCD` — один том), кроме тех, что есть и среди `ready` (виден
по-настоящему — обходится). `ScanReport` **не меняется**: счётчик неизвестных ради
строки лога не стоит правки FFI-записи и Kotlin. `moved.rs` не меняется:
кандидаты — `diff.missing` и `diff.gone`, неизвестные туда не попадают; в шапке
поправить комментарий («…и он не в непрочитанной папке» → «…и скан не лишён
сведений о нём: папка, запись, том»).

### 4. FFI — `scan_api.rs`

```rust
pub fn scan_volumes(
    &self,
    ready: Vec<String>,
    pending: Vec<String>,
    folders: FolderConfig,
    listener: Arc<dyn ScanListener>,
) -> Result<ScanReport, CoreError>
```

Всё, что делает нынешний `Core::scan` (`panic::guard`, замок `scanning`,
`relink_catalog` после скана), но с `Volumes`. `Core::scan(volumes, folders,
listener)` **остаётся экспортированным** и зовёт `scan_volumes(volumes, Vec::new(),
folders, listener)`: у него десяток вызовов в чужих тестах.

### 5. Kotlin

`StorageVolumes.kt` (имена и поведение дословно):

```kotlin
/** Что скан делает с томом, по `StorageVolume.getState()`. */
enum class VolumeReadiness { READY, PENDING, ABSENT }

/**
 * MEDIA_MOUNTED и MEDIA_MOUNTED_READ_ONLY — READY; MEDIA_CHECKING — PENDING;
 * всё остальное, и незнакомое тоже, — ABSENT.
 */
fun volumeReadiness(state: String): VolumeReadiness

/** Тома из одного чтения системы. */
data class VolumeSnapshot(
    val ready: List<File>,
    val pending: List<File> = emptyList(),
)

fun interface StorageVolumes {
    fun snapshot(): VolumeSnapshot

    /** Только готовые тома. */
    fun roots(): List<File> = snapshot().ready
}
```

`AndroidStorageVolumes.snapshot()`:

- **API 30+:** один проход по `storageVolumes`; для каждого — `volumeReadiness(state)`:
  `READY` → `directory` (не `null`), `PENDING` → `File("/storage/$uuid")` при
  `uuid != null`, `ABSENT` → ничего. Каталог проверяемой карты `getDirectory()` не
  отдаёт (`null`, пока том не смонтирован), поэтому путь выводится из `uuid`: так
  система называет тома (`/storage/1234-ABCD`), так и лежат `local_uri` в каталоге.
- **API 26–29:** сначала `storageVolumes` (с API 24) → состояния и `uuid` →
  `pending`; потом, как сейчас, `getExternalFilesDirs` → `ready`. Порядок важен:
  карта, смонтировавшаяся между двумя чтениями, окажется в обоих списках, а
  «в обоих» значит «готов»; в обратном порядке она выпала бы из обоих.
  Основной том (`uuid == null`) в `pending` не попадает.

`CoreScan.scan(volumes, included, excluded = emptyList(), pending: List<File> =
emptyList(), onProgress)` — зовёт `it.scanVolumes(volumes.map(File::getPath),
pending.map(File::getPath), …)` (параметр `pending` стоит **перед** `onProgress`,
чтобы вызовы с завершающей лямбдой `scan(volumes, folders) { … }` остались
прежними). `LibraryScanner.scan`: `val snapshot = volumes.snapshot()`, дальше
`core.scan.scan(snapshot.ready, …, pending = snapshot.pending)`; предупреждение
в лог (`AppLog.w`) — и когда есть проверяемые тома (их число).

### Отвергнуто

- **Отложить скан, пока том проверяют** (только Kotlin): пока карта «проверяется»,
  не обновлялся бы и основной том, а зависшая карта останавливала бы скан навсегда.
- **«Пропал» только со второго скана подряд:** нужен счётчик пропусков в базе
  (миграция) ради случая, который Kotlin видит сам.
- **Считать неизвестным корень, отданный как готовый, но которого нет на диске
  (`missing_roots`):** ломает Р1.2 (`a_file_on_a_card_with_a_new_volume_name_keeps_its_track`)
  и бесполезно в бою — вынутую карту Kotlin в список не кладёт.
- **При осечке одной записи считать неизвестной папку целиком:** вечная осечка
  одной записи (повреждённая запись FAT на карте) ослепила бы скан на всю папку,
  и настоящие удаления в ней никто не заметил бы. Тест
  `an_unreadable_entry_spares_only_itself` держит точный вариант; папка целиком —
  только когда имя записи неизвестно (ошибка итератора).
- **`unmounted` и `ejecting` как «проверяется»:** вручную отключённая карта осталась
  бы с «доступными», но неиграющими треками, а путь «трек не играет →
  пересканировать» (`UnavailableRescan`, один раз за запуск) не отметил бы их
  недоступными никогда. Остаётся `checking` — состояние, из которого система
  выходит сама. Застанет ли скан после загрузки `unmounted` — по логу телефона
  автора; тогда решать ему (`VolumeReadinessTest` закрепляет нынешний выбор).
- **Новый аргумент у `Core::scan`:** ломает десяток вызовов в чужих тестах и
  параллельные задачи; новый метод рядом дешевле.
- **Счётчик неизвестных в `ScanReport`:** трогает FFI-запись и Kotlin ради строки лога.

## Инварианты

- Вынутая карта (нет ни в `ready`, ни в `pending`) — файлы в `missing`, треки скрыты;
  карта вернулась — `returned`, те же треки с теми же ID.
- Файл, удалённый на деле, пропадает как раньше — и рядом с неизвестными тоже.
- Неизвестный файл не меняет доступность, источник, трек и отметку скана; не
  кандидат сведения (Р1.2) и не отдаёт свой трек копии.
- Скан без `pending` и без осечек даёт те же отчёты и тот же каталог, что `main`.
- Повторный скан после осечки или после того, как карта смонтировалась: файлы
  `unchanged`, теги не перечитываются, ID треков прежние.
- Журнал не пишется; формат каталога, журнала и FFI-записей (`ScanReport`) не меняется.
- Скорость: путь без осечек и без `pending` не медленнее — обход не делает лишних
  системных вызовов, а `diff` для файла, который виден, ничего нового не считает.

## Риски, принятые сознательно

Opus, прочти до исполнителя особенно п. 1–4; остальное — для полноты.

1. **Проверяемая карта остаётся в каталоге «доступной».** Читать её сейчас
   нельзя: трек с неё не заиграет, пока карту не смонтируют. Это лучше, чем спрятать
   всю SD-библиотеку из списков, плейлистов и «Любимого». Скан после монтирования
   сам не запустится: следующий пойдёт со старта приложения, по «Rescan» или через
   `UnavailableRescan`. Запускать скан по `ACTION_MEDIA_MOUNTED` — отдельная
   задача (см. «Замечено»).
2. **Только `checking`.** `unmounted` и `ejecting` — вынутая карта (см. «Отвергнуто»).
   Если загрузка телефона автора застаёт скан в `unmounted` — решает автор.
3. **Путь проверяемой карты — `/storage/<uuid>`**, по соглашению Android, потому что
   `getDirectory()` у неё `null`. У странной прошивки соглашение может не сойтись —
   защита тогда не сработает, как до задачи (вреда нет).
4. **Ошибка итератора записей** (имя неизвестно) делает неизвестной папку целиком на
   этот скан: настоящие удаления в ней заметит следующий.
5. Файл, удалённый **в момент** скана, если `metadata()` вернул `NotFound`, считается
   неизвестным на этот скан; следующий скан пометит его пропавшим. Раздельно
   `NotFound` не обрабатывается: цена — один скан, выигрыш — одна ветка меньше.
6. `Core::scan` остаётся экспортированным, но Kotlin его больше не зовёт.
7. **Как проверены тесты.** Эталонная реализация (откачена): всё зелёное, кроме
   Unix-файла (на Windows не собирается). Мутации эталона краснят свои тесты:
   `pending` не дописывается в `unseen` — четыре теста `r1_15_pending_volumes`;
   корень `pending` с разделителем в конце не нормализован — `a_pending_root_covers…`;
   `pending` бьёт `ready` — `a_volume_listed_both_ways…`; сравнение без границы
   сегмента — `a_pending_root_covers…` и `files_at_or_below…`; только точный путь без
   «под ним» — пять тестов; недоступные (`gone`) не защищены — `files_at_or_below…`;
   `ready` и `pending` перепутаны в FFI — тест FFI; перебор вместо набора — тест на
   50 000 путей (мутант считал дольше полутора минут при пороге 10 с, прогон
   оборван вручную). Отдельно: эталон и тесты прошли clippy; Unix-файл на Windows
   прогнан копией с подставленным `PermissionsExt` — собирается, clippy чист, тесты
   честно пишут `skipped`; на Linux он не запускался.
