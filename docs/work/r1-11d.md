## Цель

Когда задача сделана:

1. В секции поиска и на экране альбома **отказ сервера, истёкший срок и «нет соединения» —
   три разные беды**. 503, 5xx, 403, «не дождались» — «{провайдер} не отвечает»; 429 —
   «просит подождать»; «Нет сети» (и совет про прошивку TECNO/Infinix/itel) — только когда
   соединения не вышло (R1 №13, v0.2 №30).
2. **`Retry-After` доходит до ядра.** Короткий срок ядро ждёт и повторяет, длинный — не
   стучится; провайдер отдыхает ровно столько, сколько просил сервер.
3. **Таблица «статус HTTP → ошибка» — в одном месте** ядра и открыта для Kotlin
   (`check_http_status`): ею воспользуется Downloader YouTube (Ю3б), второй таблицы не будет.
4. В онлайн-секции поиска есть **«Повторить»** (R1 №15); возврат из альбома не запускает
   поиск заново и не сбрасывает список (R1 №14).
5. Поиск, альбом и поток, ушедшие до `connect_online` на холодном старте, **ждут его**
   (R1 №27, v0.2 №33).

## Решение

### А. Таблица «статус → ошибка» — `core/providers/src/http/status.rs` (новый)

Единственное место, где написано, что значит ответ с этим статусом. `HttpClient` берёт решение
отсюда, Kotlin — через `check_http_status` (раздел Г). Публично, из `plinth_providers::http`:

```rust
/// 2xx → Ok(()). 404, 410 → Unavailable("http N"). Остальное → Network("http N");
/// у статуса, который может пройти сам (429 и 5xx), со сроком сервера:
/// Network("http N, retry after S s"). У прочих срок отбрасывается.
pub fn check_status(status: u16, retry_after: Option<Duration>) -> Result<(), CoreError>;

/// Значение заголовка `Retry-After`: целые секунды (цифры, пробелы по краям
/// терпятся). Дата, дробь, знак, пустое, мусор, переполнение u64 — None.
pub fn parse_retry_after(value: &str) -> Option<Duration>;

/// Network("timed out") — как ядро писало «не дождались» и раньше.
pub fn timed_out() -> CoreError;

/// Что случилось с сетевым вызовом, по его ошибке.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum NetFailure {
    NoConnection,                                              // любой другой текст Network
    TimedOut,                                                  // ровно "timed out"
    Status { status: u16, retry_after: Option<Duration> },     // "http N[, retry after S s]"
}
impl NetFailure {
    /// None — ошибка не Network (Parse, Unavailable, …): в том числе Unavailable("http 404").
    pub fn of(error: &CoreError) -> Option<Self>;
}
```

И `pub(crate) fn is_transient(status: u16) -> bool` (429 и 500..=599). Таблица:

| Статус | Ошибка | Повтор в `HttpClient` | Здоровье провайдера |
|---|---|---|---|
| 2xx | — | — | успех |
| 404, 410 | `Unavailable` | нет | успех (провайдер жив) |
| 429, 5xx | `Network("http N")` | да | отказ; со сроком — пауза на срок (раздел В) |
| остальное (3xx, прочие 4xx) | `Network("http N")` | нет | 4xx не меняет, 3xx — отказ (как было) |

Текст ошибки — единственный носитель статуса и срока (`CoreError` и его `flat_error` в Kotlin не
меняются), но читает его **одна** функция, `NetFailure::of`. Разбор «http N» где-либо ещё
(`http_status` в `client.rs` и т. п.) удаляется. В тексте по-прежнему нет адреса и запроса.

`HttpResponse` (`transport.rs`) получает `pub headers: Vec<(String, String)>` (порядок и регистр
имён — как прислал сервер), `pub fn with_header(self, name: &str, value: &str) -> Self` и
`pub fn header(&self, name: &str) -> Option<&str>` (первое совпадение, регистр имени не важен).
`HttpResponse::ok` / `::status` — с пустыми `headers`. `FixtureTransport::recorded` строит ответ с пустыми `headers`.

### Б. `HttpClient::get_within` и `Retry-After` — `client.rs`

- Решение по статусу — `check_status` (старая `status_error` и `http_status` уходят).
- У ответа со статусом, который может пройти сам, читается `Retry-After` (`parse_retry_after`) и
  кладётся в ошибку (`check_status`). Срок принадлежит **только этой попытке**: следующая без
  заголовка живёт по своей паузе.
- Пауза перед следующей попыткой: `max(наша пауза, срок сервера)` — срок сервера нашу паузу не
  укорачивает. Через `pause`, как и раньше (тесты записывают паузы).
- Предел: `const MAX_RETRY_AFTER_WAIT: Duration = 10 с` (константа в `client.rs`, **не** поле
  `HttpPolicy` — литералы `HttpPolicy { … }` есть в чужих тестах). Сервер просит дольше —
  не ждём и не стучимся: возвращается последняя ошибка, с настоящим статусом и сроком.
- Уже существующее правило «пауза, съедающая остаток срока, не берётся» остаётся и возвращает
  ту же ошибку со статусом (не «timed out»).
- Без срока всё как было: 429 и 5xx — до трёх попыток с паузами 0,5 и 1 с. 403, 400, 3xx — сразу.
  404 и 410 — сразу `Unavailable`, что бы ни было в заголовках.
- «Срок вышел до первой попытки» — `timed_out()`.

### В. Здоровье — `Health::after` (`health.rs`)

Через `NetFailure::of`. Отказ статусом, который может пройти сам, **с ненулевым сроком** —
`Down { failures: прежние + 1, until: now + min(срок, down_for) }` с первого же отказа
(сервер сам сказал, когда вернуться). Срок 0 — обычный отказ. Остальное — как было: 4xx кроме
429 не меняют здоровье, 429/5xx без срока и 3xx — отказ, «нет соединения» и таймаут — короткий
бан (`down_for / 20`). `Registry` не меняется: бан по-прежнему отдаёт `Unavailable("provider … is down")`.

### Г. FFI — `core/ffi/src/api/online_api.rs`

```rust
pub enum NetAnswer {
    Response { status: u16, body: Vec<u8>, headers: Vec<NetHeader> },  // + headers
    NoAnswer { reason: String },        // соединения не вышло
    TimedOut,                           // новое: не дождались
    TooLarge,
}
pub enum OnlineProblem { NoNetwork, ProviderDown, RateLimited /* новое */, Broken }
#[derive(Debug, Clone, PartialEq, Eq, uniffi::Record)]
pub struct OnlineAlbumReply { pub tracks: Vec<OnlineTrackInfo>, pub problem: Option<OnlineProblem> }
// было: -> Result<Vec<OnlineTrackInfo>, CoreError>
pub fn online_album(&self, provider: String, item: String) -> Result<OnlineAlbumReply, CoreError>;
#[uniffi::export]
pub fn check_http_status(status: u16, retry_after: Option<String>) -> Result<(), CoreError>;
pub(crate) struct PlatformTransport(pub(crate) Arc<dyn NetTransport>);   // было приватным
```

- `PlatformTransport::get`: `Response` → `HttpResponse` с заголовками; `TimedOut` → `Err(timed_out())`;
  `NoAnswer` и `TooLarge` — как были.
- Одна функция `problem_of(&CoreError) -> OnlineProblem` для секции поиска и для альбома:
  `Network` + `Status { 429, _ }` → `RateLimited`; `Network` + другой `Status` или `TimedOut` →
  `ProviderDown`; `Network` + `NoConnection` → `NoNetwork`; `Unavailable` → `ProviderDown`;
  прочее → `Broken`.
- `online_album`: провайдер ответил `Network`, `Unavailable` или `Parse` — это `OnlineAlbumReply
  { tracks: [], problem: Some(problem_of) }`, не ошибка. Источники выключены, неверный ID,
  `Internal`, `Storage` — по-прежнему `Err`.
- `check_http_status` — таблица для Kotlin: `parse_retry_after(retry_after)` → `check_status`
  (через `panic::guard`). Kotlin-обёртки в этой задаче нет: Ю3б/Ю3в обернут её в пакете `ffi`.
- Тесты внизу `online_api.rs` (внутри файла) правятся механически: `Recorded` кладёт `headers` из
  ответа; восемь `core.online_album(…).unwrap()` → `….unwrap().tracks`; проверка «выключено —
  `Err(Unavailable)`» остаётся. Больше в них ничего не меняется.

### Д. Kotlin: транспорт, типы, репозиторий

- `NetAnswer.Response(status: Int, body: ByteArray, headers: List<Pair<String, String>> = emptyList())`
  и `NetAnswer.TimedOut` (`data object`) в `ffi/CoreOnline.kt`; `toRust()` и обратные отображения.
- `OnlineProblem.RATE_LIMITED`; `RustOnlineProblem.toApp()`.
- `OnlineAlbumReply(tracks: List<OnlineTrack>, problem: OnlineProblem?)`; `CoreOnline.album()`
  возвращает его; `internal fun RustOnlineAlbumReply.toApp()`. `CoreFailure` по-прежнему
  летит для `Err` ядра.
- `HttpUrlTransport`: заголовки ответа — в `Response.headers` (все пары, ключ `null` строки
  статуса пропускается, каждое значение — отдельной парой); `SocketTimeoutException`
  (в том числе срок запроса целиком) → `NetAnswer.TimedOut`; остальные `IOException` — `NoAnswer`
  с именем класса, как было.
- `CoreOnlineRepository.album`: `reply.problem?.let(OnlineAlbum::Failed) ?: OnlineAlbum.Tracks(reply.tracks)`;
  `catch (CoreFailure)` — как было (`problem()`).
- Экран альбома: `NO_NETWORK` → «Нет сети» (+ подсказка про прошивку, как было); `RATE_LIMITED` →
  `online_rate_limited` с именем провайдера; всё остальное — `online_album_unavailable`, как было.

### Е. Kotlin: поиск (R1 №14, №15) — `SearchViewModel`, `SearchScreen`

- Новое: `fun onRetryOnline()` — повторяет онлайн-поиск по тому же устоявшемуся тексту
  (`Searching` → ответ); пустой текст или выключенные источники — ничего.
- Последний ответ сети помнится в модели (одна запись: текст → `OnlineResults.Found`), и пока
  текст тот же, новый запрос не уходит — ни после повторной подписки, ни после ухода с экрана
  больше чем на 5 с. Ответ с бедой помнится так же: заменить его могут только «Повторить»
  и новый текст.
- Повторная подписка **не проходит через пустое**: первый же кадр — прежнее состояние, ни
  `OnlineResults.None` / `Searching`, ни пустой библиотечный список для прежнего текста (иначе
  `LazyColumn` уходит из композиции и теряет прокрутку).
- `SharingStarted.WhileSubscribed(5_000)` остаётся: уход с экрана больше чем на 5 с отменяет идущий
  запрос (Р1.11а, `SearchViewModelCancelTest` не меняется и проходит). Библиотечный запрос
  вправе перезапуститься.
- `SearchScreen.ProblemNote`: под текстом беды (и под подсказкой про прошивку) — кнопка
  «Повторить» (`online_retry`, строка уже есть) → `viewModel::onRetryOnline`; для всех бед секции.
  Текст `RATE_LIMITED` — `online_rate_limited`.

### Ж. Kotlin: холодный старт (R1 №27, v0.2 №33) — `online/GatedOnlineRepository.kt` (новый)

Гонка: `OnlineSwitch` включает источники (`setEnabled`) и поиск/загрузчик плеера идут в ядро
одновременно, оба ждут одно открытие ядра; кто первый — тот и прав. Ядро не различает «выключены»
и «ещё не включены», поэтому ждать должен тот, кто знает порядок: Kotlin.

```kotlin
class GatedOnlineRepository(
    private val inner: OnlineRepository,
    private val waitLimit: Duration = 60.seconds,
) : OnlineRepository
```

- `setEnabled(enabled)`: делегирует; **в `finally`** открывает ворота — упало подключение или
  выключено, ждать всё равно больше нечего.
- `search`, `album` (suspend): ждут ворота не дольше `waitLimit` (отмена корутины — обычная),
  потом делегируют. Вышел срок — вызов всё равно идёт дальше (ядро решит само).
- `stream` (блокирующий, зовёт загрузчик плеера): то же ожидание, прерываемое (`InterruptedException`
  идёт наружу), потом делегирует.
- `known`, `add` — каталог, не ждут.
- `OnlineModule.provideOnlineRepository` возвращает `GatedOnlineRepository(CoreOnlineRepository(…))`;
  `OnlineSwitch` получает этот же репозиторий (через DI), `OnlineSwitch.kt` не меняется.

### Отвергнуто

- **Новый вариант `CoreError`** — ломает `CoreException` в Kotlin и все `match`; текст `Network`
  уже несёт статус, достаточно одного читателя (`NetFailure::of`).
- **Разбор статуса по тексту ошибки в Kotlin** (для экрана альбома) — вторая таблица; поэтому
  `online_album` отдаёт `problem`, как секция поиска.
- **Поле `HttpPolicy::max_retry_wait`** — ломает литералы `HttpPolicy { … }` в чужих тестах.
- **Менять `Registry`** (отдавать причину бана вместо `Unavailable`) — не нужно задаче, см. ограничения.
- **Ждать `connect_online` внутри ядра** (condvar) — порядок знает Kotlin, и ядро блокировалось бы
  на событии платформы.
- **`SharingStarted.Eagerly` для `uiState`** — ломает Р1.11а (отмена при уходе с экрана).
- **Дата в `Retry-After`** — второй разбор времени с часами ради редкого случая.

### Принятые ограничения

- Второе нажатие «Повторить» в паузе отдыха провайдера покажет «не отвечает» (бан), а не «просит
  подождать»: бан отдаёт `Unavailable`.
- `Retry-After` датой игнорируется — клиент живёт по своей паузе.
- 429 без срока по-прежнему повторяется три раза (0,5 и 1 с).
- Таймаут соединения при «Wi-Fi без интернета» теперь «не отвечает», а не «нет сети»; подсказка про
  прошивку — только при отказе соединения (так вёл себя сбой Н7: `ConnectException`).
- Экран альбома без срока и отмены (`resolve` с `Limits::none()`) — Р1.11д.

## Инварианты

- Статус и срок едут только в тексте `Network`, грамматика одна, читает её одна функция.
- В тексте ошибки нет адреса и запроса (ADR 0008).
- `Unavailable` (404, 410) провайдеру не в укор; 4xx кроме 429 здоровье не меняют.
- Срок сервера никогда не укорачивает нашу паузу; срок дольше 10 с и срок, не влезающий в
  остаток срока поиска, не ждутся, а ошибка остаётся настоящей (429, не «timed out»).
- Подсказка про прошивку — только для `NO_NETWORK`.
- Отмена поиска при уходе с экрана и смене запроса работает, как в Р1.11а.
- Ожидание первого `setEnabled` ограничено и прерываемо; упавший `setEnabled` ворота открывает.
- Существующие тесты (кроме перечисленных в «Файлы») проходят без правок.
