## Цель

Файл, который человек перенёс, переименовал вместе с папкой или переложил на
другую SD-карту, не теряет лайк, оценку, плейлисты и историю: после скана
перепривязка узнаёт его по паспорту, трек получает прежний ID, а скрытая
запись старого пути уходит из каталога.

## Контекст

Что происходит сейчас. Личность трека в каталоге — путь. Скан видит новый путь
как новый трек (`scan/mod.rs:182` `add`, `TrackId::new()`), а старый помечает
недоступным и скрывает (`scan/diff.rs:27–50`, `scan/mod.rs:172–180`).
Лайки, плейлисты и история лежат в журнале по ID старого трека, и в списках их
не видно. `relink` (`sync/src/journal/relink.rs:35`) ищет по паспорту только
треки журнала, **которых нет в каталоге**; старый трек в каталоге остаётся
(недоступный), поэтому «потерянным» не считается.

Прочитать:

## Решение

**Опустевший трек** — у него есть источники, и все они — локальные файлы с
`availability = 'unavailable'`. Доступный файл, сетевой источник (хоть бы и
недоступный) и отсутствие источников — не опустевший: сетевой трек не
«переезжает», его вернёт `restore_online_track`.

**Перепривязка считает потерянным и опустевший трек.** Паспорт журнала,
чей трек в каталоге опустел, ищется среди **живых** треков каталога тем же
`best`/`score`; нашёлся — новый трек (вместе со своими версиями, файлом и
артистами) получает ID опустевшего, а запись опустевшего уходит из каталога.
Лайки, оценка, плейлисты и история остаются там, где были: в журнале они по ID
опустевшего, и этот ID теперь у играющего трека. Если новый трек успел получить
свои данные (послушали копию), работает слияние Р1.1 (`fold`) — только в
сторону старшего ID, как раньше.

Новые методы `Database` (`passport_repo.rs`, `impl Database`):

```rust
/// Опустевшие треки: у трека есть источники, и все они — локальные файлы
/// с `availability = 'unavailable'`. Пропавший файл, сетевой источник и
/// трек без источников сюда не попадают.
pub fn gone_tracks(&self) -> Result<BTreeSet<TrackId>, CoreError>;

/// Трек `from` занимает место опустевшего трека `to`: запись `to` (версии,
/// файлы, учёт скана, связи с артистами — каскадом) удаляется, затем
/// `rekey_track(from, to)`. Всё одной транзакцией, входящей в открытую
/// (`atomically`, как у `rekey_track`). Отказ — `CoreError::Storage`,
/// каталог прежний: `from == to`; `from` нет в каталоге; `to` не опустевший
/// (в том числе его нет вовсе). `prune_catalog` не зовёт — это делает
/// `relink` один раз после всех замен.
pub fn replace_gone_track(&self, from: TrackId, to: TrackId) -> Result<(), CoreError>;
```

Подсказка к `gone_tracks`: один запрос по `version JOIN source`, сгруппированный
по `v.track`, с условием `count(*) = sum(s.local_uri IS NOT NULL AND
s.availability = 'unavailable')`. Проверка `to` в `replace_gone_track` —
отдельным запросом по одному треку, **не** через `gone_tracks()`: метод
зовётся по разу на каждый перенесённый файл, а переименование папки — это
тысячи файлов.

Изменения в `relink.rs` (сигнатуры публичного API не меняются):

1. В начале `let gone = db.gone_tracks()?;`. Живые треки каталога — `catalog`
   без `gone` (раньше `known` был всем каталогом). `lost` — паспорта журнала,
   чьего трека нет среди живых.
2. `free`/`held` собираются **только из живых**: опустевший не добыча и не
   кандидат на слияние (иначе скрытый остаток старого дубликата перехватит ID —
   тест `a_hidden_leftover_does_not_take_the_id_of_a_moved_file`).
3. Везде, где был `db.rekey_track(found.track, passport.track)` — прямой путь
   и конец `fold`, — теперь `take_place`. `fold` получает `&BTreeSet<TrackId>`
   (опустевшие). Порядок в `fold` прежний: сначала журнал, потом каталог.

   ```rust
   // приватное, relink.rs
   fn take_place(db: &Database, gone: &BTreeSet<TrackId>, from: TrackId, to: TrackId) -> Result<(), CoreError> {
       // to ∈ gone → db.replace_gone_track(from, to); иначе db.rekey_track(from, to)
   }
   fn fold(journal: &mut Journal, db: &Database, gone: &BTreeSet<TrackId>, from: TrackId, to: TrackId)
       -> Result<(), CoreError>;
   ```
4. Остальное не меняется: порядок «свободный кандидат по `best` → сетевой по
   паспорту → слияние с занятым, **новее** потерянного ID», `fold_ops`, `best`,
   `score`, число в ответе (перенесённые + слитые + восстановленные).
5. После циклов, если `gone` не пуст, **один** `db.prune_catalog()` — альбомы и
   артисты, оставшиеся без треков (перенос с правкой альбома оставляет старый
   альбом пустым). Не на каждый трек: `prune_catalog` просматривает таблицы.
6. Обновить doc-комментарии: модуля `relink.rs` и `relink` (перенесённый файл —
   тоже «потерянный»), `track_passports`/новых методов; в логе — счётчики, без
   путей и названий (§17.3).

Отвергнуто:

- **Искать перенос в сканере** (`diff`: `added` ↔ `missing`, переписать путь у
  того же источника). Не покрывает копию, оригинал которой удалён уже
  следующим сканом (тест `a_copy_that_got_data_…`); скан не знает о данных
  пользователя; нужен был бы счётчик в `ScanReport` → FFI и Kotlin.
  Перепривязка идёт сразу после каждого скана и уже умеет сливать данные (Р1.1).
- **Переставить источник нового трека на скрытый** (скрытая запись остаётся,
  получает новый файл). Теги, версия и артисты нового файла свежее скрытых;
  `rekey_track` уже есть и им кончается `fold`.
- **Выдерживать несколько сканов** прежде чем считать файл перенесённым:
  перенос и «карту вынули» выглядят одинаково, а ожидание держит данные
  скрытыми. Цена ошибки — в «Рисках».
- **Считать опустевшим любой трек без доступного источника**, в том числе
  сетевой: файла, который мог переехать, у него нет.

Не входит: обновление паспорта при скане (Р1.7), уборка скрытых остатков без
данных (Р1.11), склейка дубликатов (v0.3), сообщение человеку о числе
перенесённых.

## Инварианты

- Данные не теряются. Журнал только пополняется операциями `fold`; запись
  опустевшего трека уходит из каталога в той же транзакции, где преемник
  получает его ID (`replace_gone_track`).
- Играющее не трогается: трек, у которого есть хоть один не-недоступный
  источник, сетевой трек и трек без источников не заменяются и не удаляются.
- Подходящего файла нет — каталог не меняется. Скрытый трек остаётся, и
  вернувшийся файл (`returned`) оживляет его вместе с данными.
- Повторный `relink` возвращает 0 и ничего не меняет: ни дублей прослушиваний
  и записей плейлиста, ни разворота слияния. Оборванный посреди `fold` повтор
  доводит дело до конца (журнал уже записан, операции идемпотентны, Р1.1).
- Слияние идёт только в сторону старшего ID (`candidate.track >
  passport.track`): так ID сходятся на всех устройствах. Дубликат старше
  опустевшего не сливается и не переименовывается.
- После переноса следующий скан не видит ни новых, ни изменённых, ни
  вернувшихся, ни пропавших файлов: источник и отметка скана переехали вместе
  с треком.
- Один `gone_tracks()` и один `prune_catalog()` на вызов `relink`;
  `replace_gone_track` — константное число запросов на файл.
- Формат журнала, схема БД, сканер, FFI и Kotlin не меняются.

  Kotlin, схема или миграция, `ScanReport`); проверки упали дважды подряд;
- прежний тест из «Готово, когда» краснеет от новой логики — править его
  нельзя;
- `gone_tracks` не выходит одним запросом, как в подсказке, или
  `replace_gone_track` не получается без собственной транзакции — вложенная
  в транзакцию `relink` она упадёт.

## Риски, принятые сознательно

- **Карту вынули, а те же песни лежат ещё где-то** (скачанная копия): скану
  «вынули» и «перенесли» неотличимы. Пропавшие с карты треки с данными уступят
  место копиям, а когда карту вставят обратно, её файлы станут новыми треками
  без данных. Данные видны сразу, дубликаты разберёт v0.3. Выдерживать
  несколько сканов отвергнуто (см. выше).
- **Перенос вместе с правкой названия или исполнителя** (редакторы тегов)
  не узнаётся: паспорт — название и исполнитель. Паспорт журнала обновляется
  при следующем действии с треком; при скане — с Р1.7. Файл без тегов идёт под
  именем файла, и переименование его тоже не узнаётся.
- **Две разные записи с одним названием, исполнителем и длительностью в
  пределах двух секунд** — тот же риск, что у перепривязки после
  переустановки; альбом и MBID лишь предпочтение.
- **Удаление новой из двух копий с данными**: данные пропавшей остаются
  скрытыми (S8). Склейка дубликатов — v0.3.
- Инструментальные контрактные тесты на эмуляторе (`seed_for_test` и
  `hide_for_test`, `app/src/androidTest/.../library/`) не запускались; в них
  скрытые файлы не засеваются заново теми же названием и исполнителем, поэтому
  затронуты быть не должны.
