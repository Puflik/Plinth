## Цель

Файл перенесли в другую папку, переименовали его или папку, карта
оказалась с другим именем тома — скан узнаёт в новом файле пропавший, и трек
остаётся прежним: тот же ID, тот же источник, та же дата добавления. Лайк,
оценка, плейлисты и история видны на нём сразу после скана, журнал при этом
не пишется.

## Решение

**1. Узнаёт скан, а не перепривязка.** Сопоставление идёт в `scan()` — между
чтением тегов (`read`) и записью пачек, пока новый файл ещё не стал треком.
Найдена пара — новый файл пишется как новое место пропавшего: тот же
источник получает новый путь. Почему так, а не переносом данных
перепривязкой (`relink` + `fold` из Р1.1):

- журнал не пишется вовсе. Карта на 5 000 треков с новым именем тома — ноль
  операций, а не тысячи `Like`/`AddEntry`/`Play` с копиями; пути в журнал не
  попадают (ADR 0007);
- ID сохраняется у всех треков, а не только у тех, на кого есть данные в
  журнале: очередь (`QueueKeeper`) хранит ID треков, прослушивание —
  `source` (ID источника), «Недавно добавленные» — `added_at`;
- скан в одном проходе знает оба факта — какой файл исчез и какой появился.
  Перепривязка видит каталог после скана: ей пришлось бы удалять скрытый
  трек и переключать ID нового — больше движущихся частей.

Отвергнуто: перенос данных перепривязкой (выше); сведение внутри `write` —
`write` пишет пачками и служит `seed_for_test` и помощнику тестов
`common::scan` для заведения новых треков; второй источник у старого трека
со старым путём — висящий недоступный источник и два локальных источника
одной версии, которых каталог сейчас не знает.

**2. Общий механизм с Р1.1 — сравнение паспортов.** `key`, `best`, `score` и
`DURATION_TOLERANCE` переезжают из `relink.rs` в
`core/library/src/model/passport.rs` без изменения правил и служат обоим:

```rust
// core/library/src/model/passport.rs
/// Разница длительности одной песни в разных файлах: кодировщики по-разному
/// считают тишину в начале и конце.
const DURATION_TOLERANCE: Duration = Duration::from_secs(2);

impl TrackPassport {
    /// По чему паспорта сводятся в пары: нормализованные название и исполнитель.
    pub fn key(&self) -> (String, String);
    /// Насколько `other` похож на этот паспорт; `None` — это другой трек.
    /// Ключи сверяет вызывающий. MBID, если известен у обоих, — совпадает
    /// (+4); альбом у обоих один (+2); длительность, если известна у обоих, —
    /// в пределах двух секунд (+1), дальше — `None`. Симметрично.
    pub fn likeness(&self, other: &TrackPassport) -> Option<u8>;
    /// Лучший из подходящих `candidates`; при равенстве — первый.
    pub fn best_match(&self, candidates: &[TrackPassport]) -> Option<usize>;
}
```

`relink.rs` зовёт их вместо своих функций; своих копий там не остаётся.
Поведение перепривязки не меняется. Слияние данных (`fold`) скану не нужно:
новый файл сводится в том же скане, где появился, своих данных у него нет.

**3. Кто «пропавший» (кандидат).** Локальный файл каталога, которого обход
не нашёл и который лежит не в непрочитанной папке:

- был доступен до этого скана — `diff.missing`, как сейчас;
- недоступен с прошлых сканов и по-прежнему не найден — новое поле
  `ScanDiff::gone`, тем же правилом про непрочитанные папки, порядок по
  источнику, как у `missing`.

Не кандидаты: файлы на своём месте (в том числе вернувшиеся), файлы в
папках, которые не прочлись. Вынутая карта особым случаем не считается:
Kotlin не отдаёт её корень, её файлы пропадают, как и сейчас.

**4. Кто сводится.** Только новые файлы (`diff.added`), теги которых
прочлись (`readable`). Нечитаемый новый файл заводится под именем файла, как
сейчас: `write` пропускает файл с `known` и `!readable`, и сведённый
нечитаемый файл не попал бы в каталог вовсе. Паспорт нового файла — по тем
же правилам, что у каталога: название — `title(scanned)` (тег или имя файла),
исполнитель — `tags.artist` или пустая строка, альбом — `tags.album`,
длительность — `tags.duration`, MBID и источников нет. ID трека в нём —
заглушка: сравнение его не читает. Паспорт пропавшего — из каталога
(`Database::track_passport`), а не из журнала: у трека без данных паспорта в
журнале нет, а теги каталога свежее (паспорт журнала может отстать — Р1.7).

**5. Как сводится.** Новые файлы — по порядку `files` (новые идут по пути:
обход их сортирует). Для каждого — кандидаты с тем же `key()`, из них
`best_match`; кандидаты одного ключа заранее упорядочены по ID трека, так
что при равенстве берётся трек, заведённый раньше (меньший ID). Каждый
пропавший берётся один раз, каждый новый файл сводится не больше чем с
одним. Без квадратичных проходов по файлам: на 20 000 перенесённых время
растёт линейно.

**6. Что делает пара.** Новому файлу ставится `known` = `KnownFile`
пропавшего, а пропавший снимается с `diff.missing` — иначе `mark` тут же
скрыл бы его снова. Запись идёт прежним путём `update` без правок: трек и
версия обновляются из тегов, тот же источник (тот же ID) получает новый
`local_uri`, `available` и новую отметку скана с новой папкой. ID трека,
версии и источника и `added_at` остаются. `mark` не меняется: сведённого
уже нет в `missing`, а `gone` он не трогает — эти файлы и так недоступны.

**7. Чтение базы.** Паспорта пропавших читаются одним `DbAccess::run` за
скан и только если есть хотя бы один читаемый новый файл и хотя бы один
пропавший. Обычный повторный скан (нового нет) базу лишний раз не читает.
Нового SQL не нужно: хватает `track_passport`.

**8. Итог скана.** Новое поле — сразу после `missing`:

```rust
// core/library/src/scan/mod.rs, ScanReport
    pub missing: u32,
    /// Пропавшие файлы, найденные на новом месте (Р1.2): их треки остались
    /// прежними. В `added` и `missing` они не считаются.
    pub moved: u32,
```

`added` — новые файлы, ставшие новыми треками; `missing` — пропавшие в этом
скане и не найденные; `found` — как сейчас. Отчёт считается после сведения;
остановленный на чтении скан, как и сейчас, отдаёт пустой отчёт со
`stopped`. Зеркало `#[uniffi::remote(Record)] ScanReport` в
`core/ffi/src/api/scan_api.rs` получает то же поле на том же месте (иначе не
соберётся). Kotlin не меняется: `CoreScanReport` берёт поля по именам, и
показывать `moved` пока некому.

**9. Журнал и перепривязка.** Скан журнал не пишет. `Core::scan` по-прежнему
зовёт `relink_catalog`; для перенесённых треков ей делать нечего — их ID в
каталоге.

**Предлагаемое устройство (не обязательно дословно):** приватный модуль
`core/library/src/scan/moved.rs` с функцией вроде
`pub(super) fn pair(diff: &mut ScanDiff, files: &mut [ScannedFile], vanished: Vec<(KnownFile, TrackPassport)>) -> usize`;
`scan()` собирает `vanished`, зовёт её и считает отчёт. Обязательны
публичные сигнатуры выше (`TrackPassport::key/likeness/best_match`,
`ScanDiff::gone`, `ScanReport::moved`) и правила п. 3–8.

## Инварианты

- Перенесённый файл: ID трека, версии и источника и `added_at` прежние;
  старого пути в каталоге нет; источник доступен по новому пути, отметка
  скана и папка — новые. Следующий скан ничего не меняет.
- Файл, который на месте, свой трек не отдаёт: копия рядом с живым
  оригиналом — новый трек.
- Нечитаемый новый файл не сводится и заводится под именем файла, как
  раньше.
- Сведение одно к одному и детерминировано (порядок путей, лучшее сходство,
  при равенстве — трек с меньшим ID). Правила сходства — те же, что у
  перепривязки, в одной функции.
- Перепривязка ведёт себя как прежде: `core/sync/tests/passports.rs` зелёный
  без правок.
- Скан журнал не пишет; `relink` после скана с переносом ничего не находит.
- Остановка скана на записи не портит каталог: записанные пачки целы,
  несведённое остаётся как было, следующий скан сведёт снова.
- Без нового файла или без пропавших сведение базу не читает. Сведение
  линейно по числу файлов.
- Путей в логах нет (§17.3): отчёт — только числа.
- `seed_for_test` и `scan::write` не сводят — они заводят новые треки, как
  раньше.
- Прежние тесты не меняются (`scan.rs`, `passports.rs`, тесты в `diff.rs` и
  `scan_api.rs`, Kotlin).

  `write`, `ScanDiff::gone`, `ScanReport::moved`, модуль `relink.rs`,
  `Core::scan`.
- Новых `#[allow]`, `unwrap`/`expect` вне тестов нет; CI ветки зелёный;
  отчёт заполнен.

## Остановиться и написать, если

- защищённый тест кажется неверным; нужен файл вне «Менять»; проверки упали
  дважды подряд;
- прежний тест падает из-за сведения (ждёт нового трека там, где правило
  сводит) — это решение, не код;
- прежнего `update` не хватает, чтобы перевести источник на новый путь
  (уникальный индекс `local_uri`, внешние ключи, отметка скана), или `mark`
  нужно менять сильнее, чем «сведённого нет в `missing`»;
- сведению нужны запись в журнал, правка перепривязки сверх переезда
  сравнения или новый SQL;
- Gradle не собирается из-за нового поля.

## Риски, принятые сознательно

- **Сначала копия, потом удаление — разными сканами.** Копию, найденную,
  пока оригинал на месте, скан заводит новым треком; когда оригинал удалят,
  его данные останутся на скрытом треке. Два живых файла одной песни — задача
  идентичности v0.3 (B2, B3), не переноса. Одним сканом (перенос внутри
  тома, переименование, новая карта) это не грозит.
- **Карта вынута, а те же песни заново легли на телефон.** Новые файлы
  заберут треки карты; вернётся карта — её файлы станут новыми треками без
  данных. Данные не теряются: они у копий, которые у человека были на тот
  момент.
- **Слабые теги.** Одно название и исполнитель, без альбома, длительности в
  пределах двух секунд — разные песни могут свестись (то же правило, что у
  перепривязки после переустановки).
- **Перенос и правка тегов разом** не узнаются: общего паспорта нет — как и
  до задачи. Отпечатки — v0.3.
- Удалённую песню скачали снова через месяцы — к ней вернутся прежние лайк,
  оценка, история и блокировка трека. Так и задумано.
- `moved` виден только в логе: Kotlin его не показывает.

## Замечено, не в этой задаче

- Р1.7: паспорт в журнале не обновляется при правке тегов. Сведение скана
  берёт паспорт каталога и от этого не зависит, перепривязка после
  переустановки — зависит.
- Жадность сопоставления (каждый берёт лучшего по очереди) — та же, что у
  перепривязки; ревью v0.2 отметило её как «не проверено».
- Личность известного пути — сам путь: если на место перенесённого файла
  тут же лёг другой, он перезапишет трек прежнего (было и до задачи).
- `ScanResult.updated` в `LibraryScanner.kt` считается, но нигде не читается.
