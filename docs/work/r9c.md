## Цель

1. Лайки, оценки, плейлисты и история остаются на песне, когда файл переносят в
   два шага (копия, потом удаление — так переносят на SD-карту), когда скан застал
   файл недокопированным и когда перенос пришёлся на обход (№2).
2. Перенесённый файл достаётся треку, которому он подходит лучше всех (№12), а
   между пропавшими треками первым — тому, у кого есть данные пользователя, а не
   самому старому (№11).
3. «Восстановить» посреди «Пересканировать» не теряет новые теги файла и не рвёт
   сведение перенесённого файла (№19).

## Решение

### Что не так

Пары «новый файл ↔ пропавший трек» строит только скан, в котором файл появился
(`moved::relocate` берёт кандидатами файлы с `known.is_none()`). Файл, который
получил свой трек раньше, дальше идёт как «знакомый» и к сведению не допускается, а
пропавший трек (`missing`, потом `gone`) ждёт «нового» файла, которого уже не будет.
Три сценария №2 — один механизм: файл заведён своим треком, когда оригинал ещё был
жив (а, в) или читался не до конца (б). Сценарий (в) — файл виден на двух местах за
один скан — даёт то же состояние, что (а); отдельного теста у него нет: гонку с обходом
тестом не поймать.

### Варианты для №2

- **А. Двойник отдаёт файл (выбран).** После основной записи скан смотрит пропавшие треки,
  у которых есть данные пользователя, и ищет среди живых файлов каталога **двойника**:
  трек без данных с тем же ключом паспорта и подходящим сходством. Файл двойника становится
  новым местом пропавшего — ровно как у перенесённого файла в Р1.2 (тот же источник получает
  новый путь; ID трека, ID источника и дата добавления прежние), трек двойника уходит из
  каталога. Журнал не пишется; всё в `plinth-library`; одна транзакция на пару; оборванный
  скан достроит следующий. Почему: данные в журнале лежат за ID — ID не меняется, значит и
  журнал (`relink`, `fold`, `describe_changed`) ничего не замечает; ядро скана не получает
  зависимости от `plinth-sync`; Р9г не задето (общий только `model/passport.rs`).
- **Б. Слияние в журнале при перепривязке** (так планировал Sonnet на замере Р1.2,
  `docs/work/effort/r1-2-sonnet-max.md`): после скана `relink` сливает данные скрытого
  трека в живого двойника через `fold`, скрытый трек удаляется. Плюс: покрывает и двойника
  с данными (данные объединяются). Отвергнут для этой задачи: пишет в журнал по догадке
  при обычном скане; живёт в `relink.rs`/`passport.rs` пакета `sync` — файлы Р9г; данные
  переезжают на ID двойника, а не остаются на своём; те же вопросы про вынутую карту.
  Слияние данных двух треков остаётся «Замеченным» (ниже) и ложится поверх А отдельной задачей.
- **В. Копии — источники одной версии** (идентичность v0.3, эпик A): убирает дубли из
  списков, но меняет модель и закреплённое тестом Р1.2 «копия рядом с живым оригиналом —
  новый трек». Вне Р9в.
- **Г. Выдерживать несколько сканов**, прежде чем считать файл перенесённым: отвергнуто ещё
  в Р1.2 (перенос и «карту вынули» неотличимы, ожидание держит данные скрытыми).

### Ограничения выбранного решения (принятые)

1. **Двойник с данными не трогается.** Копию между шагами лайкнули, оценили, добавили в
   плейлист или послушали — её трек не отдаётся, данные оригинала остаются на скрытом треке
   (как и сейчас). Склеить данные двух треков можно только в журнале — вне этой задачи.
2. **Пропавший трек, чей том скан не обходил, двойнику ничего не отдаёт.** Вынутая карта и
   «перенесли» для скана неотличимы; без этого условия данные карты ушли бы давно лежащей
   копии на телефоне и не вернулись бы вместе с картой (минус варианта Б в замере Р1.2).
   Условие: путь файла пропавшего лежит под одним из корней `Volumes::ready` этого скана.
   Новые файлы условием не связаны — сведение Р1.2 для них прежнее (принятый риск Р1.2:
   «Карта вынута, а те же песни заново легли на телефон»).
3. **Слабые теги** — тот же риск, что в Р1.2: название, исполнитель и длительность ±2 с —
   правила `TrackPassport::key`/`likeness`; альбом у двойника может быть другой.
4. **Ретро-починка.** Этап срабатывает и для давно скрытых (`gone`) треков с данными — при
   ближайшем скане, где что-то пропало или изменилось. У тех, кто уже потерял лайки по №2, они
   вернутся на файл-двойник, если он есть.

### Новые типы и функции — дословно

```rust
// core/library/src/model/passport.rs (+ pub use в model/mod.rs)
/// Пара, найденная [`TrackPassport::pair_up`]: индексы в `wanted` и `candidates`
/// и сходство (`likeness`).
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct Pairing {
    pub wanted: usize,
    pub candidate: usize,
    pub score: u8,
}

impl TrackPassport {
    /// Сводит `wanted` с `candidates`; пара — тот же ключ (`key`) и `likeness` не `None`.
    /// Пары раздаются лучшими вперёд: по убыванию сходства; при равном сходстве
    /// первым идёт кандидат с меньшим `rank(индекс кандидата)`, затем желающий,
    /// стоящий раньше в `wanted`, затем кандидат, стоящий раньше. Каждый паспорт
    /// входит в пару не больше одного раза. Порядок результата не определён.
    pub fn pair_up<R: Ord>(
        wanted: &[TrackPassport],
        candidates: &[TrackPassport],
        rank: impl Fn(usize) -> R,
    ) -> Vec<Pairing>;
}
```

Группировать кандидатов по `key()` надо (иначе перебор — квадрат), сравнивать паспорта —
только `likeness`. `best_match` остаётся: им пользуется перепривязка (`core/sync`); её жадность —
№21, это Р9г, и Р9г переведёт перепривязку на `pair_up` — так правила скана и перепривязки
не расходятся (комментарий над `impl TrackPassport` это требует).

```rust
// core/library/src/db/repo/scan_repo.rs
impl Database {
    /// Треки каталога, на которые у пользователя есть данные: строка `track_user`,
    /// запись плейлиста, прослушивание, решение о склейке (обе стороны), блокировка
    /// трека — то же, что журнал считает данными (`referenced` в `core/sync`).
    pub fn tracks_with_user_data(&self) -> Result<HashSet<TrackId>, CoreError>;

    /// Трек, которому сейчас принадлежит версия; версии нет — `None`. ID версии и
    /// источника перепривязка не меняет, ID трека — меняет.
    pub fn track_of_version(&self, version: VersionId) -> Result<Option<TrackId>, CoreError>;
}
```

`tracks_with_user_data` — один запрос `UNION` по `track_user`, `playlist_entry`, `play_event`,
`merge_decision` (`track_low`, `track_high`), `block_entry` (`kind = 'track'`; `target` — 16 байт ID).

### Этап 1 — раздача пар лучшими вперёд, данные — первыми (№12, №11)

`moved::pair` (и `relocate`, который его зовёт) переписывается на `TrackPassport::pair_up`.
`wanted` — паспорта новых читаемых файлов в порядке `files` (обход сортирует по пути).
Пропавшие делятся на две группы: **с данными пользователя** (`tracks_with_user_data()`) и
остальные; сначала раздаётся первая группа (каждый берёт свой лучший файл из свободных), затем
вторая — из оставшихся. Внутри группы — `pair_up`, `rank` кандидата — `(не исчез в этом скане,
ID трека)`: при равном сходстве первым идёт исчезнувший в этом скане (защищённый тест Р1.2
`r1_2_vanished_now_first.rs`), затем более старый трек. Почему данные — первыми, а не только при
равном сходстве: трек с данными, которому файл не достался, остаётся скрытым при живом файле, а
этап 2 всё равно отдал бы файл ему (двойник без данных уходит); так итог не зависит от того, какой
из двух этапов его достроил, и пара «данные ↔ файл» не проходит через промежуточного владельца.
Множество треков с данными — один вызов `tracks_with_user_data()` в том же заходе в базу, что и
`track_passports()`; сведение по-прежнему идёт только когда есть читаемый новый файл и
пропавший. `Candidates`, `order`, `take` уходят. Внутренние тесты `moved.rs` (`pair(…)`) — править
сигнатуры вызовов, смысл не ослаблять: у `pair` появляется параметр с множеством треков с данными.

### Этап 2 — двойник отдаёт файл (№2)

Новый модуль `core/library/src/scan/twin.rs`; зовёт его `scan_volumes` **после** основной
записи (`write` по пачкам) и **до** `mark`. Порядок внутри:

1. **Ворота** (в памяти, без заходов в базу): этап запускается, только если скан что-то
   потерял или изменил — `diff.missing` не пуст или `diff.changed` не пуст — **и** остаток
   `diff.missing ∪ diff.gone` после этапа 1 не пуст. Тихий скан (ничего не пропало и не
   изменилось) не делает ни одного захода: пропавший навсегда трек с лайком, которому двойника
   нет, не должен стоить базе лишнего на каждом скане (тест `a_quiet_scan_does_not_look_for_twins`).
   Из остатка берутся те, чей путь лежит под корнем из `volumes.ready` (путь — из `known`, снимка в
   начале скана: источник → путь; граница — целый сегмент пути, как в `diff::is_unknown`). Пусто —
   выход. Дальше — один заход в базу (`db.run`): п. 2; из пропавших остаются только те, чей трек (по
   **свежему** ID) несёт данные. Пусто — выход.
2. **Свежее состояние** (в том же заходе в базу): `known_local_files()` — после записи он знает и
   новые файлы, и обновлённые теги изменённых; ID треков в нём свежие (перепривязка могла пройти
   во время скана, №19). Пропавших сверять по ID **источника**: `KnownFile.source` не меняется.
   Паспорта — `track_passports()`; данные — `tracks_with_user_data()`.
3. **Двойники.** Двойник — файл, который скан видел (путь есть в `walked.files`), чей источник
   доступен (после записи), чей трек: без данных, ровно с одним локальным файлом, не входит в
   остаток пропавших, и теги которого в этом скане прочлись (файл, у которого чтение не удалось —
   `readable == false` в `files`, — не двойник: его теги в базе — имя файла). Паспорт двойника —
   из `track_passports()` (для только что обновлённого файла он уже свежий). Оставлять в
   кандидатах только двойников с ключом, который есть среди пропавших с данными.
4. **Пары:** `TrackPassport::pair_up(пропавшие с данными, двойники, rank)`; порядок пропавших:
   исчезнувшие в этом скане, затем давно недоступные, внутри — по ID трека; `rank` двойника — ID
   его трека.
5. **Теги двойников** читаются `reader.read` вне базы (как весь скан); файл не прочёлся — пара
   отбрасывается (в лог, не ошибка).
6. **Запись пачками по `BATCH`**, каждая — `db.run(|db| db.in_transaction(…))`. На пару, внутри
   транзакции: ID треков **заново** по версиям (`track_of_version` — перепривязка могла пройти
   между шагами); проверить заново: у трека двойника по-прежнему нет данных (множество читается
   один раз на пачку, внутри транзакции), у него одна версия и один источник — иначе пару
   пропустить; `delete_track(двойник)` (каскад уносит версию, источник и отметку скана; артистов и
   альбом, оставшихся без треков, уберёт `prune_catalog` в `mark`); затем
   `write(db, &[ScannedFile { file: найденный файл двойника, known: Some(пропавший с новым ID
   трека), tags, readable: true }], now)` — та же запись «новое место прежнего источника», что у
   перенесённого файла в Р1.2. После пачки — `progress(ScanProgress { phase: Writing, done: total,
   total })` (стоп-флаг; `false` — остановиться: сделанное остаётся, `mark` не вызывается, как у
   остановки основной записи).
7. Сведённые пропавшие снимаются с `diff.missing`/`diff.gone` (иначе `mark` скроет их заново);
   в итоге скана `moved` растёт на число пар, `missing` убывает на число сведённых из `diff.missing`.

Параметры этапа лучше собрать одной структурой (контекст скана: база, читатель, тома, снимок
`known`, итог обхода, файлы, время): функция с девятью аргументами не пройдёт clippy
(`too_many_arguments`).

Оборванный посреди скан: каждая пара — одна транзакция, остальные достроит следующий скан.
Цепочка «этап 1 отдал файл треку без данных → этап 2 отдал его же треку с данными» невозможна:
этап 1 раздаёт сначала пропавших с данными, и любой файл, подходящий такому треку, ему и
достаётся.

### №19 — запись не верит ID, снятому в начале скана

1. `scan::update` (`scan/mod.rs`) берёт трек по **версии**: `db.track_of_version(known.version)?`,
   запасной — `known.track`; обновляет этот трек и его версию. ID версии и источника
   перепривязка не меняет, ID трека — меняет.
2. `moved::relocate` в том же заходе в базу, где читает паспорта, сверяет пропавших с
   `known_local_files()` по ID источника и берёт оттуда свежие `KnownFile` (пропавших, чьего
   источника в базе уже нет, пропускает); пары строятся по свежим ID.

### Порядок работы

1. Новый API: `Pairing`/`pair_up`, `tracks_with_user_data`, `track_of_version` — зеленеют `r9c_new_api`,
   `r9c_user_data_set`. 2. №19 (`update` по версии, свежие ID в `relocate`) — `r9c_stale_ids`.
3. Этап 1 (`pair` на `pair_up`, данные первыми) — `r9c_best_pair`, прежние `r1_2_*` без правок.
4. Этап 2 (`twin.rs`) — `r9c_across_scans`, `r9c_copy_then_delete`. 5. ADR 0007, замер, проверки.

Публичные `ScannedFile`, `write(db, files, now)` и `ScanReport` **не меняются**: у `ScannedFile`
семь построителей вне `scan/` (тесты, `ffi/src/api/test_api.rs`, примеры).

## Инварианты

- Данные пользователя не теряются и не переезжают: трек, у которого они есть, из каталога не
  уходит; ID трека и источника, дата добавления остаются у трека-владельца данных; журнал скан
  не пишет. Уходит только трек **без** данных (проверено внутри транзакции).
- Играющее не пропадает: файл двойника в каталоге остаётся — под ID владельца данных. Трек, у
  которого есть данные, и трек с несколькими версиями или источниками двойником не бывает.
- «Не увидел» — не «нет» (Р1.15): пропавший, чей том скан не обходил, двойнику ничего не отдаёт;
  файл, который скан не увидел, двойником не бывает; недочитанный файл не двойник и не забирает
  трек (страж Р1.2 `a_file_whose_tags_do_not_read_does_not_take_a_gone_track`).
- Копия рядом с живым оригиналом по-прежнему новый трек (страж Р1.2).
- Повторный скан после сведения ничего не меняет (`moved`, `missing`, `added`, `changed` = 0).
- Тихий скан (ничего не пропало и не изменилось) не делает лишних заходов в базу: столько же,
  сколько в каталоге без пропавших (тест со счётчиком заходов).
- Оборванный скан (остановка, сбой) оставляет каталог согласованным: пара либо сведена целиком,
  либо не тронута.
- Формат базы и журнала не меняется: новых колонок и миграций нет.
