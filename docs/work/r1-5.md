## Цель

Сбой копии или миграции на данных пользователя больше не запирает ядро:
порча — карантин; миграция не прошла на данных — файл целым в сторону,
новая база, пользовательское из журнала; сбой среды — ошибка без потерь,
следующий запуск повторит; копия не снялась — миграции идут без неё. Одно
обновление — одна законченная копия.

## Контекст

- Целиком: `core/library/src/db/migrations/runner.rs`, `db/backup.rs`,
  `db/integrity.rs`. Диапазоны: `db/connection.rs:1–145`, `db/mod.rs:45–58`
  (`Opened`, `Recovery`), `core/ffi/src/session.rs:50–101` (как `recovery`
  становится `database_recovered`, а `catch_up` пересобирает проекцию — у
  новой базы нет `JournalMark`), образец теста — `session.rs:267`
  (`a_corrupted_database_is_recovered_without_loss`).
- SQLite 3.53.2 (`libsqlite3-sys` 0.38.2), проверено по `sqlite3.c`:
  `VACUUM INTO` в непустой файл не пишет и при ошибке цель **не удаляет**
  (`end_of_vacuum`). Оборванная копия остаётся на диске — отсюда временное
  имя. Цель сначала подключается (`ATTACH`), размер проверяется потом: в
  чужую базу — «output file already exists» (`SQLITE_ERROR`), в мусор —
  `SQLITE_NOTADB` ещё на `ATTACH`, а это `is_corruption`.
- Текст ошибки SQLite несёт полный путь: на старом коде T4 падает с
  `unable to open database: C:\…\plinth.db.bak-…-v1`.

## Решение

| Где | Ошибка | Сейчас | Станет |
|---|---|---|---|
| копия | порча (`is_corruption`) | `Backup(CoreError)` → отказ на каждом запуске | карантин `.corrupt-<мс>`, база заново (б) |
| копия | любая другая (место, путь, ввод-вывод) | отказ | `log::warn!` — код, не текст ошибки; `.bak.tmp` удалён, миграции без копии (а) |
| ротация копий | `read_dir`/`remove_file` | отказ, хотя копия снята | `log::warn!`, не ошибка |
| миграция | порча | карантин | без изменений |
| миграция | среда (`is_environmental`) | отказ | отказ, файлы не тронуты — следующий запуск повторит |
| миграция | прочее, база была до открытия | отказ навсегда | файл с `-wal`/`-shm` → `<база>.migration-failed-<мс>`, база заново (в) |
| миграция | прочее, база создана этим открытием (и в `replace`) | отказ | отказ, второго откладывания нет |
| база новее кода | — | отказ | без изменений (ADR 0011) |

1. **Одна копия на открытие** — перед первой ожидающей миграцией базы,
   бывшей до открытия (`current > 0`), имя `-v<версия при открытии>`.
   Промежуточные версии выводятся из неё тем же кодом; `KEEP = 3` теперь
   значит «три обновления» (г). Копия пишется во временный
   `<база>.bak.tmp` (застарелый удаляется **до**), затем переименовывается в
   `<база>.bak-<мс:013>-v<from>`; при ошибке `.bak.tmp` удаляется. Так
   оборванная копия — ни при ошибке, ни при убитом процессе — не считается
   копией и не вытесняет законченные. Застарелый `.bak.tmp` не удалился
   (кроме `NotFound`) — `BackupError::Io`, `VACUUM INTO` не запускается: в
   мусорный файл он упал бы с `SQLITE_NOTADB`, и здоровую базу отложили бы
   как испорченную.
2. **Сбой копии:** порча — `MigrationError::Backup(e)` без миграций, дальше
   карантин (б); иное — предупреждение в лог, миграции идут (а). В лог —
   шаг и код (`sqlite_error_code()`/`extended_code`, у `Io` — `ErrorKind`),
   не текст ошибки: в нём полный путь (§17.3).
3. **Провал миграции:** порча — карантин, как сейчас; среда — ошибка, файл
   не тронут (новая база упёрлась бы в то же место, а отложенный файл держал
   бы его); иначе на базе, бывшей до открытия, — файл в сторону и база
   заново (в), на новой — ошибка. Это и есть «откат на бэкап» §17.4:
   транзакция вернула файл к версии до упавшего шага, он лежит целым;
   состояние до обновления — в `.bak-…`. Отвергнуто: вернуть `.bak` на место
   (та же миграция упадёт снова); откладывать при любой ошибке (нехватка
   места выбросила бы здоровую базу); новый флаг в `StartupReport` (FFI и
   Kotlin; сообщения «библиотека восстановлена» достаточно, причина — в логе).

```rust
// db/backup.rs — backups() и KEEP прежние
#[derive(Debug)]
pub(crate) enum BackupError { Sqlite(rusqlite::Error), Io(String) } // Io — без путей
pub(crate) fn backup(conn: &Connection, db: &Path, from: i32) -> Result<PathBuf, BackupError>;

// db/migrations/runner.rs — сигнатура migrate прежняя
pub(crate) enum MigrationError {
    Newer { found: i32, known: i32 },
    /// `existed` — база была до этого открытия (`current > 0` в начале migrate).
    Failed { version: i32, name: &'static str, error: rusqlite::Error, existed: bool },
    /// Только порча: иные сбои копии из migrate не выходят.
    Backup(rusqlite::Error),
    Sqlite(rusqlite::Error),
}

// db/integrity.rs
/// Сбой среды, а не данных — повтор может пройти: DiskFull, OutOfMemory,
/// SystemIoFailure, DatabaseBusy, DatabaseLocked, ReadOnly, PermissionDenied,
/// CannotOpen, FileLockingProtocolFailed, OperationInterrupted.
pub(crate) fn is_environmental(error: &rusqlite::Error) -> bool;
/// `<имя>.<label>-<мс>` вместе с `-wal`/`-shm`; label — "corrupt" или "migration-failed". Не удаляет.
pub(crate) fn quarantine(path: &Path, label: &str) -> Result<PathBuf, CoreError>;

// db/connection.rs, приватное. Разбор Failed: порча → Corrupt; existed && !среда → Unmigratable; иначе Other.
enum Failure { Corrupt(String), Unmigratable(String), Other(CoreError) }
fn replace(path: &Path, label: &str, reason: String) -> Result<Opened, CoreError>;
```

Причина для `Unmigratable` — прежний текст `migration {version} ({name})
failed: {error}`. Публичный API (`Opened`, `Recovery`, `StartupReport`) и FFI
не меняются; меняются доки: «испорчена **или миграция на ней не прошла**».

## Инварианты

- Журнал не трогается. После любой замены базы пользовательское возвращает
  журнал (`catch_up`), каталог — скан.
- Файлы базы не удаляются: откладываются целиком, переименованием, с
  `-wal`/`-shm`. Удаляются только `.bak.tmp` и копии сверх `KEEP`.
- Отложенный после провала миграции файл — состояние до упавшего шага:
  прежний `user_version`, данные на месте.
- Ошибкой открытия из-за копий и миграций кончаются только: база новее кода,
  сбой среды, провал миграции на базе, созданной этим открытием.
- За открытие — не больше одного откладывания; следующее открытие после
  восстановления обычное: `recovery: None`, новых файлов нет.
- `backups()` видит только законченные копии; за открытие — не больше одной.
- `m000*.rs` и эталоны `tests/fixtures/db/*` не меняются. В логах нет полных
  путей (§17.3).

## Риски, принятые сознательно

- Ошибочная миграция, проскочившая CI, теперь обходится каждому пересборкой
  и пересканом, а не отказом запуска. Сторож — эталоны
  (`every_released_database_opens_and_keeps_its_data` требует
  `recovery.is_none()`). «Выгрузить лог» из §17.4 — UI, вместе с Р1.4.
- `.corrupt-*` и `.migration-failed-*` — полные копии, их никто не чистит
  (кандидат в Р1.11). Миграция, падающая и на новой базе, оставляет по
  маленькому отложенному файлу на запуск — такую ловит CI.
- Устойчивый сбой среды отказывает на каждом запуске — цена того, что здоровую
  базу не выбрасываем; что видит человек, решает Р1.4.
- Копия пишется с `synchronous` исходной базы, переименование без `fsync`:
  после отключения питания законченная по имени копия может оказаться
  неполной. Время `VACUUM INTO` на большой базе не мерено (Р1.12).
