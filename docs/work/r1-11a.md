## Цель

1. Онлайн-поиск отменяется, когда запрос сменили или ушли с экрана, и укладывается в
   общий срок 15 с: «сеть есть, но молчит» даёт секции «нет сети» через ~15 с (на `main` —

   провайдера и не доигрывает повторы.
2. Треки элемента Internet Archive идут по диску и номеру; без номера и при равных
   номерах — в естественном порядке имён («2» раньше «10»).

## Решение

### Принцип

Срок и отмена — свойства **одного вызова**, а не клиента: поэтому они едут в запросе
(`SearchQuery`) до `HttpClient`, а не живут в нём. Отмена — флаг, который ядро
проверяет **между** шагами; прервать уже идущий `HttpURLConnection` ядро не может, поэтому
запрос получает не больше, чем осталось от срока, а Kotlin-корутина поиска не ждёт ядро.
Срок и отмена — только поиск; `resolve`, `stream`, `known`, `add` не меняются.

### А. Ядро: срок и отмена (`plinth-providers`)

**А1. `http/limits.rs` (новый), реэкспорт из `http/mod.rs`:**

```rust
/// Отмена: клоны видят одно состояние; отменённое не возвращается.
#[derive(Debug, Clone, Default)]
pub struct Cancel(/* Arc<AtomicBool> */);
impl Cancel {
    pub fn new() -> Self;
    pub fn cancel(&self);
    pub fn is_cancelled(&self) -> bool;
}

/// Срок и отмена одного вызова. `Limits::default()` == `Limits::none()`: ни срока, ни отмены.
#[derive(Debug, Clone, Default)]
pub struct Limits { /* deadline: Option<Instant>, cancel: Cancel */ }
impl Limits {
    pub fn none() -> Self;
    /// Срок — от «сейчас». Не поместился в `Instant` (`Duration::MAX`) — срока нет.
    pub fn within(budget: Duration) -> Self;
    /// Отмена — та же, что у `cancel`: `cancel.cancel()` виден через эти `Limits`.
    pub fn cancelled_by(self, cancel: &Cancel) -> Self;
    pub fn is_cancelled(&self) -> bool;
    /// Сколько осталось; `None` — срока нет, `Some(0)` — вышел.
    pub fn left(&self) -> Option<Duration>;
}
```

**А2. `HttpClient::get_within`** (`http/client.rs`); `get(url, headers)` теперь —
`get_within(url, headers, &Limits::none())`, поведение `get` не меняется:

```rust
pub fn get_within(&self, url: &str, headers: &[(String, String)], limits: &Limits)
    -> Result<Vec<u8>, CoreError>;
```

Правила, по порядку (тексты ошибок — ровно такие, без адреса и запроса):

1. Перед **каждой** попыткой: отменено — `Err(Network("cancelled"))`, транспорт не зовётся.
2. Перед первой попыткой срок вышел (`left() == Some(0)`) — `Err(Network("timed out"))`,
   транспорт не зовётся.
3. `HttpRequest.timeout` попытки = `min(policy.timeout, left())`; срока нет — `policy.timeout`,
   как сейчас.
4. После неудачной попытки, которую повторили бы (нет ответа, 429, 5xx): отменено —
   `Err(Network("cancelled"))` сразу, без паузы.
5. Перед паузой: срока нет — пауза берётся; иначе если `left() <= пауза` — **не** паузить и не
   повторять: вернуть последнюю настоящую ошибку (`last`), а не выдуманную.
6. После паузы: отменено — `Err(Network("cancelled"))`.
7. Ответ, который пришёл (2xx, 404/410, прочие статусы), возвращается как раньше, даже если
   отменили в это время: на этом уровне ответ не выбрасывается.

**А3. `SearchQuery`** (`model/search_result.rs`): поле `limits: Limits` (по умолчанию `none`),

```rust
pub fn within(self, limits: Limits) -> Self;
pub fn limits(&self) -> &Limits;
```

`#[derive(PartialEq, Eq)]` с `SearchQuery` снять (никто не сравнивает запросы, токен
отмены сравнивать нечем).

**А4. `InternetArchive::search`** передаёт `query.limits()` в `HttpClient::get_within`
(приватный `get` получает параметр `limits`); `resolve` — `&Limits::none()`.

**А5. `Registry::search`** — правила, по порядку для каждого провайдера:

1. Пустой запрос — пусто (как раньше).
2. Отменено — остановиться, вернуть уже собранное.
3. Провайдер `Down` — секция `Unavailable("provider … is down")`, как раньше (срока не тратит).
4. Срок вышел (`left() == Some(0)`) — секция `Err(Network("timed out"))`; провайдера **не**
   спрашивают и **не** пишут в здоровье: его вины нет.
5. Спросили; после ответа отменено — ответ (и успех, и отказ) **выбросить**: ни в здоровье,
   ни в результат; остановиться.
6. Иначе `observe` как раньше. Срок, истёкший посреди запроса провайдера, — обычный отказ
   (`Network` без `http `): считается как «нет соединения» (бан 15 с после трёх).

### Б. Граница с Kotlin (`plinth-ffi`, `online_api.rs`)

```rust
/// Срок одного онлайн-поиска вместе с повторами и паузами: одна попытка политики (15 с,
/// `config.json`). Решение планировщика; `advancedsearch` IA на пробе 2026-10-15 отвечал за
/// 1,9–5,9 с, поэтому 10 с резали бы медленный, но живой ответ.
pub(crate) const SEARCH_BUDGET: Duration = Duration::from_secs(15);

/// Отмена онлайн-поиска. Kotlin заводит по одной на вызов и зовёт `cancel`, когда ответ не нужен.
#[derive(uniffi::Object, Default)]
pub struct OnlineCancel { /* cancel: Cancel */ }
#[uniffi::export]
impl OnlineCancel {
    #[uniffi::constructor] pub fn new() -> Arc<Self>;
    pub fn cancel(&self);
}

// в #[uniffi::export] impl Core — третий параметр:
pub fn online_search(&self, query: String, limit: u32, cancel: Arc<OnlineCancel>)
    -> Result<Vec<OnlineSearch>, CoreError>;   // = online_search_within(…, &cancel, SEARCH_BUDGET)

// в обычном (не exported) impl Core — для тестов с коротким сроком:
pub(crate) fn online_search_within(&self, query: String, limit: u32, cancel: &OnlineCancel,
    budget: Duration) -> Result<Vec<OnlineSearch>, CoreError>;
```

Ответ на отменённый поиск — то, что собрано до отмены, обычно пустой список (не беда
провайдера, не ошибка): его уже никто не ждёт. Выключенные источники и пустой запрос —
пусто, как раньше. `panic::guard` остаётся.

Старые тесты в `online_api.rs` (модуль `tests`): все пять вызовов `online_search(..)` (в
`search_gives_a_section_per_provider` — два, ещё в трёх тестах — по одному) получают
третий параметр `OnlineCancel::new()`; а в `kotlin_gets_the_policy_headers_and_timeout`
(623–644) строка `assert_eq!(requests[0].timeout_ms, 15_000)` становится
`assert!((14_000..=15_000).contains(&requests[0].timeout_ms))` — первая попытка поиска теперь
получает остаток срока (чуть меньше 15 с), а не ровно 15 с политики. Других изменений старых тестов нет.

### В. Kotlin

1. **`ffi/CoreOnline.kt`**: класс-обёртка и новый параметр, остальное в файле не трогать.

   ```kotlin
   /** Отмена одного вызова [CoreOnline.search]: зови [cancel], когда ответ уже не нужен. */
   class OnlineCancel {
       internal val rust = RustOnlineCancel()   // io.github.puflik.plinth.ffi.generated.OnlineCancel
       fun cancel() = rust.cancel()
   }
   fun search(query: String, limit: Int, cancel: OnlineCancel = OnlineCancel()): List<OnlineSection>
   ```

   Объект не закрывать вручную: `cancel()` может прийти после конца вызова, а закрытый
   объект UniFFI бросает `IllegalStateException`; хватит очистки по сборке мусора.

2. **`online/CoreOnlineRepository.search`** — вызов ядра живёт **вне** корутины поиска:
   `withContext(io)` и `coroutineScope` не возвращаются, пока блокирующий вызов не вернулся,
   а `runInterruptible` не помогает (ни JNI, ни сокет на `interrupt` не отзываются). Форма:

   - поле `private val calls = CoroutineScope(SupervisorJob() + io)`;
   - `val cancel = OnlineCancel()`; `val call = calls.async { quietly(TAG, "search") { core.online.search(query, SEARCH_LIMIT, cancel) } }`;
   - `try { call.await().orEmpty() } catch (c: CancellationException) { cancel.cancel(); throw c }`.

   `CancellationException` не глотать; `quietly` уже ловит только `CoreFailure`.
   `attempt` остальным методам остаётся.

3. **`online/HttpUrlTransport.kt`**: `NetRequest.timeout` — срок на запрос **целиком**
   (соединение + заголовки + тело). Ядро просит ровно остаток своего срока, а таймаут чтения
   `HttpURLConnection` сбрасывается с каждым куском: сочащийся по байту ответ держал бы запрос
   и поток IO сколько захочет сервер. Выход за срок — `NetAnswer.NoAnswer("SocketTimeoutException")`
   (то же имя, что у таймаута чтения). Как — на усмотрение исполнителя; достаточно проверять
   срок между чтениями тела и не позволять `readTimeout` превысить остаток; обрыв соединения
   по таймеру допустим, но не нужен. Остальное (`Response`, `TooLarge`, имя исключения без
   адреса) не меняется.

4. **Не меняются**: `SearchViewModel` (отмена доходит до него как отмена корутины:
   `flatMapLatest` — новый запрос, `WhileSubscribed(5_000)` — уход с экрана; пять секунд
   нужны повороту экрана), `OnlineRepository` (интерфейс), `FakeOnlineRepository`.

### Г. Порядок треков элемента IA (`internet_archive/mapping.rs`, `values.rs`)

**Г1. Диск трека** — по имени якоря (`anchor`: имя исходного файла с папками), по порядку:

1. Имя файла (после последнего `/`) содержит маркер etree `d<N>t<M>`: `d` или `D`, перед
   которой **нет буквы** ASCII (начало имени, цифра, знак — можно); 1–2 цифры диска; `t`/`T`;
   1–3 цифры трека; за ними не цифра. Берётся первое такое место; диск — `N`.
   Диск: `gd77-05-08d1t01.flac` → 1; `show.2006.D2T1.flac` → 2; `set_d4t10.flac` → 4;
   `show-d3t001.flac` → 3. Не диск: `Odd1t3.flac` (перед `d` буква), `d100t1` (три цифры
   диска), `d1t1234` (четыре цифры трека).
2. Иначе — компонент пути (папка, не файл), слева направо, первый подходящий: `cd`, `disc`
   или `disk` (без учёта регистра), любое число разделителей из ` ` `_` `.` `-`, 1–2 цифры, за
   ними конец компонента или не цифра. Диск: `CD1`, `cd 2`, `Disc_03`, `Disk-4`,
   `CD 2 - Live`, `Disc 10`. Не диск: `Discography`, `CD`, `Disc A`, `CD 2007 Remaster`,
   `Bonus CD 2`.
3. Иначе диска нет. Диск 0 — не диск (как трек «0» — не номер).

`RemoteTrack.disc` = найденный диск.

**Г2. Порядок.** Ключ: `(диска нет, диск, номера нет, номер)`, дальше — естественный порядок
имени якоря. То есть: треки с диском первыми, по возрастанию диска, без диска — после; внутри
диска пронумерованные по номеру, безномерные — после них; равные ключи — по имени.
Порядок не зависит от порядка файлов в ответе провайдера.

**Г3. Естественный порядок имён** `natural_cmp(a, b)`:

- имя режется на куски: подряд цифры ASCII — кусок-число, остальное подряд — кусок-текст;
- куски сравниваются попарно слева направо: число с числом — по значению (отбросить ведущие
  нули, сравнить длину, потом посимвольно — без переполнения); текст с текстом — после
  `to_lowercase()` у обоих; число с текстом — число раньше;
- первое неравенство решает; если один набор — начало другого, короткий раньше;
- равные полностью (разница в регистре или нулях: `B`/`b`, `02`/`2`) — по байтам исходных
  строк: порядок полный и повторяемый.

`["10 Finale","3 Song","1 Intro","11 Bonus","2 Song"]` → `1 Intro, 2 Song, 3 Song, 10 Finale,
11 Bonus`; `track_1, track_2, track_02b, track_10`; `a1, a2, A10, B, b`.

**Г4.** Остальное не меняется: ID трека и вариантов, состав и порядок вариантов, якоря,
`FFI`/Kotlin (в `OnlineTrackInfo` поля диска нет — см. «Замечено»). Тест
`tracks_go_by_number_then_by_name` (`mapping.rs:184`) остаётся как есть и проходит.

### Отвергнуто

- **`CoreError::Cancelled`**: новый вариант проходит через FFI, `CoreFailure`, `CoreProblem`
  (ADR 0010) ради сигнала, который никто не показывает. Реестр узнаёт отмену по флагу.
- **Поток на попытку в ядре** (вернуться сразу, бросив поток в транспорте): ядро начнёт
  порождать потоки и звать колбэк Kotlin с чужого потока; зависший поток всё равно живёт до
  таймаута сети. Выигрыш — тот же, что у `async` в Kotlin, цена выше.
- **Обрыв соединения по отмене** (`disconnect()` по идентификатору вызова): вызову нужно имя,
  транспорту — таблица вызовов. Запрос и так не живёт дольше остатка срока.
- **Срок в `config.json` провайдера**: общий срок поиска — политика приложения, не данные IA;
  когда провайдеров станет несколько, делить его будет реестр.
- **Поле `disc` в метаданных IA**: в 116 просмотренных элементах его нет — поддержка была бы
  мёртвым кодом. Появится — отдельная правка.
- **«Номера повторяются — значит, по именам»**: портит альбом с одним случайным повтором;
  диск надёжнее видно по имени и папке.
- **Урезать `WhileSubscribed(5_000)`**: поворот экрана не должен терять поиск.
- **Срок для `resolve`/`stream`**: вне задачи (см. «Замечено»).

## Инварианты

- Без срока и отмены всё как раньше: `HttpClient::get`, `resolve`, `stream`, `known`, `add`.
- Отменённый поиск: ни записи в здоровье, ни секции, ни нового запроса к сети после отмены;
  Kotlin-корутина поиска возвращается сразу, не дожидаясь ядра.
- Три отменённых поиска подряд не отправляют провайдера в `Down`.
- Ни один запрос к сети не получает таймаут больше остатка срока; повторы и паузы не выходят
  за срок поиска. Транспорт не держит запрос дольше его `timeout` (с запасом на один блок
  чтения).
- Ошибки `cancelled` и `timed out` не содержат ни адреса, ни запроса.
- Порядок треков детерминирован и не зависит от порядка файлов в ответе; ID и варианты треков
  те же; записанные ответы IA (`tests/internet_archive.rs`) дают те же треки в том же порядке.
- Каталог, журнал и «Любимое» не затрагиваются.

## Риски, принятые сознательно

- **Отменённый вызов доживает.** Корутина возвращается сразу, но блокирующий вызов ядра
  живёт, пока идущий запрос не кончится (не дольше остатка срока, ≤ 15 с). Печатающий человек
  оставляет по одному такому потоку IO на каждую паузу набора ≥ 300 мс; у `Dispatchers.IO` их 64.
- **Три медленных поиска подряд** (каждый на всём сроке) дают провайдеру 15 с отдыха
  («нет соединения», Р1.8) — секция показывает «Internet Archive не отвечает» вместо
  нового ожидания.
- **15 с** — выбор планировщика: ровно одна попытка политики; повторы остаются, пока есть
  остаток. `advancedsearch` IA на пробе 2026-10-15 (8 запросов с ПК) отвечал за 1,9–5,9 с, с
  телефона по мобильной сети медленнее, так что 10 с резали бы живой ответ. Число одно
  (`SEARCH_BUDGET`); поменять — одна строка и один тест.
- **Диск по имени** — эвристика: непохожее на `d1t01`/`CD1` диском не считается, и порядок
  идёт по номерам, как раньше.

## Замечено, не в этой задаче

- Альбом (`resolve`) тоже без срока и отмены: `core.online.album` в `withContext(io)` из
  `OnlineAlbumViewModel` — тот же класс, что находка 10 (остальное онлайн: 13, 14, 28–33). `Limits`
  и `get_within` для него готовы.
- Экран альбома не показывает диск: в `OnlineTrackInfo` нет поля `disc`. У многодисковых
  концертов с нумерацией на диск номера повторяются (1, 2, 3, 1, 2, 3).
- У секции с бедой нет кнопки «повторить» (находка 9, UI).
