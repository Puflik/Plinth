## 3. Что пришлось сделать и что увидели

1. **Rhino не нужен на нынешнем пути.** Для клиента `VISIONOS` экстрактор делает восемь запросов
   (`visitor_id` ×3, `reel_item_watch`, `player` ×2, `sw.js`, `next`) и не скачивает JS-плеер;
   `n` и подпись не разбираются. «Прогрев Rhino» в первом потоке — не слагаемое; Rhino загрузится,
   если экстрактор вернётся к клиенту с шифром (день, когда `VISIONOS` накроют). Поэтому зависимость
   Rhino (jar 1,2 МиБ; правило R8 держит его целиком) платится заранее за путь, который сегодня не
   используется. Чтобы убедиться, что под R8 этот путь работает, в раннер добавлен сценарий `rhino`
   (вызывает `YoutubeJavaScriptPlayerManager.getSignatureTimestamp`, `getUrlWithThrottlingParameterDeobfuscated`,
   `deobfuscateSignature` — реальный `base.js` и настоящий Rhino).
2. **Медленный первый запрос потока.** Запрос `pos=0, len=-1` (без `Range`-заголовка, `DefaultHttpDataSource`
   отправляет `Range: bytes=0-`) читается ≈ 10–16 КиБ/с: 32 КиБ за 5 с, 98 КиБ за 10 с, 196 КиБ за 20 с,
   при нужных 20 КиБ/с для Opus 160. Игра на старте подвисает (`BUFFERING`, за 20 с реального
   времени сыграно 9,4 с) — одинаково для Opus 251, AAC 140, с `User-Agent` клиента и «Plinth». Запросы
   с других позиций (после перемотки: `pos = 2046865`, `5350986`, `3698334`) идут ≈ 200 КиБ/с, то есть
   скорость сети не мала. Причина не установлена (темп YouTube на запросах с нуля? первое соединение?).
   Для этого написан сценарий `probe` (разные `Range`, `range=` в адресе, без `Range`, второй раз);
   не запущен. От его результата зависит, нужен ли Ю3б свой `DataSource` (куски `range=`, как в NewPipe).
3. **IPv6 на эмуляторе.** Один раз ожидание соединения с `googlevideo.com` по IPv6 вышло по таймауту
   (8 с, `fec0::` без маршрута), и возобновление после четвёртой перемотки заняло 11,1 с (остальные —
   1,2–2,4 с). Видимо, артефакт эмулятора, но у `HttpURLConnection` нет быстрого переключения на IPv4,
   так что в сетях со сломанным IPv6 то же будет на телефоне — проверять в Ю6.
4. **Gradle и R8.** `settings.gradle.kts`: репозиторий JitPack с `content { includeGroup("com.github.TeamNewPipe") }`
   (группа покрывает и `nanojson` с хешем коммита); `gradle/libs.versions.toml`: `newpipeExtractor = "v0.26.5"`;
   `app/build.gradle.kts`: `applicationIdSuffix = ".spike"` (в `defaultConfig`: release → `….plinth.spike`,
   debug → `….plinth.spike.debug`), release подписан отладочным ключом (иначе не ставится на эмулятор),
   `implementation(libs.newpipe.extractor)`. Правила R8 — копия `app/proguard-rules.pro` NewPipe без
   `-dontobfuscate` и без правил ExoPlayer/OkHttp/kotlinx.serialization: `timeago.patterns`, весь `org.mozilla.javascript`
   (`-keep ... { *; }`, как у NewPipe), `ClassFileWriter`, `javax.script`, `jdk.dynalink` + `-dontwarn`,
   поля `GeneratedMessageLite`. Сужать правило Rhino не пробовали.
5. **`Downloader`** (`SpikeDownloader`, ≈ 120 строк на `HttpURLConnection`): GET и POST; заголовки запроса
   из экстрактора, `User-Agent` по умолчанию — Firefox, но `User-Agent` из запроса его заменяет;
   `Accept-Encoding: gzip` выставляется всегда (чужие значения затираются: `br` разобрать нечем), ответ
   разжимается вручную по `Content-Encoding`; `HEAD` без тела; 429 → `ReCaptchaException`; в журнал
   идут метод, хост и путь (без query), статус, размер, время. Куки согласия сами не понадобились.
6. **`User-Agent` для потока.** Экстрактор отдаёт его отдельно: `YoutubeParsingHelper.getVisionOsUserAgent(Localization)`
   (`com.google.visionos.youtube/1.02(RealityDevice14,1; U; CPU visionOS 25_6_0 like Mac OS X; GB)`),
   а по адресу тип клиента узнаётся функциями `isVisionOsStreamingUrl` / `isIosStreamingUrl` /
   `isAndroidStreamingUrl`. В прогоне сервер принял и «Plinth»; полагаться на это не стоит — Ю3б должен
   ставить `User-Agent` клиента, который выдал ссылку.
7. **Java API выше minSdk 26** (статический разбор constant pool по `api-versions.xml` из SDK; скрипт не
   в репозитории). Экстрактор: `List.of`/`Map.of`/`Set.of`, `Objects.requireNonNullElse` (API 30),
   `String.isBlank`, `URLDecoder.decode`/`URLEncoder.encode` с `Charset`, `Optional.or`/`stream`,
   `Collectors.toUnmodifiableList` (API 33). Rhino 1.8.1: `Math.multiplyHigh`, `BigInteger.intValueExact`
   (API 31), `java.beans` (нет на Android — закрыто `-dontwarn`). `jsoup`, `protobuf-javalite`, `nanojson` —
   чисто. Часть вызовов D8 заменяет своими «backports» при `minSdk 26`; что осталось, **не проверено** —
   нужно либо смотреть `dexdump` итогового APK, либо гонять эмулятор API 26 (в этом спайке по заданию
   только API 36).

## 4. Риски для Ю3б–Ю3г (пока предварительные)

- **Старт потока.** Если причина п. 3.2 — запрос с нуля, нужен свой `DataSource` (куски `range=` в адресе,
  как у NewPipe `YoutubeHttpDataSource`), иначе первые секунды каждого трека подвисают. Работа Ю3б растёт.
- **Трафик и время одного `resolve`.** `StreamExtractor.fetchPage()` тянет `next` — 330–420 КБ JSON после
  разжатия на каждый поток (в сети меньше за счёт gzip; не измерено), всего 8 запросов, 1,9–2,5 с.
  Не нужно для воспроизведения; обойти можно только своим запросом `player` — вне `YoutubeSource`
  из Ю1. Для мобильной сети и «Радио» (много потоков подряд) это существенно.
- **Срок жизни ссылки** — 6 ч; `OnlineResolver` раскрывает адрес перед каждой загрузкой, так что
  хватает; кэшировать адрес дольше 6 ч нельзя.
- **Дорога к Rhino.** См. п. 3.1: платим за путь, который не исполняется; под R8 не проверен.
- **IPv6/соединения.** `DefaultHttpDataSource` — `HttpURLConnection` без быстрого переключения на IPv4;
  запасной вариант — `OkHttpDataSource` (отдельная зависимость).
- **Java API ниже 33** — п. 3.7.
- **Срок жизни экстрактора.** Тег `v0.26.5` — 2026-08-15; через два месяца клиент `VISIONOS` всё ещё играет.

(`emulator-5554`, без окна, запускал этот спайк). Чужой `io.github.puflik.plinth` на нём не трогали.
Ворктри для базы: `C:\claude\Plinth-base` (отсоединённый `main` 7a834d2, `local.properties` скопирован,
сборка не запускалась; путь той же длины, что у `Plinth-yu3a`, — чтобы строки с путями в Rust-ядре не
давали шума в размере). Удалить в конце: `git worktree remove C:/claude/Plinth-base`.

Дальше, по порядку:

1. Собрать и поставить APK с новыми сценариями. PowerShell, `JAVA_HOME = C:\Program Files\Android\openjdk\jdk-21.0.8`,
   в `C:\claude\Plinth-yu3a`: `.\gradlew.bat assembleGithubRelease --console=plain` (повторная сборка быстрая,
   Rust уже собран); `adb -s emulator-5554 install -r app\build\outputs\apk\github\release\app-github-release.apk`.
2. Запуск: `adb -s emulator-5554 shell am start -W -n io.github.puflik.plinth.spike/io.github.puflik.plinth.spike.SpikeActivity --es scenario probe`
   (также `rhino`, `cold`, `all`); журнал — `adb -s emulator-5554 exec-out cat /sdcard/Android/data/io.github.puflik.plinth.spike/files/yu3a-report.txt`,

   эмуляторе не делать.
3. `probe` → решить, нужен ли свой `DataSource` (п. 3.2). Если нужен — набросать минимальный (кусок `range=`
   в адресе) и повторить минуту игры; цель — запись «что пришлось сделать».

## 6. Что не проверено

- Телефон автора и любое железо, кроме эмулятора x86_64 (не по заданию). Эмулятор быстрее телефона:
  цифры времени — нижняя граница.

- Поведение через 6 ч (истечение ссылки в середине трека), параллельная игра двух потоков.
