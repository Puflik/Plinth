## Цель

Четыре дефекта вокруг записи пользовательского и очереди:

1. **№18.** Диск полон, лайк или плейлист не записались — человек узнаёт об этом каждый раз

## Решение

Четыре независимые части; порядок реализации любой. Формат файлов очереди **не меняется**
(`VERSION = 2`).

### 1. №18 — «не сохранено» (сообщение), `core/`, `ffi/`, `ui/common/`

**Что есть.** Диск полон: `Store::persist` отказывает, `CoreJournal.write` бросает
`CoreFailure`, репозиторий глотает её в лог, сердце не меняется. `PlinthCore.call` кладёт
отказ в `CoreErrors.errors` как `AppError.CoreFailed(STORAGE)`, а `ErrorPresenter` говорит
о любом `STORAGE`/`INTERNAL` **один раз за процесс** одним флагом `toldCoreFailed`: если до
лайка уже была паника или отказ записи прослушивания, о лайке не скажут никогда, а после
первого сообщения — ни о чём.

**Что делаем.** Отказ **записи пользовательских данных** вида `STORAGE` получает своё
сообщение со своей памятью:

```kotlin
// core/AppError.kt — CoreFailed получает второе поле (значение по умолчанию — старые вызовы целы)
data class CoreFailed(
    val problem: CoreProblem,
    /** Отказал вызов, который записывал пользовательское (лайк, плейлист…): правка не на диске. */
    val saving: Boolean = false,
) : AppError

// core/ErrorPresenter.kt
sealed interface ErrorNotice {
    // …прежние…
    /** Правка (лайк, плейлист…) не записалась: вероятно, на устройстве кончилось место. */
    data object NotSaved : ErrorNotice
}

@Singleton
class ErrorPresenter @Inject constructor(private val clock: Clock) {   // kotlin.time.Clock
    constructor() : this(Clock.System)       // прежние тесты зовут ErrorPresenter()
    …
}

// ffi/CoreFailure.kt
internal companion object {
    fun of(exception: CoreException, saving: Boolean = false): CoreFailure   // …AppError.CoreFailed(problem, saving)
}

// ffi/PlinthCore.kt
internal fun <T> call(saving: Boolean = false, block: (Core) -> T): T   // CoreFailure.of(e, saving)

// ffi/CoreJournal.kt
private inline fun <T> write(saving: Boolean = true, crossinline block: (Core) -> T): T =
    core.call(saving) { block(it) }.also { core.userDataChanged() }
// recordPlay: write(saving = false) { … } — запись истории не пользовательская правка
```

Правила `ErrorPresenter.present`:

- `AppError.CoreFailed` с `saving == true` и `problem == STORAGE` → `ErrorNotice.NotSaved`,
  **кроме** случая, когда с прошлого такого сообщения прошло меньше `NOT_SAVED_EVERY = 10.seconds`
  (`companion`-константа). Прошлое — по `clock.now()`; часы пошли назад (`now < прошлого`) —
  сообщение говорится снова, а не молчит до «будущего». Повторные касания сердца на полном
  диске не копят очередь строк.
- Память `NOT_SAVED` и флаг `toldCoreFailed` **независимы**: после «не сохранено» паника
  по-прежнему получает своё «Что-то пошло не так» (один раз), и наоборот.
- Всё остальное — как прежде: `STORAGE`/`INTERNAL` без `saving` — один раз за процесс
  (`ErrorPresenterTest` и план 17.6 это держат); `INTERNAL` при записи — тоже общее
  «Что-то пошло не так» с кнопкой «Сохранить лог» (паника — ошибка, её надо отдать
  разработчику); `NETWORK`/`PARSE`/`UNAVAILABLE` при записи — тишина.

UI (`ui/common/ErrorNotices.kt`): `ErrorNotice.NotSaved` → строка `error_not_saved`,
`SnackbarDuration.Long` (там же, где `JournalStartedOver`); без кнопки. Строки (оба файла,
`values/strings.xml` и `values-ru/strings.xml`, рядом с `error_core_failed`):

```xml
<string name="error_not_saved">Couldn’t save the change. The device may be out of space.</string>      <!-- values -->
<string name="error_not_saved">Не удалось сохранить изменение. Возможно, на устройстве кончилось место.</string>  <!-- values-ru -->
```

`strings.xml` общие, но эта задача отдана им явно — других задач на них сейчас нет.

Поправить KDoc: `ErrorPresenter` (список правил — новый пункт), `CoreErrors`/`PlinthCore.call`
(что значит `saving`), `AppError.CoreFailed`.

### 2. №19 — порча `position.bin`, `queue/FileQueueStore.kt`

- `load()`: **очередь** читается как раньше (любая ошибка → `null`); **позиция** — отдельным
  `private fun readPosition(): Duration` вне того `try`: файла нет, он короче 8 байт или не
  читается (`IOException`, в том числе `EOFException`) — `Duration.ZERO`; прочитанное отрицательное —
  тоже `ZERO` (положительное, даже огромное, остаётся: проигрыватель сам зажмёт). Время
  последней игры — как сейчас (`readPlayedAt`).
- `write(file, durable, block)`: новый параметр `durable: Boolean = false`. При `true` перед
  закрытием и переименованием: `flush()`, затем `FileOutputStream.fd.sync()`. Включить **только
  для `queue.bin`** (меняется редко, раз за смену трека). `position.bin` пишется каждую секунду
  и `played.bin` раз в минуту — `sync` на каждую запись дорог для батареи и флеша, а порча
  теперь читается как «с начала трека». Это сам «потерянный файл» из находки (переименование
  легло на диск, данные нет) — для очереди закрывается `sync`, для позиции — допуском при чтении.

### 3. №27 — длинная строка и пара очередь/позиция, `queue/FileQueueStore.kt`

**Длинная строка.** `DataOutputStream.writeUTF` бросает `UTFDataFormatException`
(наследник `IOException`) на строке длиннее 65 535 байт **модифицированного UTF-8**
(`\u0000` — 2 байта, символ вне BMP — 6: суррогатная пара по 3). `write` ловит `IOException` —
запись очереди молча не удаётся, пока такая строка в очереди.

- Все **переменные** строки пишутся через `private fun DataOutputStream.writeText(text: String)`,
  то есть `writeUTF(text.fitUtf())`; постоянные метки (`"file"`, `"remote"`, `"tracks"`, `"none"`,
  `repeat.name`…) — как есть. Список: контексты `album` (название, исполнитель), `folder`,
  `search`, `artist`, `playlist` (id и имя); `writeNullable`; адреса источников
  (`uri`, `url`, `track`).
- `fitUtf` (top-level, `internal`, в том же файле или в `queue/Utf.kt`): возвращает **самый длинный
  префикс**, чей размер в модифицированном UTF-8 не больше `MAX_UTF = 65_535` байт; считает
  по символам: `'\u0001'..'\u007f'` — 1, `'\u0000'` и до `'\u07ff'` — 2, остальные (в том
  числе каждая половина суррогатной пары) — 3; если префикс кончается **первой** половиной пары
  (высокий суррогат без низкого), она отбрасывается. Строка, которая помещается, возвращается
  как есть (тот же объект).
- Класс `FileQueueStore` уже держит 17 функций из 19, разрешённых detekt
  (`allowedFunctionsPerClass`): в класс добавить только `readPosition` и `writeText`,
  всё остальное — вне класса.

**Пара очередь/позиция.** Находка: после неудачной записи очереди `QueueKeeper` продолжает
писать позицию **новой** очереди к **старому** `queue.bin`. Правило: на диске позиция либо
принадлежит очереди в `queue.bin`, либо отсутствует.

- `saveQueue`: записать `queue.bin` (`durable`). **Не вышло** → поле `queueStale = true`,
  позиция не трогается. **Вышло** → `queueStale = false`, записать позицию `0`; если и **она**
  не записалась — `positionFile.delete()` (нет файла = «с начала»; позиция прежней очереди
  у новой не остаётся).
- `savePosition`: при `queueStale` ничего не пишет (очередь на диске прежняя, позиция новой
  ей не принадлежит); иначе — как сейчас. `savePlayedAt` от очереди не зависит.
- `queueStale` — обычное поле: всё идёт под `exclusive`.

### 4. №26 — очередь 0.1.x, `queue/LegacyUriQueueStore.kt`, `queue/MediaStorePaths.kt`, `di/AudioModule.kt`

**Что есть.** 0.1.1 хранил в очереди `content://media/external/audio/media/<id>`; ядро 0.2
узнаёт файл по **пути** (`track_at` ищет по `local_uri`), поэтому у этих треков нет
истории, сердца и отметки «играет». Играют они по-прежнему.

**Что делаем.** Декоратор `QueueStore`, который при чтении переводит такие адреса в пути.
Файл на диске он не переписывает; запись очереди сохранит уже пути.

```kotlin
// queue/LegacyUriQueueStore.kt (новый файл)
/** Пути файлов по адресам MediaStore вида content://media/<том>/audio/media/<число>. */
fun interface MediaPaths {
    /**
     * Для каждого из [uris], чей файл нашёлся, — его путь; остальных в ответе нет. Не бросает
     * ничего, кроме отмены корутины: нет доступа к MediaStore — пустой ответ.
     */
    suspend fun pathsOf(uris: Set<String>): Map<String, String>
}

/** [QueueStore], который при чтении заменяет адреса MediaStore из очереди 0.1.x путями файлов. */
class LegacyUriQueueStore(
    private val store: QueueStore,
    private val paths: MediaPaths,
) : QueueStore

// queue/MediaStorePaths.kt (новый файл, Android)
class MediaStorePaths(
    private val resolver: ContentResolver,
    private val io: CoroutineDispatcher,
) : MediaPaths
```

`LegacyUriQueueStore.load()`:

1. `store.load()`; `null` → `null`, `paths` не зовётся.
2. Собрать **без повторов** адреса `AudioSource.LocalFile` с префиксом `content://media/` из трёх
   мест очереди: `contextItems`, `playingManual`, `upNext`. Пусто → вернуть прочитанное как есть,
   `paths` не зовётся.
3. **Один** вызов `paths.pathsOf(набор)`. Пустой ответ — вернуть как есть.
4. Каждый элемент с адресом из ответа — `item.copy(source = AudioSource.LocalFile(путь))`
   (остальные поля — название, исполнитель, альбом, длительность, владелец альбома — те же);
   адрес без находки или с пустым/пробельным путём остаётся как был. Порядок, `order`,
   `position`, `shuffle`, `repeat`, `context`, позиция в треке и время последней игры — без
   изменений.
5. `saveQueue`, `savePosition`, `savePlayedAt` — прямо в `store`.

`MediaStorePaths.pathsOf`: из набора берутся адреса формы `content://media/<том>/audio/media/<число>`
(том любой: `external`, `external_primary`…); остальные пропускаются. Если подходящих нет — пустой
ответ без запроса. Иначе **один** запрос ко всей коллекции
(`MediaStore.Audio.Media.EXTERNAL_CONTENT_URI`, колонки `_ID` и `DATA`, без отбора), в `withContext(io)`;
по ходу курсора берутся строки из набора нужных id, обход прерывается, когда нашлись все. Запрос на
каждый адрес не годится: очередь из тысяч треков держала бы восстановление секунды. `DATA`
объявлена устаревшей с API 29 (`@Suppress("DEPRECATION")` с причиной — как в `MediaStoreSource`
версии 0.1.1: `git show v0.1.1:app/src/main/kotlin/io/github/puflik/plinth/library/scan/MediaStoreSource.kt`);
путь из `DATA` — тот, по которому играет и сканирует приложение. `SecurityException` и ошибки провайдера
(`IllegalArgumentException`, `UnsupportedOperationException`) → `AppLog.w` и пустой ответ.

Проводка (`di/AudioModule.kt`, `provideQueueStore`):
`LegacyUriQueueStore(FileQueueStore(File(context.filesDir, "queue"), io), MediaStorePaths(context.contentResolver, io))`.
`QueueKeeper` и его тесты не меняются.

### Отвергнуто

**№18**
- Разовость снять для всех отказов ядра: паника на каждый вызов — шум; держит план 17.6 и
  `ErrorPresenterTest`.
- `replay` у `CoreErrors.errors`: после поворота экрана старые вести показались бы заново.
- Копить вести, пока приложение в фоне: решение ревью №16 (`ErrorNoticesTest`) — вернувшийся
  человек видит только то, что случилось при нём. Поэтому отказ записи прослушивания из
  `ListeningRecorder` в фоне по-прежнему только в логе; это сознательно.
- Разбирать текст ошибки ядра на «нет места»: `CoreException.Storage` одна на диск, базу и права;
  формулировка осторожная («возможно»), по виду и по тому, что вызов был записью, достаточно.
- Рисовать лайк по памяти ядра, пока запись не удалась: сердце показало бы то, чего нет на
  диске. Сердце, как и прежде, не меняется (`userDataChanged()` при отказе не зовётся).
- «Не сохранено» и для `recordPlay`: на полном диске сообщение шло бы после каждого трека.

**№19**
- `sync` на каждую позицию (раз в секунду) — дорого, и допуск при чтении закрывает то же.
- Контрольная сумма или поколение в `position.bin`: другой файл, другой формат; не стоит
  ради секунды позиции.

**№27**
- Длина-префикс вместо `writeUTF` (версия 3): два чтения, миграция и неясное «назад»; обрезка
  длиной строки в 64 КБ ничего не стоит — строк такого размера в очереди не бывает, она нужна
  только чтобы одна из них не останавливала сохранение.
- Не записывать элемент/контекст с длинной строкой: очередь обрезалась бы там, где её не просили.

**№26**
- Сбросить очередь 0.1.x при чтении: теряется живая очередь (автор в 2026-10 проверял апгрейд и
  ценил, что она цела) и однократные файлы «Открыть с…», у которых тоже адрес
  `content://media/…`.
- Переводить в `CoreUserDataRepository.trackAt`: история и сердце появились бы, но отметка
  «играет» в списках сравнивает адрес с `LibraryTrack.uri` и обложка берётся по тому же адресу — не
  выиграли бы; и конструктор репозитория, общий с контрактными тестами на эмуляторе, пришлось бы менять.
- Переводить в `QueueKeeper.start()`: конструктор и его тесты менять не нужно только у декоратора.
- Искать по тегам (название+исполнитель+длительность): нужен новый вызов ядра; догадка.
- Переписывать `queue.bin` после перевода: лишняя запись при каждом старте, а выгоды нет — пути
  и так лягут при первой смене очереди.

### Что остаётся (сознательно)

- Лайк, который не записался, остаётся в памяти ядра; следующая удачная запись положит его
  на диск вместе с собой, а до этого сердце его не показывает и после смерти процесса его нет
  (сообщение это и говорит).
- Свёрнутое приложение вести не копит (ревью №16): запись из `ListeningRecorder` в фоне — в лог.
- Окно между записью `queue.bin` и позиции `0`: убитый процесс оставит новую очередь с позицией
  прежней очереди. Окно в доли миллисекунды; закрыть можно поколением очереди в обоих файлах — не сейчас.
- Адрес `content://media/…`, который `MediaStore` уже не знает (база переиндексирована), остаётся
  как был: играет, но без истории и сердца.
- Формат пути из `DATA` и пути ядра — один и тот же `/storage/emulated/0/…` (см. «Риски»).

## Инварианты

1. Формат `queue.bin`/`position.bin`/`played.bin` тот же (`VERSION = 2`): что пишет новый код,
   читает прежний; что писал прежний (в том числе 0.1.1), читает новый.
2. `load()` не бросает исключений. Повреждённый `queue.bin` — по-прежнему «ничего не сохранено»;
   повреждённые `position.bin` и `played.bin` очередь не теряют.
3. Позиция на диске либо принадлежит очереди в `queue.bin`, либо файла позиции нет.
4. Никакая переменная строка не делает запись очереди невозможной; обрезается хвост строки,
   всё остальное цело; строки, что помещаются, не меняются ни на байт.
5. Перевод адресов 0.1.x идемпотентен и не пишет на диск: повторное чтение даёт то же;
   адрес без находки остаётся как был; `MediaPaths` не зовётся, если переводить нечего; один

## Риски, принятые сознательно

1. **Путь `DATA` и путь ядра могут различаться записью** (`/sdcard/…` против
   `/storage/emulated/0/…`; ядро получает пути от сканера, `DATA` — от `MediaStore`). Тогда
   `trackAt` останется `null`, как сегодня: хуже не станет. Сверить на телефоне автора при
   приёмке (одна строка в логе/отладчике: `trackAt(путь из очереди)`).
2. **Один запрос ко всей аудиоколлекции** на старте, но только если в очереди есть адреса
   `content://media/`: десятки миллисекунд на десятки тысяч строк; у обычного запуска стоимость — нуль.
3. **Обрезанный адрес** (>64 КБ) — другой адрес; таких адресов не бывает, а очередь должна
   сохраниться. Обрезанное имя плейлиста в заголовке очереди — безобидно.
4. **Интервал «не сохранено» по настенным часам**: сдвиг часов вперёд снимает гашение (говорим
   раньше), назад — тоже снимает (см. правило); хуже — лишнее сообщение, не потерянное.

## Замечено, не в этой задаче

- `CoreErrors.errors` без `replay`: сообщение, что пришло между перезапусками сбора
  (`repeatOnLifecycle` при повороте), теряется — и о записи, начатой касанием. Окно в миллисекунды.
- Запись, не попавшая на диск, остаётся в памяти ядра и всплывёт в сердце на следующем сигнале
  `userDataChanged` — после какой-нибудь другой записи; это безвредно, но сердце «догоняет».
- `PlaylistRepository.create` при отказе возвращает `null`; экраны, судя по коду, это молча
  проглатывают — теперь после этого будет «не сохранено», но сам диалог не проверялся.
