## Цель

Лайки, подписки и чёрный список держат «добавление побеждает параллельное удаление»
(ADR 0007) при любой истории установок, а не только при общей: защищённый тест Р1.6
`sets_stay_add_wins_a_like_removed_on_the_new_installation_returns` перестаёт падать в
1–3 % прогонов. Журналы прошлых версий читаются.

## Контекст

Множества лежат в плоских картах `yrs` (`likes`, `subscriptions`, `blocks`) под ключом
без установки: `<TrackId>`, `<ArtistId>`, `track:<id>` / `artist:<id>`. Две установки с
разной историей — новая и восстановленная копия старой — добавили один ключ порознь:
обе вставки без левого соседа, и `yrs` оставляет за ключом вставку с **большим** номером
клиента (проверено; номер — случайные 53 бита на каждое `Journal::open`). Если это та,
что потом снята, добавление из копии пропадает. Сломан и ADR 0007: «добавление побеждает»
держалось только при общей истории. В эталоне `registers-legacy` номер клиента лайка —
около 0,974 диапазона, поэтому защищённый тест падал в 1–3 % прогонов (на `main`
`45ea51f`: 2 из 200).

Р1.6 развела регистры: у каждой установки свой слот `ключ@<DeviceId>`, ключ без суффикса —
слот журнала до Р1.6. Вся машинерия в `doc.rs` уже есть; множества её не используют.

отсутствующего — `false`, операция в журнал и в базу не идёт.

## Решение

**Слот на установку — и у множеств.** Элемент множества с id `K` (ключ, каким он был) хранится
слотами: `K@<DeviceId>` — добавление этой установки — и `K` без суффикса — слот журнала до
Р1.6б (читается, новым кодом не пишется). Установка пишет только свой слот, поэтому
параллельных вставок одного ключа нет и `yrs` ничего не разводит по номеру клиента.

1. **Добавление** (`Like`, `Subscribe`, `Block`): у элемента уже есть слот — любой: свой,
   чужой, без суффикса; читаемый или нет — ничего не делает (`false`, как прежний `add`).
   Иначе пишет слот `K@<своя установка>` с той же записью, что и раньше. Слоты ищет проба
   ключей по суффиксам установок карты (`open` + `has_slot`), без прохода по карте на каждую
   операцию.
2. **Снятие** (`Unlike`, `Unsubscribe`, `Unblock`): стирает все слоты элемента, которые
   видит, читаемые и нет (`remove_slots`); `true`, если стёрт хоть один. Слот, которого
   снимавшая установка не видела, остаётся: параллельное добавление сильнее снятия.
3. **Чтение** (`state`): элемент есть, если у него есть читаемый слот. Списки — по id, как
   были. `since` у подписки и записи чёрного списка берётся из действующего слота — того
   же, что у регистров: с наибольшим `(meta.at, meta.device)`, при равенстве — по ключу
   (`newest`). Нечитаемый слот пропускается и считается в `unreadable` — каждый один раз,
   даже если у элемента есть читаемый (как у регистров).
4. **Без изменений:** `superseded` (ключ — `DeviceId`, только пополняется, снимать нечего:
   параллельные вставки теряют лишь копию записи, ключ остаётся); `plays`, `decisions`;
   запись `codec`, `OP_SCHEMA` (= 2), файлы `store`, `Op`, `JournalState`, FFI, Kotlin.

```rust
// core/sync/src/journal/doc.rs

// Slots: три новые карты; суффиксы собираются при первом обращении к карте в правке.
struct Slots {
    ratings: Option<Suffixes>,
    playlists: Option<Suffixes>,
    entries: Option<Suffixes>,
    settings: Option<Suffixes>,
    passports: Option<Suffixes>,
    likes: Option<Suffixes>,
    subscriptions: Option<Suffixes>,
    blocks: Option<Suffixes>,
}

/// Добавляет элемент множества `id` слотом установки `meta.device`; `false` — у элемента
/// уже есть слот: свой, чужой или журнала до Р1.6б, читаемый или нет.
fn add_member(
    register: Register<'_>,
    txn: &mut TransactionMut,
    id: &str,
    meta: &OpMeta,
    record: impl FnOnce() -> Vec<u8>,
) -> bool {
    if has_slot(register, txn, id) {
        return false;
    }
    put(register.map, txn, own_key(id, meta.device), record())
}

// write_one: Like (так же Subscribe и Block — со своими ключами и записями).
Op::Like { track } => {
    let found = open(&self.likes, &mut slots.likes, txn, meta.device);
    add_member(found, txn, &track.to_string(), meta, || encode(meta, |_| ()))
}
Op::Unlike { track } => {
    let found = open(&self.likes, &mut slots.likes, txn, meta.device);
    remove_slots(found, txn, &track.to_string())
}

// state: те же `registers`, что у остальных; id приходит без суффикса.
state.likes = registers(&self.likes, txn, &mut skip, |id, value| {
    let (meta, ()) = slot(value, |_| Ok(()))?;
    Ok((meta, id.parse()?))
});
state.subscriptions = registers(&self.subscriptions, txn, &mut skip, |id, value| {
    let artist = id.parse()?;
    let (meta, since) = slot(value, |r| r.since())?;
    Ok((meta, Subscription { artist, since }))
});
state.blocklist = registers(&self.blocks, txn, &mut skip, |id, value| {
    let target = block_target(id)?;
    let (meta, since) = slot(value, |r| r.since())?;
    Ok((meta, BlockEntry { target, since }))
});
```

Фрагменты — рабочий набросок: он собран и прогнан планировщиком, но имена внутренних
помощников любые, а поведение — по пунктам выше. `add` остаётся для `superseded`, `keyed` — для
`read_superseded`: мёртвого кода быть не должно (`clippy -D warnings`). Шапка `doc.rs` и
комментарий к `registers` описывают то, что делает код: множества теперь тоже слоты.

Отвергнуто:

- **Править результат слияния по времени.** Проигравшую вставку `yrs` стирает при
  интеграции — сравнивать не с чем (как в Р1.6).
- **Номер клиента `yrs` из времени.** Старый код пишет случайные 53-битные номера — новый
  должен их бить; решает время открытия сессии, а не записи (как в Р1.6).
- **Двойная запись: слот и ключ без суффикса — чтобы 0.2.x видел новые лайки.** Ключ без
  суффикса снова спорил бы по номеру клиента; снятие обязано стирать оба; объём вдвое. Для
  регистров так не делали.
- **Метки в значении записи (множество внутри значения).** Конкурирующую вставку `yrs`
  отбросит целиком вместе с метками.
- **Свой слот и при добавлении элемента, виденного по чужому слоту.** Журнал растёт, `false`
  у `write_one` пропадает, выигрыша нет: установка добавляет только то, чего не видит.
- **Короче суффикс, чтобы не раздувать ключи.** `DeviceId` — UUID v7: его первые байты — время
  создания, а не случайность; обрезка ради 20–30 байт на слот вернула бы возможность
  совпадения слотов двух установок, а с ней — прежний баг.

## Инварианты

- Сходимость: после полного обмена у всех реплик одно `JournalState`, в любом порядке
  обмена и при любых номерах клиентов `yrs`.
- Добавление побеждает снятие, которого оно не видело; снятие стирает все слоты, которые
  видело — свои, чужие, без суффикса, читаемые и нет, — и ничего больше.
- Журнал любой прошлой версии читается: ключи без суффикса — слоты (`journal_corpus.rs`, эталон
  `registers-legacy`, тесты `doc.rs` зелёные без правок).
- Повторное добавление имеющегося и снятие отсутствующего журнал не меняют (`false`,
  вектор состояния `yrs` на месте).
- Порядок списков `JournalState` — по id, как был; `unreadable` считает каждый нечитаемый слот.
- Старый код не ломается о новые ключи: ключ `K@<установка>` не разбирается как id —
  пропускается как нечитаемый, документ не портится. Данные, записанные новой версией, для
  него скрыты, но остаются в документе.
- Формат записи, `OP_SCHEMA`, `store`, FFI, Kotlin, схема БД не меняются.

## Риски, принятые сознательно

- **0.2.x не видит новые лайки, подписки и чёрный список** (см. вопрос 1 ниже): ключ со слотом
  для него нечитаем, а его «снять» не стирает слот новой версии. Как у регистров с Р1.6.
- **Журнал растёт:** ключ слота длиннее на 37 байт, и стёртые слоты в снимке остаются
  надгробиями с тем же длинным ключом (+38 байт на элемент: тысяча лайков — +38 КБ; вопрос 2).
- **Каждая правка, трогающая множество, один раз проходит по его ключам** (сбор суффиксов
  установок) — как у регистров; цена — в замере.
- **Добавление элемента, у которого есть чужой слот, ничего не пишет:** установка не
  «закрепляет» чужое добавление против параллельного снятия, которого не видела. В
  приложении это недостижимо: на лайкнутый трек приходит `Unlike`.
- **Один `DeviceId` у двух живых копий журнала** (каталог склонирован): слот общий, спорят как
  раньше; сходимость сохраняется.
- **`since` при нескольких слотах** — по времени записи, а не наименьший (вопрос 3).

## На что смотреть при чтении плана (Opus)

План меняет раскладку ключей в журнале — данные пользователя. После каждого вопроса — мой
ответ; поправки оформляются твоим коммитом тестов (в шапку идёт его хеш).

1. **0.2.x и новые ключи — главный вопрос.** Ключи `K@<установка>` в `likes`, `subscriptions`,
   `blocks` 0.2.x не разбирает (`TrackId` из `uuid@uuid` не парсится): пропускает и считает в
   `unreadable`. Лайки, поставленные на 0.3, для него скрыты; его «снять лайк» стирает только ключ
   без суффикса, поэтому слот 0.3 остаётся, и лайк «возвращается» на 0.3 (добавление побеждает
   снятие, которого оно не видело). Для регистров это принято в Р1.6; но лайки — самое частое
   действие человека. Окно риска: пока на его устройствах разные версии. Следа у `unreadable` нет —
   он идёт только в журнал (`rebuild.rs:69`), а `unreadable` в `mirror` считает файлы-копии,
   а не записи. **Выбрано как у регистров;** двойная запись отвергнута (причины в «Решении»).
   Если не принимаешь — нужен другой план, а не правка этого.
2. **Размер и цена.** Замер (`docs/work/r1-6b-bench.rs.txt`; release, ПК, 10 000 лайков; в скобках —
   `main`): *только журнал* — снимок 1 060 033 байт (680 033: +38 байт на лайк, +56 %); после снятия
   всех 810 154 (430 116: стёртый слот остаётся надгробием с тем же длинным ключом); все лайки одной
   правкой 29 мс (20); `state()` 6,9 мс (2,9); один лайк 1,3 мс (2,4 — шум). *Путь приложения*
   (`record_and_project_all`; в журнале ещё паспорта, которые заводит проекция) — снимок 2 814 789
   (2 434 749: +16 %), все лайки одной правкой 383 мс (346–388), один лайк 4,4 мс (3,1–3,7), снятие
   3,0 мс (2,0), `state()` 19 мс (16–19). Рост размера — только ключи: 38 байт на элемент множества;
   прослушивания, которых в журнале большинство (ADR: 85 % событий), не растут. Принимаю цену; нужен
   другой выбор — это про суффикс ключа, а не про код (укоротить его нельзя: «Решение», «Отвергнуто»).
3. **`since` у подписки и чёрного списка.** При нескольких слотах — слот с большим `at`, как
   у регистров; тест `the_newest_slot_decides_since` это фиксирует. `since` нигде не меняет
   логику: в базе `INSERT OR REPLACE` (последняя запись), Kotlin его не читает. Альтернатива —
   наименьший `since` («с каких пор»); не выбрана: «последняя запись действует» — одно правило на
   весь документ. Не согласен — поправь тест и `Решение`, п. 3.
4. **Добавление при существующем слоте — `false` и без записи.** Фиксируют
   `an_add_of_an_element_that_has_a_slot_changes_nothing` и
   `the_old_layout_is_read_erased_and_not_added_twice`; образец OR-set в
   `three_installations_follow_the_add_wins_model` на это опирается. Если захочешь «писать свой слот
   всегда» — три теста и один пункт «Решения» меняются.
5. **Защищённый тест Р1.6 остаётся как был** и после правки не мигает (замер ниже). Новых
   фикстур нет: журналы до правки — `registers-legacy` и корпус 0.2.0 (в обоих множества лежат
   ключами без суффикса); подписки и чёрный список в старой раскладке кладут сами тесты.
   Напоминание к выпуску 0.3, не к задаче: `journal_corpus.rs` велит завести эталон выпуска, когда
   поменялся формат журнала, — `make_journal_fixture -- 0.3.0` покажет и слоты регистров, и слоты
   множеств.
6. **Вне задачи:** падения `479462c` и `c6f5939` этой причиной не объясняются (запись
   `docs/decisions.md`, 2026-10-25). Если встретится ещё одно мигание — его назовёт аннотация CI.
