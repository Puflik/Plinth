## Цель

Оценка, имя плейлиста, позиция записи, настройка и паспорт — регистры: при
параллельных записях одного ключа действует запись с большим `OpMeta.at`, а не та,
чей случайный номер клиента `yrs` больше. «Восстановить» из копии старой установки
не затирает сделанное позже; журналы прошлых версий читаются.

## Контекст

Сейчас регистр — ключ `yrs`-карты (`ratings`, `playlists`, `entries`, `settings`,
`passports`), значение — запись `codec.rs`: заголовок (`OpMeta`: схема, установка,
`at`) и поля. Параллельные вставки одного ключа `yrs` разводит по номеру клиента
(**побеждает больший**, проверено) — он случайный 53-битный на каждое
`Journal::open`; проигравшее значение стирается при слиянии. `OpMeta.at` пишется,
но не читается. Итог (находка 6): старая 5★ из копии побеждает новую 3★ в
половине случаев.

Прочитать: `core/sync/src/journal/doc.rs` целиком (688 строк: `Roots::write`, `state`,
`read`/`put`/`add`, `delete_playlist`, тесты с `Replica`); `mod.rs:60–125`
(`Journal::open`, `record_all`); `op_meta.rs`; `codec.rs:1–60`; ADR 0007 «Документ»;
`tests/journal_corpus.rs` (корпус выпусков — читать, не менять).

## Решение

**Слот на установку.** Регистр с id `K` (`track`, `playlist`, `entry`, имя настройки)
хранится слотами: `K@<DeviceId>` — запись этой установки — и `K` без суффикса — слот
журнала до Р1.6 (читается, новым кодом не пишется). Установка пишет только свой слот,
поэтому параллельных записей одного ключа нет, `yrs` ничего не разводит и ни одно
значение не теряется.

1. **Чтение.** Действует читаемый слот с наибольшим `(meta.at, meta.device)`. Нечитаемые
   слоты пропускаются и считаются в `JournalState.unreadable`. Порядок списков в
   `JournalState` — по id, как был.
2. **Запись** (`Rate Some`, `RenamePlaylist`, `MoveEntry`, `Set`, `Describe`): в свой
   слот. `at` записи = `max(meta.at, 1 мс + наибольший at среди читаемых слотов
   этого id, которые запись видит)`: увиденное значение перекрывается всегда, как бы
   ни шли часы. В заголовок идёт этот `at`. Запись, равная действующему значению,
   не пишется (как раньше, `Option<OpMeta>` = `None`).
3. **Создание** (`CreatePlaylist`, `AddEntry`): как раньше, если слот с таким id уже
   есть — ничего не делает; иначе пишет свой слот. Достаточно проверить два ключа
   (`K`, `K@<своя установка>`), без прохода по карте: импорт плейлиста не должен
   стать квадратичным.
4. **Удаление** (`Rate None`, `RemoveEntry`, `DeletePlaylist` и записи удаляемого
   плейлиста): стирает все слоты id, которые видит; чего не видело, остаётся —
   параллельная запись сильнее удаления, как у множеств.
5. **Без изменений:** множества (`likes`, `subscriptions`, `blocks`) — «добавление
   побеждает» (ADR 0007), в том числе лайк, поставленный и снятый на новой установке,
   по-прежнему возвращается с копией (осознанно, страж-тест; решать иначе — автору);
   `plays`, `decisions`; запись `codec`, `OP_SCHEMA` (= 2), файлы `store`.
6. **Время снаружи:** `Journal::record_at` и `record_all_at` — как `record`/`record_all`,
   но с заданным временем; `record*` зовут их с `Timestamp::now()`. Остальной код
   (FFI, `projection.rs`) не меняется.

```rust
// core/sync/src/journal/mod.rs
pub fn record_at(&mut self, op: &Op, at: Timestamp) -> Result<Option<OpMeta>, CoreError>;
pub fn record_all_at(&mut self, ops: &[Op], at: Timestamp) -> Result<Option<OpMeta>, CoreError>;
// возвращаемый OpMeta — заголовок правки с переданным at, как у record_all
```

Внутренние помощники `doc.rs` (имена любые): слоты id; действующее значение
(`current`); `put_register`; `add_register`; `remove_register`; чтение `state` с
группировкой слотов по id (часть ключа до `@`). Прежние `read`/`put`/`add` для
регистров не нужны — удалить, если ими больше никто не пользуется (`clippy -D warnings`).

Отвергнуто:

- **Номер клиента из времени** при открытии журнала: старый код пишет случайные
  53-битные номера, новый должен их бить, то есть выходить за 2^53; решает время
  открытия сессии, а не записи — долгий процесс на другом устройстве проигрывает.
- **Править после слияния по `at`:** проигравшее значение `yrs` стирает при
  интеграции, сравнивать не с чем.
- **Журнал версий (массив):** растёт на каждую перестановку записи плейлиста.
- **Множества тоже по времени** (надгробия с `at`): другое решение ADR, не эта задача.

Не входит: сигналы Kotlin, миграция старых ключей (их читают, не переписывают),
правка `JournalState`, FFI.

## Инварианты

- Сходимость: после полного обмена у всех реплик одно `JournalState`, в любом
  порядке обмена и при любых номерах клиентов.
- Ни одно значение не теряется молча: параллельные записи разных установок живут в
  разных слотах; удаление стирает только увиденное.
- Побеждает большее `at`; при равенстве — большая `DeviceId` (`Ord`). Запись,
  видевшая значение, побеждает его даже при отставших часах.
- Журнал любой прошлой версии читается: ключи без суффикса — слоты с их `at`
  (`journal_corpus.rs` и эталон `registers-legacy` зелёные без правок).
- Повторная запись того же значения журнал не меняет.
- Старый код не ломается о новые ключи: пропускает их как нечитаемые, документ не
  портит.
- Формат записи, `OP_SCHEMA`, `store`, FFI, Kotlin, схема БД не меняются.

## Риски, принятые сознательно

- **Запись, равная действующему значению, не пишется:** повтор того же значения не
  «закрепляет» его против параллельной записи, которой установка не видела.
- **Параллельные записи (не видевшие друг друга) упорядочены по часам устройств.**
  Часы врут — выигрывает «будущее»; но видевшая его запись всё равно перекроет (+1 мс).
- **Один `DeviceId` у двух живых копий журнала** (каталог склонирован): слот общий,
  спорят как раньше; сходимость сохраняется.
- **Размер и скорость:** ключ регистра длиннее на 37 байт (≈ +2–3 % журнала); чтение
  и запись регистра — проход по ключам корня.
- **Старый код** новые ключи не видит: данные, записанные новой версией, для него
  скрыты, но в документе остаются.
- **Лайк** по-прежнему возвращается с копией (страж-тест).
- **v1.5:** паспорт, переписываемый по кругу двумя устройствами с разными тегами
  (Р1.7), остаётся; регистры теперь сохраняют оба значения — по ним можно будет
  спросить человека о параллельном переименовании (план §10).

- `doc.rs`, чтение: `registers` — из слотов одного id (ключ до `@`) действует
  читаемый с наибольшим `(meta.at, meta.device)`; при равенстве обоих — слот с
  большим ключом, чтобы выбор не зависел от порядка обхода карты (иначе
  сходимость держалась бы на хеше). Слоты сортируются по `(id, ключ)`, группы

  `K` и `K@<своя>`, без прохода), `remove_slots` (стирает все слоты id, которые
  видит, и читаемые, и нет: нечитаемый слот из будущей версии иначе воскресил бы

- `mod.rs`: `record_at`, `record_all_at`; `record` / `record_all` зовут их с
  `Timestamp::now()`; возвращается заголовок правки с переданным `at` (без
  подъёма). Импорт `Timestamp`.

**На что глянуть при ревью:**

- Тай-брейк по ключу в `newest` — моё добавление к «наибольший `(at, device)`»:
  слот до Р1.6 `K` и слот `K@D` той же установки с равным `at` иначе выбирались
  бы по порядку обхода хеш-карты.
- `MoveEntry` / `RenamePlaylist` / `Rate` читают слоты id проходом по ключам
  корня: на карте записей в 10 000 — микросекунды на ключ; `AddEntry` этого не
  делает. Индекса слотов не понадобилось (условие остановки не сработало).
- Старый код новые ключи не портит, но и не пропускает все: оценки,
  плейлисты, записи и паспорта он не разбирает (`key.parse()` падает — слот
  нечитаемый), а `settings` читает без разбора ключа, поэтому старый
  бинарь покажет настройку из слота `version_preference@<установка>` как ещё
  одну запись. Данные в документе целы; это поведение старого кода, а не нового.
  Проверено чтением старого `state`, не запуском старой сборки.
- Время сведено к `Timestamp + 1 мс` через `Add<Duration>` (насыщение при
