# Работа Opus и Sonnet

С 2026-10-04 (решение автора): **думает и решает Opus, кодит Sonnet.** Состав
с 2026-10-10 (автор): **Sonnet 5.5 max планирует** — файл задачи, ветка, тесты
до кода; **Sonnet 5.5 ultracode кодит** — одну задачу по файлу задачи в своей
ветке; **Opus 5.5 max** читает план задачи с данными пользователя до
исполнителя, ревьюит и сливает, а планирует сам в крайних случаях; граф
обновляет **Haiku 5.5 high**. Правила, которые нельзя нарушать, — в
`CLAUDE.md` («Работа Opus и Sonnet»); здесь — порядок, роли и строки, которыми
агентов зовут.

## Цикл задачи

1. **Планировщик: файл задачи.** `docs/work/<id>.md` по `TEMPLATE.md`. `<id>` —
   короткий, латиницей: `r1-5`, `r1-12`.
2. **Планировщик: ветка, ворктри, тесты.**
   ```text
   git worktree add C:\claude\Plinth-<id> -b work/<id> main
   Copy-Item C:\claude\Plinth\CLAUDE.md, C:\claude\Plinth\.claude, C:\claude\Plinth\local.properties C:\claude\Plinth-<id> -Recurse
   ```
   `CLAUDE.md`, `.claude/` (хуки) и `local.properties` (путь к Android SDK) в
   git не входят — без копии чат в ворктри останется без правил и хуков, а
   Gradle не найдёт SDK. Память проекта привязана к пути
   `C:\claude\Plinth` и в ворктри не подхватится: нужное из неё — ниже, в
   «Что исполнитель знает без памяти».
   В ворктри — тесты в **отдельных файлах** (Rust: `core/<крейт>/tests/<id>_*.rs`
   или модуль-файл `#[cfg(test)] mod <id>_tests;`; Kotlin: свой класс теста):
   исходник исполнитель править обязан, и тест внутри него не защитить.
   Планировщик сам убеждается, что тесты падают на текущем коде — утверждением,
   а не компиляцией; ошибка компиляции допустима только там, где задача вводит
   новый API, и тогда его сигнатура — в разделе «Решение». Первый коммит ветки:
   файл задачи + тесты; хеш — в шапку файла задачи; пуш ветки (CI гоняет
   `work/**`). Задача с данными пользователя (журнал, миграции, перепривязка,
   CRDT): до исполнителя план читает Opus и при нужде дописывает тесты своим
   коммитом — тогда в шапку идёт его хеш, с ним сверяются защищённые тесты.
3. **Sonnet: реализация.** Отдельный чат, строка из «Как звать агента». Коммиты
   и пуш — только в `work/<id>`; в конце — «Отчёт исполнителя» в файле задачи.
4. **Opus: ревью** (раздел «Ревью» ниже). Не прошло — замечания дописываются в
   файл задачи («Ревью, круг N»), тот же исполнитель продолжает.
5. **Opus: слияние.** Перебазирование `work/<id>` на `main`, перемотка `main`
   (история линейная, как была), пуш. Перебазирование меняет хеши — в файл
   задачи, `tasks.md` и `docs/decisions.md` идут хеши из `main`. Потом
   CHANGELOG, `tasks.md`, `docs/decisions.md`; удаление ветки (локально и в
   origin) и ворктри — сборки в ворктри весят гигабайты. `git worktree remove`
   спотыкается о длинные пути сборок Gradle («Filename too long»): регистрацию
   он снимает, а каталог добивает `cmd /c rd /s /q "\\?\C:\claude\Plinth-<id>"`.

## Что исполнитель знает без памяти

- **Gradle** — из PowerShell с `$env:JAVA_HOME = "C:\Program Files\Android\openjdk\jdk-21.0.8"`;
  JBR Android Studio по старому пути сломан, системная `java` — 1.8. Задачи —
  с вариантом: `testGithubDebugUnitTest`, `testFdroidDebugUnitTest`,
  `ktlintCheck`, `detekt`, `lintGithubDebug`. SDK Gradle берёт из
  `local.properties` (Opus копирует его в ворктри); нет файла —
  `$env:ANDROID_HOME = "C:\Users\User\AppData\Local\Android\Sdk"`.
- **Rust** — из `core/`: `cargo test`, `cargo clippy --workspace --all-targets -- -D warnings`,
  `cargo fmt --all -- --check` (на Windows шумит «Incorrect newline style» по
  чужим файлам — смотреть только настоящие `Diff in`).
- **Инструментальные тесты — только на эмуляторе** (`Medium_Phone_API_36.0`),
  `$env:ANDROID_SERIAL = "emulator-5554"` — в той же команде, что и Gradle: среда
  между вызовами не живёт, а телефон автора бывает подключён по USB. Без фильтра
  Gradle поставит тесты и на телефон поверх отладочной сборки автора и в конце
  удалит её с данными; да и HiOS замораживает процесс тестов.
- **Известное:** на Windows падают 7 тестов `DataStore*SettingsTest` (на 2026-10-28; раньше 4)
  (`IOException` в `FileStorage.kt:114`) — не из-за задачи; на Linux в CI проходят.
- **Коммиты:** текст файлом, `git commit -F <файл>`; без `Co-Authored-By` и
  «Generated with Claude Code». Теги — только по слову автора.

уровень, поэтому вывод ориентировочный):

- **Данные пользователя** (журнал, миграции, перепривязка, CRDT) — планирование
  и ревью на **max**: только он сверил поведение SQLite по исходнику и дал
  устойчивую к обрыву копию; цена — примерно вдвое дороже «экстры».
- **Остальное** (UI, мелкие правки, CI) — **экстра** (xhigh): почти тот же

- **«Ультракод»** для планирования не брать: самый дешёвый, но пропустил
  разницу «сбой среды / провал на данных» и не отметил, что решение меняет ADR.
- В промпте замера подставлять уровень: в замере `<уровень>` остался
  незаменённым, и чаты угадывали его сами.

**Какая модель планирует.** Автор (2026-10-08): если Sonnet max справится —
понижать планировщика, Opus — только в крайних случаях. Замер на Р1.2 (один
прогон, `docs/work/effort/r1-2-sonnet-max.md`): Sonnet max спланировал на

дешевле. Значит:

- планирование можно отдавать **Sonnet max**;
- ревью — Opus: в замере каждый план поймал то, что пропустил другой. Для
  данных пользователя дёшево и полезно, чтобы Opus прочёл план до исполнителя;
- чат замера открывать в каталоге песочницы, а не в `C:\claude\Plinth`: там
  хук `SessionStart` подмешивает сводку прошлой сессии, и замер перестаёт

Первый настоящий случай — Р1.7 (2026-10-10): план Sonnet max принят без правок

свой `ci.yml` запускает нужные цели и выводит их итог в аннотацию проверки
(`::warning::`), а её видно через `api.github.com` без прав администратора, в

annotation» кладёт имена упавших тестов и текст паники в аннотацию задания «Rust
core». Путь без входа: `actions/runs?head_sha=<коммит>` → `actions/runs/<run>/jobs`
→ `check-runs/<id задания>/annotations`. Так нашёлся нестабильный тест Р1.6 о
множествах (`docs/decisions.md`, 2026-10-25).

## Параллельно

Несколько Sonnet-ов — каждый в своей ветке и ворктри. Opus раздаёт задачи так,
чтобы списки «Менять» **не пересекались**; задача, которой нужен уже занятый
файл, ждёт слияния первой и ветвится от нового `main`. Общие файлы
(`CHANGELOG.md`, `tasks*.md`, `docs/decisions.md`, `Cargo.lock`,
`gradle/libs.versions.toml`, `strings.xml`) правит только Opus при слиянии,
если файл задачи не отдал их явно одной задаче. Больше двух-трёх сборок разом
машина не потянет: у каждого ворктри свои `core/target` и `app/build`.

## Как звать агента

Промпт — одна строка: роль и задача (автор, 2026-10-12: проще, чем копировать
длинные промпты). Остальное агент читает сам: правила — `CLAUDE.md` и раздел
своей роли ниже, задачу — `docs/work/<id>.md`. Что раньше уходило в промпт —
на что смотреть при чтении плана, оговорки для исполнителя, — планировщик
пишет в сам файл задачи.

С 2026-10-16 (автор: «ты ж сам можешь создавать новые подчаты — так почему
это не делаешь?») сессии агентов запускает **Opus сам** — `start_session` в
приложении, контекст `fresh`, в этой же папке (`use_worktree: false`: ворктри
агент заводит сам, по шагу 2). Планировщик — Sonnet 5.5, effort max;
исполнитель — Sonnet 5.5, effort max: «ultracode» параметром запуска не
задаётся. Строки ниже — первые сообщения этих сессий. Когда агент кончил ход,
весть приходит Opus от приложения — автору пересылать её не нужно; замечания
ревью Opus шлёт той же сессии исполнителя (`SendMessage`). Перед запуском —
проверка окна (`CLAUDE.md`, «Пятичасовое окно»); разом — не больше двух
сессий, со списками «Менять» без пересечений.

- Планировщику: `Plinth: ты планировщик задачи <id> (<Р… в tasks.md / находка ревью>), роль — docs/work/README.md, «Планировщик».`
- Opus, план задачи с данными пользователя: `План <id> готов — прочитай до исполнителя.`
- Исполнителю: `Plinth: ты исполнитель задачи <id>, роль — docs/work/README.md, «Исполнитель».`
- Исполнителю после ревью: `Ревью <id>, круг <N> — в файле задачи; продолжай.`
- Opus, ревью: `Исполнитель закончил <id> — проверяй.`

Отвечает агент так же одной строкой — «План <id> готов», «<id> готово», «<id>:
стоп, вопрос в отчёте». Подробности — только в файле задачи: их читает Opus, а
чат агента автор не читает (автор, 2026-10-12).

## Исполнитель (Sonnet)

Делаешь ровно файл задачи — решения в нём уже приняты. Рабочий каталог —
ворктри `C:\claude\Plinth-<id>` (ветка `work/<id>`); работай только там.
Прочитай `CLAUDE.md` (раздел «Работа Opus и Sonnet» обязателен), «Что
исполнитель знает без памяти» выше и `docs/work/<id>.md`. Код и тесты — в
стиле окружающего кода.

Порядок: прочитай указанное в «Контекст» → убедись, что защищённые тесты
падают → реализуй → прогони все «Проверки» → коммиты и пуш в `work/<id>`
(`git commit -F файл`, без подписи Claude) → заполни «Отчёт исполнителя»,
коммит, пуш. После ревью замечания — в «Ревью, круг N» того же файла.

Нельзя: менять, удалять или глушить защищённые тесты (`#[ignore]`, `@Ignore`,
`#[allow]`, `@Suppress`, ослабленные утверждения); трогать файлы вне списка
«Менять»; писать в `main`, сливать, перебазировать. Проверки упали — одна
попытка исправить; упали снова — стоп и отчёт. Сомневаешься в решении или
тесте — не додумывай: стоп и вопрос в отчёте.

## Ревью (Opus)

Ветка `work/<id>`, ворктри `C:\claude\Plinth-<id>`. Прочитай `docs/work/<id>.md`,
включая «Отчёт исполнителя».

Проверь по порядку: 1) защищённые тесты не тронуты — `git diff <коммит тестов>
origin/work/<id> -- <файлы тестов>` пуст; 2) нет новых `#[ignore]`/`@Ignore`/
`#[allow]`/`@Suppress` и ослабленных утверждений; 3) изменены только файлы из
«Менять»; 4) CI ветки зелёный (или прогони «Проверки» сам); 5) инварианты
держатся — прочитай дифф (`git diff main...origin/work/<id>`) как чужой код:
что сломается при обрыве, повторе, пустых и испорченных входах.

Не прошло — замечания в файл задачи («Ревью, круг N»), коммит в ветку, автору —
строка исполнителю на продолжение. Прошло — перебазируй на `main`, перемотай
`main`, пуш; CHANGELOG, `tasks.md`, `decisions.md`; удали ветку и ворктри.

## Планировщик (Sonnet max; Opus — в крайних случаях)

Решаешь и пишешь тесты, код реализации не пишешь. Прочитай `CLAUDE.md`, этот
файл, `TEMPLATE.md`; затем только то, что нужно задаче (большие документы —
диапазонами).

Сделай: файл `docs/work/<id>.md` по шаблону; ветку и ворктри (шаг 2); тесты в
отдельных файлах; убедись, что они падают на текущем коде; первый коммит
ветки, пуш. В `main` не коммить: `tasks.md` и другие общие файлы правит Opus.
Промптов не пиши: всё, что нужно читающему план и исполнителю, — в файле задачи. В конце — строка «План <id> готов» и, если задача с данными
пользователя, напоминание, что до исполнителя план читает Opus.
