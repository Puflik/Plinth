# Работа Opus и Sonnet

С 2026-10-04 (решение автора): **думает и решает Opus, кодит Sonnet.** Состав
с 2026-10-10 (автор): **Sonnet 5.5 max планирует** — файл задачи, ветка, тесты
до кода; **Sonnet 5.5 ultracode кодит** — одну задачу по файлу задачи в своей
ветке; **Opus 5.5 max** читает план задачи с данными пользователя до
исполнителя, ревьюит и сливает, а планирует сам в крайних случаях; граф
обновляет **Haiku 5.5 high**. Правила, которые нельзя нарушать, — в
`CLAUDE.md` («Работа Opus и Sonnet»); здесь — порядок и шаблоны промптов.

## Цикл задачи

1. **Планировщик: файл задачи.** `docs/work/<id>.md` по `TEMPLATE.md`. `<id>` —
   короткий, латиницей: `r1-5`, `r1-12`.
2. **Планировщик: ветка, ворктри, тесты.**
   ```text
   git worktree add C:\claude\Plinth-<id> -b work/<id> main
   Copy-Item C:\claude\Plinth\CLAUDE.md, C:\claude\Plinth\.claude, C:\claude\Plinth\local.properties C:\claude\Plinth-<id> -Recurse
   ```
   `CLAUDE.md`, `.claude/` (хуки) и `local.properties` (путь к Android SDK) в
   git не входят — без копии чат в ворктри останется без правил и хуков, а
   Gradle не найдёт SDK. Память проекта привязана к пути
   `C:\claude\Plinth` и в ворктри не подхватится: нужное из неё — ниже, в
   «Что исполнитель знает без памяти».
   В ворктри — тесты в **отдельных файлах** (Rust: `core/<крейт>/tests/<id>_*.rs`
   или модуль-файл `#[cfg(test)] mod <id>_tests;`; Kotlin: свой класс теста):
   исходник исполнитель править обязан, и тест внутри него не защитить.
   Планировщик сам убеждается, что тесты падают на текущем коде — утверждением,
   а не компиляцией; ошибка компиляции допустима только там, где задача вводит
   новый API, и тогда его сигнатура — в разделе «Решение». Первый коммит ветки:
   файл задачи + тесты; хеш — в шапку файла задачи; пуш ветки (CI гоняет
   `work/**`). Задача с данными пользователя (журнал, миграции, перепривязка,
   CRDT): до исполнителя план читает Opus и при нужде дописывает тесты своим
   коммитом — тогда в шапку идёт его хеш, с ним сверяются защищённые тесты.
3. **Sonnet: реализация.** Отдельный чат, промпт ниже. Коммиты и пуш — только
   в `work/<id>`; в конце — «Отчёт исполнителя» в файле задачи.
4. **Opus: ревью.** Промпт ниже. Не прошло — замечания дописываются в файл
   задачи («Ревью, круг N»), тот же исполнитель продолжает.
5. **Opus: слияние.** Перебазирование `work/<id>` на `main`, перемотка `main`
   (история линейная, как была), пуш. Перебазирование меняет хеши — в файл
   задачи, `tasks.md` и `docs/decisions.md` идут хеши из `main`. Потом
   CHANGELOG, `tasks.md`, `docs/decisions.md`; удаление ветки (локально и в
   origin) и ворктри — сборки в ворктри весят гигабайты. `git worktree remove`
   спотыкается о длинные пути сборок Gradle («Filename too long»): регистрацию
   он снимает, а каталог добивает `cmd /c rd /s /q "\\?\C:\claude\Plinth-<id>"`.

## Что исполнитель знает без памяти

- **Gradle** — из PowerShell с `$env:JAVA_HOME = "C:\Program Files\Android\openjdk\jdk-21.0.8"`;
  JBR Android Studio по старому пути сломан, системная `java` — 1.8. Задачи —
  с вариантом: `testGithubDebugUnitTest`, `testFdroidDebugUnitTest`,
  `ktlintCheck`, `detekt`, `lintGithubDebug`. SDK Gradle берёт из
  `local.properties` (Opus копирует его в ворктри); нет файла —
  `$env:ANDROID_HOME = "C:\Users\User\AppData\Local\Android\Sdk"`.
- **Rust** — из `core/`: `cargo test`, `cargo clippy --workspace --all-targets -- -D warnings`,
  `cargo fmt --all -- --check` (на Windows шумит «Incorrect newline style» по
  чужим файлам — смотреть только настоящие `Diff in`).
- **Известное:** на Windows падают 4 теста `DataStore*SettingsTest`
  (`IOException` в `FileStorage.kt:114`) — не из-за задачи; на Linux в CI проходят.
- **Коммиты:** текст файлом, `git commit -F <файл>`; без `Co-Authored-By` и
  «Generated with Claude Code». Теги — только по слову автора.

## Какой effort

По замеру 2026-10-04 (одна задача, Р1.5, планирование; по одному прогону на
уровень, поэтому вывод ориентировочный):

- **Данные пользователя** (журнал, миграции, перепривязка, CRDT) — планирование
  и ревью на **max**: только он сверил поведение SQLite по исходнику и дал
  устойчивую к обрыву копию; цена — примерно вдвое дороже «экстры».
- **Остальное** (UI, мелкие правки, CI) — **экстра** (xhigh): почти тот же
  план за половину цены.
- **«Ультракод»** для планирования не брать: самый дешёвый, но пропустил
  разницу «сбой среды / провал на данных» и не отметил, что решение меняет ADR.
- В промпте замера подставлять уровень: в замере `<уровень>` остался
  незаменённым, и чаты угадывали его сами.

**Какая модель планирует.** Автор (2026-10-08): если Sonnet max справится —
понижать планировщика, Opus — только в крайних случаях. Замер на Р1.2 (один
прогон, `docs/work/effort/r1-2-sonnet-max.md`): Sonnet max спланировал на
уровне Opus max — другое, но обоснованное решение, тесты проверены временной
реализацией, его страж нашёл дыру в плане Opus; токенов столько же, токен
дешевле. Значит:

- планирование можно отдавать **Sonnet max**;
- ревью — Opus: в замере каждый план поймал то, что пропустил другой. Для
  данных пользователя дёшево и полезно, чтобы Opus прочёл план до исполнителя;
- чат замера открывать в каталоге песочницы, а не в `C:\claude\Plinth`: там
  хук `SessionStart` подмешивает сводку прошлой сессии, и замер перестаёт
  быть слепым.

Первый настоящий случай — Р1.7 (2026-10-10): план Sonnet max принят без правок
решения; Opus, прочитав его, дописал один тест; ревью с первого круга. В тот же
день автор закрепил состав (в начале файла).

Р1.6 (2026-10-11): решение плана Sonnet max верное, но критерий скорости мерил не
тот путь. Opus прочёл план уже после исполнителя, и это стоило круга ревью: план

## Параллельно

Несколько Sonnet-ов — каждый в своей ветке и ворктри. Opus раздаёт задачи так,
чтобы списки «Менять» **не пересекались**; задача, которой нужен уже занятый
файл, ждёт слияния первой и ветвится от нового `main`. Общие файлы
(`CHANGELOG.md`, `tasks*.md`, `docs/decisions.md`, `Cargo.lock`,
`gradle/libs.versions.toml`, `strings.xml`) правит только Opus при слиянии,
если файл задачи не отдал их явно одной задаче. Больше двух-трёх сборок разом
машина не потянет: у каждого ворктри свои `core/target` и `app/build`.

## Промпт исполнителю (Sonnet)

```text
Plinth, задача <id>. Ты исполнитель: делаешь ровно файл задачи, решения в нём уже приняты.

Рабочий каталог — ворктри C:\claude\Plinth-<id> (ветка work/<id>); работай только там. Прочитай CLAUDE.md (раздел «Работа Opus и Sonnet» обязателен), docs/work/README.md (раздел «Что исполнитель знает без памяти») и docs/work/<id>.md. Код и тесты — в стиле окружающего кода.

Порядок: прочитай указанное в «Контекст» → убедись, что защищённые тесты падают → реализуй → прогони все «Проверки» → коммиты и пуш в work/<id> (git commit -F файл, без подписи Claude) → заполни «Отчёт исполнителя», коммит, пуш.

Нельзя: менять, удалять или глушить защищённые тесты (#[ignore], @Ignore, #[allow], @Suppress, ослабленные утверждения); трогать файлы вне списка «Менять»; писать в main, сливать, перебазировать. Проверки упали — одна попытка исправить; упали снова — стоп и отчёт. Сомневаешься в решении или тесте — не додумывай: стоп и вопрос в отчёте.
```

## Промпт ревью (Opus)

```text
Plinth, ревью задачи <id> (ветка work/<id>, ворктри C:\claude\Plinth-<id>). Прочитай CLAUDE.md и docs/work/<id>.md, включая «Отчёт исполнителя».

Проверь по порядку: 1) защищённые тесты не тронуты — git diff <коммит тестов> origin/work/<id> -- <файлы тестов> пуст; 2) нет новых #[ignore]/@Ignore/#[allow]/@Suppress и ослабленных утверждений; 3) изменены только файлы из «Менять»; 4) CI ветки зелёный (или прогони «Проверки» сам); 5) инварианты держатся — прочитай дифф (git diff main...origin/work/<id>) как чужой код: что сломается при обрыве, повторе, пустых и испорченных входах.

Не прошло — замечания в файл задачи («Ревью, круг N»), коммит в ветку, и промпт исполнителю на продолжение. Прошло — перебазируй на main, перемотай main, пуш; CHANGELOG, tasks.md, decisions.md; удали ветку и ворктри.
```

## Промпт планировщику (Sonnet max; Opus — в крайних случаях)

```text
Plinth, планирование задачи <id> (<ссылка: tasks.md / находка ревью>). Ты планировщик: решаешь и пишешь тесты, код реализации не пишешь.

Прочитай CLAUDE.md, docs/work/README.md, docs/work/TEMPLATE.md; затем только то, что нужно задаче (большие документы — диапазонами).

Сделай: файл docs/work/<id>.md по шаблону; ветку и ворктри (README, шаг 2); тесты в отдельных файлах; убедись, что они падают на текущем коде; первый коммит ветки, пуш. В конце — готовый промпт исполнителю (из README, с подставленными <id>) отдельным блоком кода.
```
