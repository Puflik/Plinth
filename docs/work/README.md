# Порядок работы над Plinth

С 2026-11-04 работа продолжается в Codex по просьбе автора. Разделение
сохранено: исследователь принимает решения и ревьюит, исполнители делают
ограниченные задачи. Модели и effort — [AGENT_ROLES.md](AGENT_ROLES.md),
точка продолжения — [CODEX.md](CODEX.md), шаблон — [TEMPLATE.md](TEMPLATE.md).
Прежний процесс и замеры Claude сохранены в [CLAUDE-WORKFLOW.md](CLAUDE-WORKFLOW.md).
Для Codex действуют этот файл и `AGENTS.md`; старые имена моделей не являются
командами запускать недоступную модель.

## Цикл задачи

1. **Исследователь (Astra)** уточняет проблему, инварианты и решение.
   Для пользовательских данных — `max`. Неопределённость в продукте выносится
   автору; ответ идёт в `docs/decisions.md`.
2. **Планировщик (Sol)** пишет `docs/work/<id>.md`, создаёт `work/<id>` и
   worktree `C:\claude\Plinth-<id>`. Для изменения поведения — отдельные файлы
   тестов, которые падают на исходной версии. Ошибка компиляции допустима только
   для нового API, чья сигнатура записана в решении. Для одной документации
   или настройки — проверка формата и согласованности вместо искусственного
   падающего теста; причина в задаче.
3. **Первый коммит ветки** — задача и тесты; хеш тестов в шапку. Рабочая ветка
   пушится для CI. Для журнала, CRDT, миграций и перепривязки **Astra max читает
   план до реализации**; дописанные им тесты меняют опорный хеш.
4. **Исполнитель (Sol, Terra или Luna)** читает задачу и её контекст,
   проверяет исходное падение, реализует разрешённые файлы, выполняет проверки,
   пишет отчёт и коммитит только в `work/<id>`.
5. **Независимое ревью (Astra)**: защищённые тесты не изменены относительно
   опорного хеша; нет игнорирования, подавления или ослабления утверждений;
   изменены только разрешённые файлы; CI зелёный; обрыв, повтор, повреждение и
   пустые входы не ломают инварианты. Для данных — `max`.
6. Замечания — в «Ревью, круг N» файла задачи. После падения проверки у
   исполнителя одна попытка исправить; второе падение подряд — стоп и отчёт.
   Это относится и к Luna/Terra. Сомнение в решении — вопрос в отчёте.
7. **Координатор** после ревью переносит задачу на актуальный main и сливает
   линейно, обычным fast-forward push. В общей документации — хеши из main.
   Затем CHANGELOG/tasks/decisions и уборка ветки/worktree. Опубликованную
   историю не переписывать без отдельного слова автора.

Защищённые тесты исполнитель не меняет ни при каком выборе модели.
Файлы вне «Менять», `AGENTS.md`, `CLAUDE.md`, `CHANGELOG.md`, `tasks*.md`,
`docs/decisions.md`, план и зависимости остаются координатору. Новый файл тоже
должен входить в список «Менять». Общие файлы явно назначает координатор;
не расширять разрешённый объём по собственной догадке.

## Worktree и контекст

Ветка задачи — `work/<id>`: CI запускается для `main`, `work/**` и PR.
Проверять существующие ветки/worktree перед созданием. Теперь `AGENTS.md`,
конфигурация моделей и роли Codex входят в Git; старые checkout могут их не
содержать. `local.properties`, локальные навыки и хуки автоматически не переносятся.
Скопировать нужное из основной папки, проверить доступность SDK и правил.
Каталоги сборок не копировать. Нужные факты из памяти писать в задачу.

Списки разрешённых файлов задач не пересекаются. Общие `strings.xml`,
lock-файлы и каталоги версий назначаются явно. По бюджету — один активный
подагент, перед каждым чтение лимитов; правила — `AGENT_ROLES.md`.
Промпт короткий: роль, id задачи и путь к ней. Подробности и промежуточные
находки остаются в файле; после завершения не оставлять фоновые сборки и ожидания.

## Проверки на этой машине

- Gradle из PowerShell: `$env:JAVA_HOME = 'C:\Program Files\Android\openjdk\jdk-21.0.8'`.
  Системная Java — 8; прежний путь JBR сломан. SDK — `local.properties` или
  `$env:ANDROID_HOME = 'C:\Users\User\AppData\Local\Android\Sdk'`.
- Задачи с flavor: `testGithubDebugUnitTest`, `testFdroidDebugUnitTest`,
  `ktlintCheck`, `detekt`, `lintGithubDebug`; набор выбирается по изменению.
- Rust из `core/`: `cargo test --workspace --locked`,
  `cargo clippy --workspace --all-targets --locked -- -D warnings`,
  `cargo fmt --all -- --check`. Каждый worktree имеет свой `core/target`.
  Локальный CRLF-шум проверять с `--config newline_style=Auto`; не применять
  массовое форматирование ради одной правки.
- Инструментальные тесты — на эмуляторе; `ANDROID_SERIAL` в том же вызове
  Gradle. Без него тесты могут поставить APK на телефон и удалить данные.
  Фильтр пакета надёжнее списка классов с запятыми.
- По состоянию на 2026-10-28 известны семь Windows-падений DataStore при
  зелёном Linux CI. Это повод сравнить с исходной версией, не заглушить тест.
- `Select-Object -First` обрывает поток сборки: вывод сохранять в лог и читать
  потом. Различать исполнение и `FROM-CACHE`/`UP-TO-DATE`; для свежего прогона
  указывать `--rerun` сразу после имени задачи.
- Телефон — личное устройство автора и источник интернета; перезагрузка
  только по его слову. Приёмка на телефоне не заменяется сборкой test APK.

## Git и ежедневная работа

Автор разрешил обычные коммиты и push проверенной работы. Перед коммитом —
`git diff --check`, проверки по объёму, просмотр точного списка файлов.
Текст коммита — файлом через `git commit -F`, без подписи ИИ.
При недоступном GitHub пуш ждёт прямой сети; локальный прокси автора не использовать.
Теги и всё, что публикует релиз, — только по явной команде автора.

Каждый день — непустой коммит с настоящей работой в main до 19:00 UTC
(00:00 +05:00). Задачи дробить на полезные завершённые части. Это правило
работы в активные сессии, а не обещание автономного запуска в отсутствие чата.
Обычно задним числом допускается только вчера. **Разовое исключение автора
2026-11-04: закрыть 2026-10-31 и 2026-11-01/02/03**; обе даты Git соответствуют
указанному дню. Фактическое решение и выполнение записываются 2026-11-04.
Более широкого постоянного разрешения это исключение не даёт.
