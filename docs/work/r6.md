## Цель

Лайк и «В плейлист…» достижимы без долгого нажатия: из меню ⋮ плеера (справа
сверху) и из видимой кнопки ⋮ на каждой строке трека, везде, где такие строки
есть. Долгое нажатие остаётся. Сердце у названия в развёрнутом плеере видно у
любого трека фонотеки.

## Решение

### Принцип

Строка трека одна — `TrackRow` (его зовут вкладки «Треки» и «Папки», альбом,
исполнитель, поиск, «Любимое» и «Недавнее», свой плейлист, альбом провайдера).
Кнопка ⋮ живёт в нём, поэтому есть везде сразу. Меню у кнопки и у долгого
нажатия — одно, один список пунктов. Очередь в плеере (`QueuePanel`) — не строка
трека фонотеки: у неё перетаскивание и свайп, а меню нет; вне задачи.

### 1. Строка трека — `TrackRow.kt`

- Справа в строке всегда: облако (если трек сетевой), длительность (если
  известна) и кнопка `IconButton` с иконкой `R.drawable.ic_more_vert` и
  `contentDescription = stringResource(R.string.library_more)` — строка уже есть,
  **новых строк в `strings.xml` не нужно**. Раньше при отсутствии облака и
  длительности справа не было ничего.
- Нажатие кнопки открывает то же `DropdownMenu`, что долгое нажатие, и **не**
  играет трек: касание кнопки не доходит до строки.
- Пункты и порядок не меняются: «Играть следующим», «Добавить в очередь»,
  «Заменить очередь», «В плейлист…», «Нравится» (у любимого — «Больше не
  нравится»). «В плейлист…» по-прежнему открывает выбор плейлиста самой строкой
  (`playlistPicker`) и наружу как `TrackAction` не уходит.
- Область касания кнопки — 48 dp: Material3 `IconButton` даёт её сам при рамке 40 dp (тест проверяет
  `assertTouchWidthIsEqualTo` и `assertTouchHeightIsEqualTo`, а не размер рамки).
- Желательно (тестом не проверяется): меню, открытое кнопкой, раскрывается у
  кнопки, а не у левого края строки.
- Строка своего плейлиста: кнопка стоит между текстом и ручкой перестановки;
  свайп вбок и перетаскивание работают как прежде.

### 2. Меню плеера — новый файл `ui/player/PlayerMenu.kt`

`PlayerMenu` выносится из `PlayerScreen.kt` (там он `private`) и меняется.
Сигнатура дословно:

```kotlin
@Composable
internal fun PlayerMenu(
    state: PlayerUiState,
    onLike: () -> Unit,
    onOpenAlbum: (Album) -> Unit,
    onOpenArtist: (String) -> Unit,
    playlistPicker: @Composable (onDismiss: () -> Unit) -> Unit,
)
```

Пункты по порядку:

1. «Нравится» / «Больше не нравится» (`track_like` / `track_unlike` по
   `state.liked`) — только если `state.liked != null`, то есть трек фонотеки
   (`PlayerUiState.liked`: `null` — трек не из фонотеки, сердца нет);
2. «В плейлист…» (`track_add_to_playlist`) — тоже только при `liked != null`;
3. «К альбому» (`player_go_album`) — если `state.album != null`;
4. «К исполнителю» (`player_go_artist`) — если `state.artist != null`.

Кнопка ⋮ доступна, пока в меню есть хоть один пункт:
`liked != null || album != null || artist != null`. Раньше она гасла без альбома
и исполнителя — поэтому «трёх точек» для лайка не было вовсе. Выбор пункта
закрывает меню; «В плейлист…» после этого показывает `playlistPicker` — до тех
пор, пока он не вызвал `onDismiss`.

`PlayerScreen` собирает меню так: `onLike = viewModel::onLike`, `playlistPicker =
{ dismiss -> PlaylistPicker(onAdd = { viewModel.onAddToPlaylist(it.id) },
onAddToNew = viewModel::onAddToNewPlaylist, onDismiss = dismiss) }`. Сердце рядом
с названием (`LikeButton`) остаётся: меню его дублирует, а не заменяет.

Ловушка: `PlayerScreen` уже на пределе `LongMethod` (60 строк в detekt) — сборка меню и выбора плейлиста
прямо в нём даёт 66 и роняет `detekt` (проверено на временной реализации). Вынеси сборку в отдельную
`@Composable` рядом с `PlayerMenu`, а не в `PlayerScreen`.

### 3. `PlayerViewModel` и `TrackActions`

`PlayerViewModel` получает третий параметр конструктора и два метода (дословно):

```kotlin
class PlayerViewModel @Inject constructor(
    private val playback: PlaybackController,
    private val userData: UserDataRepository,
    private val actions: TrackActions,
) : ViewModel()

fun onAddToPlaylist(playlist: PlaylistId)
fun onAddToNewPlaylist(name: String)
```

Оба берут играющий трек фонотеки (`track.value`: файл — по пути, сетевой — по
ID) и пишут через `TrackActions`; трека фонотеки нет (файл из SAF, ничего не
играет) — ничего не делают и плейлистов не заводят. `TrackActions` получает два
метода по ID (существующие по `LibraryTrack` зовут их):

```kotlin
fun addToPlaylist(track: TrackId, playlist: PlaylistId)
fun addToNewPlaylist(track: TrackId, name: String)   // имя — через playlistName(): пустое — ничего
```

Единственное место, где `PlayerViewModel` собирают руками, — `PlayerViewModelTest`;
его строку планировщик уже поправил в коммите тестов.

### 4. Сердце: проверить, не чинить вслепую

Сердце у названия есть, когда `PlayerViewModel` нашёл трек фонотеки по файлу
очереди (`userData.trackOf(source)`). Тесты закрепляют: у трека фонотеки, каким
бы путём он ни попал в очередь (из списка, сетевой, очередь восстановлена после
перезапуска), `PlayerUiState.liked != null`, а касание работает — на заглушках
(`PlayerHeartTest`) и на настоящем ядре на эмуляторе (`PlayerHeartRestoreTest`,
очередь пишет и читает настоящий `FileQueueStore`). Они зелёные, если дефекта нет.
Красный — это находка: исполнитель ищет причину и правит **только**
`PlayerViewModel` или `history/TrackOf.kt`; нужна правка шире — стоп и вопрос в
отчёте.

### Что не меняется

Долгое нажатие и его меню; `TrackAction` (перечисление, кроме комментария);
`strings.xml`; репозитории (`UserDataRepository`, `PlaylistRepository`); ядро
(`core/`); навигация; мини-плеер (кнопок в нём не добавляем); очередь.

### Отвергнуто

- **Кнопки в мини-плеере.** Автор просил меню плеера и строку трека; мини-плеер
  тесный, а сердце есть в развёрнутом.
- **Лайк свайпом по строке.** Свайп в плейлисте уже убирает строку.
- **Своё, укороченное меню у кнопки ⋮.** Автор: «с тем же меню, что и у долгого
  нажатия».
- **Запись в плейлист из `viewModelScope` плеера** (прямой `PlaylistRepository`
  в конструкторе). Плеер можно свернуть сразу после выбора, и запись пропала бы;
  `TrackActions` пишет в `@ApplicationScope`, как строка списка.
- **Отдельный Hilt-ViewModel для выбора плейлиста в плеере.** Класс ради двух вызовов.
- **«В плейлист» для альбома или папки целиком.** Автор писал и об этом
  («альбомом целиком — никак»), но в Р6 это не вошло — см. «Замечено».

## Инварианты

- Долгое нажатие по строке по-прежнему открывает меню; касание строки играет трек
  с этого места.
- Нажатие ⋮ не играет, не останавливает и не меняет очередь; наружу уходит тот
  же `TrackAction`, что и после долгого нажатия.
- Лайк и плейлисты пишутся только в журнал через `TrackActions` и
  `UserDataRepository` (ADR 0007), мимо — никогда. Файл не из фонотеки (SAF) в
  лайки и плейлисты не попадает, и меню плеера ему этого не предлагает.
- Тексты — из ресурсов, оба языка; новых строк нет, `RussianTranslationTest`
  зелёный без правок.
- Доступность: у кнопки есть `contentDescription`, область касания 48 dp.
- Свайп и перестановка строки плейлиста работают как прежде; кнопка не мешает ручке.

## Проверки

Из корня; `JAVA_HOME` — `docs/work/README.md`:

```text
.\gradlew.bat ktlintCheck detekt lintGithubDebug testGithubDebugUnitTest
```

Инструментальные тесты — только на эмуляторе (на телефоне автора HiOS замораживает
процесс тестов, `docs/decisions.md`, Р1.16). Эмулятор (`Medium_Phone_API_36.0`) —
в фоне, затем:

```text
C:\Users\User\AppData\Local\Android\Sdk\emulator\emulator.exe -avd Medium_Phone_API_36.0 -no-window -no-audio
$env:ANDROID_SERIAL = "emulator-5554"; .\gradlew.bat connectedGithubDebugAndroidTest "-Pandroid.testInstrumentationRunnerArguments.package=io.github.puflik.plinth.ui"
```

**`ANDROID_SERIAL` — в той же команде, что и Gradle** (Opus, при чтении плана):
переменные среды между вызовами оболочки не живут, а телефон автора бывает подключён
по USB. Без фильтра Gradle поставит тесты и на телефон — поверх отладочной сборки
автора `io.github.puflik.plinth.debug` — и в конце удалит её вместе с данными. Перед
прогоном `adb devices`: эмулятор в списке есть, иначе не запускать.

Пакет `ui` — все экранные тесты, в том числе четыре защищённых класса. Один класс —
`...arguments.class=<полное имя>`; несколько через запятую `gradlew.bat` не передаёт
(запятая в `.bat` разделяет аргументы), поэтому по одному за запуск.

Затем весь набор, тоже с фильтром в той же команде: `$env:ANDROID_SERIAL = "emulator-5554";
.\gradlew.bat connectedGithubDebugAndroidTest` (пакет `acceptance` по умолчанию исключён). Известное: на Windows падают 4 теста `DataStore*SettingsTest` —
не из-за задачи; в CI на Linux проходят.

- кнопка ⋮ в строке плейлиста не встаёт рядом с ручкой без перестройки свайпа;
- проверки упали дважды подряд (одна попытка исправить, потом стоп).

## Риски, принятые сознательно

1. **Тесное место справа.** Название, облако, длительность и ⋮ делят строку; у названия
   уже есть многоточие. На узком экране длительность может остаться без запаса —
   смотреть на эмуляторе.
2. **Сердце ищется один раз на трек очереди.** Если фонотека в этот момент файл не знала
   (ядро ещё не открыто, скан не успел его записать), сердце появится лишь со следующим
   треком. Тесты этого не закрепляют и не чинят; см. «Замечено».
3. **Меню у кнопки.** Позиция всплывающего меню не проверяется: тест видит только то,
   что оно открылось.
4. **Выбор плейлиста поверх плеера** — тот же диалог, что в списках; он берёт список
   плейлистов через свой `PlaylistPickerViewModel`, привязанный к экрану плеера.

## Замечено, не в этой задаче

- «В плейлист» для альбома, папки, результатов поиска целиком (автор: «альбомом целиком —
  никак»).
- Сердце в мини-плеере.
- Ленивый поиск трека: `PlayerViewModel.track` можно перечитывать, когда каталог
  меняется (`catalogChanges`), а не только при смене файла.
- У строк очереди в плеере нет меню (лайк, плейлист) — только свайп и перетаскивание.

**Замечание 1 (править).** «В плейлист…» в плеере добавляет трек, который играет в момент
выбора плейлиста, а не тот, для которого выбор открыли: `onAddToPlaylist` и
`onAddToNewPlaylist` читают `track.value` при нажатии в диалоге. Пока диалог открыт (а
«Новый плейлист» — это ещё и ввод имени), трек может смениться сам, и в плейлист молча
уйдёт следующий; в диалоге не видно, какой трек добавляется, так что подмену не заметить.

Нужно: трек фиксируется, когда открывается выбор плейлиста, и в плейлист идёт он, даже если
играет уже другой; выбор закрыли — фиксация снята. Как — на твоё усмотрение, но сигнатуры
`PlayerMenu` и одноаргументных `onAddToPlaylist` / `onAddToNewPlaylist` не менять: их зовут
защищённые тесты, и без открытого выбора они берут играющий трек, как сейчас. Например:
`PlayerViewModel.onPlaylistPickerShown()` / `onPlaylistPickerClosed()` из `DisposableEffect`
в `playlistPicker` у `PlayerScreenMenu`, а методы берут `pinned ?: track.value`. Лайк из меню
и сердце не трогать: подпись пункта меняется вместе с треком на экране.

Тест — новый, JVM, свой файл рядом с `PlayerViewModelPlaylistTest` (например,
`PlayerPlaylistTargetTest`): выбор открыт на треке A → очередь перешла на B → выбран
плейлист → в плейлисте A, а не B; то же для «Новый плейлист»; выбор закрыт без выбора →
следующее «В плейлист» берёт играющий трек. Защищённые тесты по-прежнему не менять.
