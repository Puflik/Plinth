# Ревью волны R1 «Исправления по ревью v0.2»

Ревью в чистом контексте (Р9): ревьюеры не видели, как писался код, и искали,
что сломается у живого человека. Диапазон — `v0.2.0..3e78ab6` (143 коммита;
`core` и `app/src/main` — 132 файла, +9,4 тыс. строк); код читался из отдельной

считалась закрытой, но исправление не держится или задело соседнее.

Пути — от корня репозитория, `APP/` = `app/src/main/kotlin/io/github/puflik/plinth/`;
номера строк — по `3e78ab6`.

**Серьёзность:** сломается — функция не работает или данные теряются в реальном
сценарии; неприятно — работает, но человек заметит и огорчится; мелочь — редкий
случай или косметика.

**Чем подтверждено:** «тест» — воспроизведено временным Rust-тестом (в копии,

## Сломается

### 1. Лайк и «В плейлист…» из плеера после перепривязки уходят на ID, которого нет в каталоге, и пропадают

- **Где:** `APP/ui/player/PlayerViewModel.kt:47-52,66-70,90-101`, `core/ffi/src/api/scan_api.rs:98-100`, `core/ffi/src/api/mirror_api.rs:99-106`, `core/sync/src/journal/relink.rs:54-56,100`, `core/library/src/db/repo/passport_repo.rs:42-53`, `core/sync/src/journal/passport.rs:27-39`
- **Сценарий:** переустановка, журнал вернул Auto Backup или «Восстановить» в мастере. Идёт первый скан; человек включает песню, появившуюся в списке. Скан кончается, перепривязка переводит трек на ID журнала. Песня ещё играет — человек жмёт ♥ в плеере: сердце закрашено, но в «Любимом» песни нет; переключился на другой трек и обратно — сердце пустое. То же с «В плейлист…» из меню плеера: «добавлено», а в плейлисте трека не видно. Следующие сканы и перепривязки лайк не возвращают. Та же картина, если «Восстановить» нажали в настройках, пока что-то играет.
- **Почему:** `PlayerViewModel.track` вычисляется `trackOf` (путь → ID) только при смене источника (`distinctUntilChanged` по `source`) и на `catalogChanges` не перечитывается, а `rekey_track` меняет ID трека под тем же путём. `onLike`/`onAddToPlaylist` пишут устаревший ID; `describe` паспорта для него не находит (`track_passport` → `None`), так что и перепривязка его не узнает. Списки библиотеки и история не страдают: списки перечитываются по `catalogChanged()` после скана (`APP/ffi/CoreScan.kt:49`), прослушивание узнаёт ID в момент записи (`APP/history/ListeningRecorder.kt:64-65`).
- **Как воспроизвести:** временный тест в `core/sync/tests/`: старая установка сыграла песню, копия; новая — `restore` копии, скан, ID по пути («плеер»), `relink` (как `relink_catalog`), `Like` по запомненному ID. Вывод: `player id 01a141af-8763-…; catalog id now 01a141af-874b-…; journal id 01a141af-874b-…` / `heart in the player: true; liked tab: []` / `after another scan + relink: liked tab []`.
- **Подтверждено:** тест (ядро) + код (Kotlin).

### 2. Перенос в два шага, посреди копирования или во время обхода: лайки, плейлисты и история остаются на скрытом старом треке (повтор v0.2 №2 — вариант)

- **Где:** `core/library/src/scan/moved.rs:35-40,77-85` (кандидаты — только новые файлы этого скана, `known.is_none()`), `core/library/src/scan/mod.rs:144-146,212-217`, `core/library/src/scan/diff.rs:42-70`
- **Сценарий:** (а) человек переносит альбом на SD-карту обычным способом — копия, потом удаление оригинала (так же «переносит» между томами файловый менеджер). Между шагами он открывал приложение: скан при выдаче доступа на старте завёл копии новыми треками (копия рядом с живым оригиналом — новый трек, так задумано). Оригинал удалён — следующий скан скрывает старые треки; видны копии без лайков, «Любимое» пустеет, в плейлистах серые строки. (б) Скан застал файл на новом месте недокопированным: теги не прочлись (или длительность недописанного MP3 короче) — файл заведён новым треком (это закреплено тестом волны `a_file_whose_tags_do_not_read_does_not_take_a_gone_track`). Копия докачалась, следующий скан перечитал её как изменённую — пропавший трек со всеми данными остался скрытым навсегда. (в) Папку перенесли, пока шёл обход, из уже пройденной папки в ещё не пройденную: файл виден на обоих местах, новое место — новый трек, следующий скан хоронит старый.
- **Почему:** сведение перенесённых живёт только внутри одного скана. Файл, который однажды получил свой трек, дальше идёт как «знакомый» (`changed`/`unchanged`) и к сведению не допускается; пропавший трек (`missing`, потом `gone`) ждёт «нового» файла, которого уже не будет. Исправление №2 держится только для переноса, который скан увидел целиком за один проход.
- **Как воспроизвести:** временные тесты в `core/library/tests/` и `core/sync/tests/`: (а) скан `Music/Song.mp3`, лайк, `fs::copy` в другую папку, скан, удаление оригинала, скан (+ `relink`). Вывод: `scan 2: added=1 moved=0; scan 3: missing=1 moved=0` / `visible tracks: 1; the liked one among them: false`; в сквозном варианте — `liked tab []`. (б) оригинал удалён, на новом месте файл с нечитаемыми тегами; скан; файл дописан, теги читаются; скан. Вывод: `scan 2: added=1 moved=0 unreadable=1; scan 3: changed=1 moved=0`. (в) 61 файл в `Music/B`, пустая `Music/A`; первый колбэк хода второго скана переносит `B/Song.mp3` в `A/`. Вывод: `scan 2: found=62 added=1 moved=0; scan 3: missing=1 moved=0` / `liked track visible: false`.
- **Подтверждено:** тест (две области независимо — каталог и стыки; стыки оценили как «неприятно»). Скан идёт при каждой выдаче доступа на старте (`APP/ui/library/LibraryViewModel.kt:205`), по «Пересканировать» и по недоступному треку — открыть приложение между копией и удалением легко.

## Неприятно

### 3. Сбой `reset_tail` после свёртки: следующие правки пишутся в хвост, который при открытии молча отбрасывается

- **Где:** `core/sync/src/journal/store.rs:139-144` (ошибка свёртки — только `warn`, `persist` → `Ok`), `store.rs:149-154,177-186` (`reset_tail`: `File::create` усекает файл до записи заголовка; при ошибке `self.tail` — прежний дескриптор, `tail_len` не сброшен, `dirty` не ставится), `store.rs:338` (хвост без заголовка → пусто, без копии), `store.rs:344-347` (заголовок со старым `seq` → «хвост прошлого снимка», молча)
- **Сценарий:** телефон почти заполнен. Хвост дорос до 256 КБ, свёртка записала новый снимок, а сброс хвоста не удался (ENOSPC/EIO на записи заголовка после усечения или отказ `File::create`). `persist` вернул `Ok`. Дальше лайки и правки плейлистов пишутся кадрами в старый файл — без заголовка или за заголовком прошлого снимка. Каждая запись снова пробует свёртку; пока снимок в сотни КБ не помещается, а кадр в сотню байт помещается, правки лежат только в этом хвосте. Перезапуск — хвост выброшен целиком и без копии: правки, о которых журнал сказал «записано», пропали, человек ничего не видел. (В v0.2 это стояло в «Не проверено».)
- **Почему:** `reset_tail` не атомарен (усечение до записи заголовка), его отказ не переводит `Store` в `dirty`, и запись продолжает дописывать в файл, который не прочтётся; чтение хвоста без заголовка или с чужим `seq` возвращает «пусто» без `keep_aside`.
- **Как воспроизвести:** временный тест (Windows; сбои имитированы: атрибут «только чтение» на `tail` — открытый дескриптор дописывает, `File::create` в `reset_tail` отказывает; затем каталог на месте `snapshot.tmp` — `write_snapshot` отказывает). Лайки до 256 КБ хвоста, «только чтение», лайки до свёртки, `record(Like(lost))`, снять имитацию, `Journal::open`. Вывод: `compaction after 4 more likes; tail on disk 262186 B` / `record(lost) -> Ok(true); in memory liked: true` / `after reopen: lost liked: false, likes 2851 of 2852; files beside: []`.
- **Подтверждено:** тест (с имитацией сбоя ввода-вывода) + код.

### 4. Оборванный кадр огромного импорта считается порчей: копия на мегабайты рядом, а на полном диске ядро не открывается (повтор v0.2 №20: исправление задело соседнее)

- **Где:** `core/sync/src/journal/store.rs:356-364` (оборванный кадр → `whole_frame_follows`), `store.rs:389,398-414` (предел 64 МБ: вышел — «порча»), `store.rs:361,417-420` (`keep_aside(...)?` — копия обязательна, её ошибка прерывает открытие), `core/sync/src/journal/mod.rs:65,82-84` (ремонт — обязательная свёртка), `core/ffi/src/session.rs:223-233` (`damaged_snapshot` → `None` → `return Err(error)`)
- **Сценарий:** на почти полном телефоне человек импортирует M3U на 30+ тыс. строк (одна правка с паспортами — кадр ~10 МБ; столько же весит «Восстановить» большой копии — `merge` пишет её одним кадром). Место кончается посреди `write_all` — в хвосте остаётся оборванный кадр (то же дают убийство процесса и сбой питания посреди записи). При следующем запуске открытие ищет «целый кадр» за оборванным, исчерпывает предел работы и объявляет порчу: копирует хвост в `tail.damaged-<мс>` и сразу пишет новый снимок. Места нет — копия или снимок падают, `Journal::open` возвращает ошибку, `damaged_snapshot` отвечает «снимок цел», и `Core::open` отказывает при каждом запуске, пока не освободят место. До исправления №20 такой кадр просто отрезался (места не нужно) — приложение открывалось. Если место есть — в `core/journal/` остаётся копия на мегабайты; её никто не чистит, и она уходит в Auto Backup (правило берёт весь `core/journal/`; квота Auto Backup 25 МБ — знание платформы).
- **Почему:** поиск целого кадра в остатке оборванного кадра хеширует кандидатов, пока сумма не превысит `SCAN_BUDGET_BYTES` (64 МБ), и при превышении отвечает «порча»; на реальных байтах большого пакета кандидаты с длиной в мегабайты встречаются, и предел выбирается. Порча ведёт в обязательные `keep_aside(...)?` и свёртку, которым нужно место.
- **Как воспроизвести:** временный тест: пакет `CreatePlaylist` + N×`AddEntry` (`Position::run`) + N×`Describe`, хвост = лайк + оборванный кадр этой правки. Сквозной `Journal::open`: `torn import n=30000: open 85.6812ms, like kept: true, files beside: [("tail.damaged-1792103837079", 4868698)]`. Копия логики поиска со счётчиком: `n= 10000 … cut=0.999: damage=false hashed=53 MB` / `n= 30000 … cut=0.5: damage=true hashed=65 MB candidates=25` / `n= 60000 frame=19553433 B cut=0.999: damage=true hashed=75 MB`. Для N ≤ 10 000 оборванный кадр отрезается без копии.
- **Подтверждено:** тест (классификация и копия) + код (отказ открытия, когда копия или снимок не пишутся из-за места).

### 5. После `start_over` копия в папке, снятая до порчи, остаётся навсегда и при восстановлении воскрешает удалённое (повтор v0.2 №4: исправление задело соседнее)

- **Где:** `core/sync/src/journal/start_over.rs:50-73` (новый документ из базы — новыми элементами под новой установкой), `core/ffi/src/session.rs:223-235` (новое имя установки — старая копия в папке становится «чужой»), `core/ffi/src/api/mirror_api.rs:111-118` (`others`: вливаются все чужие файлы), `core/sync/src/mirror/mod.rs:48-84`, `core/sync/src/journal/doc.rs:647-655` (`remove_slots` стирает только видимые слоты)
- **Сценарий:** снимок журнала испортился, ядро начало журнал заново из базы. Потом человек удалил плейлист «Road», снял лайки и оценки. В папке лежит копия, записанная до порчи; её файл `<прежняя установка>.journal` никто не перезаписывает и не удаляет. «Восстановить» — сразу (ядро само говорит, что в копии есть новое: `news = true`) или через месяц после переустановки — и «Road» со всеми записями снова на месте, снятые оценки вернулись, снятые лайки — как ляжет номер клиента `yrs`. Воскрешение повторится при каждом будущем восстановлении из этой папки.
- **Почему:** `start_over` переносит данные базы новыми элементами `yrs` (слот `P@<новая>`, записи `E@<новая>`); удаления новой линии стирают только их. Элементы прежней линии в копии до порчи никто не удалял, для нового документа они неизвестные (добавление побеждает удаление, которого документ не видел); `restore` вливает все чужие копии разом, слоты разных установок — разные ключи, регистр берёт живой.
- **Как воспроизвести:** временные тесты: (1) установка 1 — лайк, «Road» с песней, копия 1; порча последнего байта снимка, `start_over`, `DeletePlaylist`, `Unlike`, копия 2; переустановка — скан, `restore([копия 1, копия 2])`. Вывод: `new line after delete+unlike: playlists []; liked []` / `reinstall + restore of both copies: playlists [("Road", ["Song"])]; liked []` / контроль `restore of the latest copy only: playlists []; liked []`. (2) `Like(a)`, `Like(b)`, `CreatePlaylist(Road)`, копия, `Unlike(b)`, `DeletePlaylist(Road)`, порча снимка, `start_over`, `inspect`/`restore` старой копии. Вывод: `old copy offered: news = true` / `after restore: unliked b liked again: true, deleted Road back: true; db: b liked true`.
- **Подтверждено:** тест (две области независимо — журнал и стыки; журнал оценил как «мелочь» за редкий повод — порчу снимка, стыки как «неприятно» — копия в папке остаётся навсегда). Предложит ли Kotlin старую копию сам — правдоподобно (`news = true`).

### 6. Две установки восстанавливают копии друг друга: у той, что сканировала раньше, данные второй по общим песням не видны

- **Где:** `core/sync/src/journal/relink.rs:67-81` (слияние только «трек новее потерянного ID», строка 72), `relink.rs:39-46` (тронутый трек — не свободный)
- **Сценарий:** телефон и планшет (или старый и новый телефон) пишут копию в одну облачную папку или на общую карту. Обе установки трогали одну песню: на телефоне лайк, на планшете 5★. На телефоне выбрали папку и «Восстановить»: 5★ не видно и не появится. На планшете то же действие лайк телефона показывает. Исход зависит от того, чей скан был раньше.
- **Почему:** на каждом устройстве у песни свой ID каталога, оба «заняты» данными. `fold` идёт только с более нового ID на потерянный, рассчитывая, что потерянный — от прошлой установки и старше. ID второй живой установки бывает новее местного — тогда данные лежат на чужом ID, которого в каталоге нет.
- **Как воспроизвести:** временный тест: A и B сканируют одну библиотеку (A раньше), A — лайк «Song», B — 5★ «Song» и лайк «Other»; взаимные `restore`. Вывод: `on A: liked ["Other", "Song"], Song rating None` / `on B: liked ["Other", "Song"], Song rating Some(5)`.
- **Подтверждено:** тест.

### 7. Ядро открылось не с первой попытки — весть «библиотека восстановлена» или «лайки повреждены, верните из копии» не приходит

- **Где:** `APP/ffi/CoreInitializer.kt:37-54`, `APP/library/CoreLibraryRepository.kt:85-94` (`reopen`), `APP/ffi/PlinthCore.kt:161-169` (`core()`), `core/ffi/src/session.rs:107-147,223-235`
- **Сценарий:** снимок журнала испорчен, а места на телефоне в обрез. Первое открытие при запуске падает посреди `start_over` — экран «Библиотека не открылась… освободите место». Человек чистит память и жмёт «Повторить»: ядро открывается, журнал начат заново. Если в базе ничего не было, лайков и плейлистов нет, и никто не говорит «верните их из копии в папке». То же с «Библиотека восстановлена»: база ушла в карантин на первой попытке, а пересборку из журнала сделала вторая — списки пустые до конца скана, без объяснения.
- **Почему:** что сделало открытие, читает только `CoreInitializer` — один раз, из своей единственной попытки (`report.journalStartedOver` / `databaseRecovered || restoredFromJournal`); её отказ — строка в логе. Удавшийся позже повтор — `reopen()` с кнопки «Повторить» или `core()` из любого вызова API — отчёт выбрасывает. А ядро сообщает о восстановлении только в отчёте того открытия, которое его сделало.
- **Как воспроизвести:** временный тест в `core/ffi`: лайк, свёртка, порча последнего байта снимка, `library.db*` удалены; на месте `device.tmp` — папка, поэтому первое открытие падает в `renew_device`; папку убрали — второе открытие, затем третье. Вывод: `first open: Some(Storage { message: "core: write device id: Отказано в доступе. (os error 5)" })` / `second open (the retry): StartupReport { database_recovered: false, restored_from_journal: false, journal_started_over: true }` / `third open: StartupReport { …, journal_started_over: false }`.
- **Подтверждено:** тест (ядро) + код (Kotlin).

### 8. Единственную весть «лайки и плейлисты повреждены — верните из копии» снимает поворот экрана или уход в фон, и она больше не повторяется

### 9. Копия в папке, которую ядро не читает, выглядит как «данных нет»: ни вопроса, ни сообщения (частично — повтор v0.2 №22)

- **Где:** `core/sync/src/journal/relink.rs:51-55`, `core/library/src/model/passport.rs:43-76` (`likeness`, `best_match`: при равенстве — первый кандидат)
- **Сценарий:** две копии «Кукушки»: «сингл» без тега альбома (лайк) и трек «Чёрного альбома» (5★, в плейлисте). После переустановки потерянный паспорт сингла обрабатывается первым; у обоих кандидатов у него одинаковый счёт, и он забирает первого по ID каталога — трек альбома. Паспорту альбома остаётся сингл, и он его принимает. Лайк оказывается на треке альбома, оценка и плейлист — на сингле.
- **Почему:** каждый потерянный паспорт по очереди забирает лучшего для себя; совместного сопоставления нет, а отсутствие альбома у одной стороны не отличает «не тот альбом» от «альбом неизвестен». (В v0.2 это стояло в «Не проверено».)
- **Как воспроизвести:** временный тест: старый каталог — `scan(SINGLE)`, `scan(ALBUM)` (398,0 и 398,5 с), `Like(single)`, `Rate(album, 5)`; новый — `scan(ALBUM)`, `scan(SINGLE)`, `relink`. Вывод: `album file: liked true, rating None; single file: liked false, rating Some(Rating(5))`.
- **Подтверждено:** тест.

### 22. Порча 22-байтного заголовка хвоста молча выбрасывает весь хвост без копии

- **Где:** `core/sync/src/journal/store.rs:338,344-347`
- **Сценарий:** бит-флип в магии, виде или `seq` заголовка хвоста — до 256 КБ правок после снимка (лайки, плейлисты, история) пропадают при открытии; копии `tail.damaged-*` нет, хотя порча кадра теперь откладывается. Флип в идентификаторе журнала — копия `tail.foreign-*` есть, но правки из журнала тоже уходят.
- **Почему:** нечитаемый заголовок → пустой хвост, затем `reset_tail` перезаписывает файл; «не тот `seq`» трактуется как хвост прошлого снимка — без копии.
- **Как воспроизвести:** временный тест: 5 лайков в хвосте, флип байта заголовка, `Journal::open`. Вывод: `tail header byte 0 flipped: likes 0 of 5; files beside: []` / `byte 10 … likes 0 of 5; files beside: ["tail.foreign-…"]` / `byte 14 … likes 0 of 5; files beside: []`.
- **Подтверждено:** тест.

### 23. Переименованный файл без тегов — новый трек

- **Где:** `core/library/src/scan/moved.rs:96-105`, `core/library/src/scan/mod.rs:284-286`
- **Сценарий:** запись диктофона или лекция без тегов в `Music/` — лайк, плейлист. Файл переименовали («Voice 001» → «Lecture 1»): новый трек, старый скрыт. Перенос без переименования сводится.
- **Почему:** название без тега — имя файла, ключ паспорта — название и исполнитель; переименование меняет ключ.
- **Как воспроизвести:** временный тест (без названия и исполнителя, 30 мин). Вывод: `added=1 moved=0 missing=1`.
- **Подтверждено:** тест.

### 24. Файлы обменялись путями — трек одного получает теги другого

- **Где:** `core/library/src/scan/diff.rs:47-51`, `core/library/src/scan/mod.rs:264-281`
- **Сценарий:** в папке с `01.mp3`, `02.mp3` переставили номера (или на место удалённого `Download/song.mp3` скачали другую песню с тем же именем). Скан видит «изменённый» файл на знакомом пути и переписывает трек новыми тегами: лайк «Alpha» теперь на «Beta».
- **Почему:** для изменённого файла путь — личность трека, паспорт не сверяется. Было и в v0.2, волна не тронула.
- **Как воспроизвести:** временный тест. Вывод: `changed=2 moved=0; track Alpha's ID now titled "Beta"`.
- **Подтверждено:** тест.

### 25. Отложенные базы (`corrupt-*`, `migration-failed-*`) не убираются никогда

- **Где:** `core/library/src/db/integrity.rs:92-106`, `core/library/src/db/connection.rs:140-145`
- **Сценарий:** каждая порча (в том числе найденная плановой проверкой) или провал миграции оставляет рядом полную копию базы с `-wal`/`-shm` — на 50 тыс. треков десятки МБ. Копии `.bak-*` ротируются по три, отложенные — нет; на телефоне с умирающей памятью они копятся без предела и без видимого следа.
- **Почему:** `quarantine` только переименовывает; ни ядро, ни приложение эти файлы не перечисляют и не удаляют.
- **Подтверждено:** код.

### 26. Копия перед миграцией может съесть место, нужное самой миграции: ядро не открывается до чистки

- **Где:** `core/library/src/db/migrations/runner.rs:52-58,64-67`, `core/library/src/db/connection.rs:174-183`
- **Сценарий:** будущая миграция (сейчас ожидающих нет). Свободно чуть больше размера базы: `VACUUM INTO` снимает копию, миграции на WAL места уже нет — `SQLITE_FULL`, ядро не открывается. Следующие запуски: копия не снимается (места нет), миграция снова падает, пока человек не освободит место — хотя без своей копии миграция прошла бы.
- **Почему:** копия снимается до миграции безусловно; провал миграции по месту копию не убирает.
- **Подтверждено:** правдоподобно (код; нехватка места не воспроизводилась).

### 27. Поиск, ушедший до `connect_online` на холодном старте, молча не даёт онлайн-секции до смены запроса

- **Где:** `core/ffi/src/api/online_api.rs:254-257` (источников нет — `Ok(Vec::new())`), `APP/online/CoreOnlineRepository.kt:50-62`, `APP/ui/search/SearchViewModel.kt:92-104`, `APP/ui/search/SearchScreen.kt:115-123` (пустой ответ — ни секции, ни сообщения), `APP/PlinthApplication.kt:99-103`, `APP/ffi/PlinthCore.kt:41`
- **Сценарий:** первый запуск после обновления (ядро открывается долго — пересборка или миграция), человек сразу идёт в поиск и набирает запрос. Поиск и `connect_online` ждут одно открытие ядра; если поиск прочитает список источников раньше, чем `OnlineSwitch` их включит, ответ — ноль секций: под библиотекой пусто, без «Ищем…» и объяснения, и тот же текст повторно не ищется (№15).
- **Почему:** «источники выключены» и «ещё не включены» неразличимы; пустой ответ показывается как пустота. `coreInitializer.start()` и `onlineSwitch.start()` оба асинхронны и после открытия ядра просыпаются одновременно.
- **Подтверждено:** правдоподобно (не воспроизводилось). Родственна открытой v0.2 №33 (та же гонка для `online_stream`).

## Проверено — проблем нет

- **Журнал:** оборванный кадр реального пакета (импорт 100–10 000 записей, кадры 16 КБ–3,2 МБ, обрыв на 10/50/90/99,9 %) отрезается без копии, данные до него целы, открытие ≤ 100 мс (debug); хвост из 528 байт (6 лайков, один — пакетом из трёх) обрезан на каждом байте — читаются только целые правки, пакет целиком или никак, обрезка не принята за порчу, второе открытие видит то же. Порча длины посреди хвоста — тесты волны покрывают все байты длины всех кадров. Регистры (код и тесты волны): победитель по `(at, установка, ключ)` одинаков в `state`, `current`, `passports_of`; запись, видевшая значение, получает `at ≥ seen.at + 1 мс`; удаление стирает все видимые слоты; `Timestamp + Duration` насыщается. Пакеты: `Roots::check` сверен с `write_one` по всем веткам — расхождений, при которых проверка пропустит, а запись откажет посреди пакета, нет; пакет — один кадр, на диске «всё или ничего»; импорт 60 тыс. строк с паспортами — линейно. Метка проекции: расхождение после ремонта хвоста закрывает пересборка при открытии. `start_over` берёт из базы всё, что видит проекция, без JOIN с каталогом; прослушивания при слиянии с копией не задваиваются (`ON CONFLICT(id) DO NOTHING`).
- **Пути записи (код):** снимок — tmp → `fsync` → `rename` → `fsync` каталога (Unix); кадр — `write` + `sync_data`, оборванный конец обрезается; сбой между переименованием снимка и сбросом хвоста — старый хвост отбрасывается по номеру снимка; `start_over` — новое имя установки до замены снимка, замена одним `rename`; база — WAL, метка журнала в одной транзакции с проекцией; миграция — транзакция на шаг; копия БД — `VACUUM INTO` во временный файл и `rename`. «Журнал записан, база нет» при `fold`: повтор пуст, `rekey_track` повторит следующая перепривязка.

Проверка целостности рядом с записью: 252 вызова `check_file` во время 60 пачек по 200 треков на другом соединении — ни одной ложной порчи. Миграции: одна копия на обновление через `.bak.tmp`, порча при копии — карантин, несоздавшаяся копия не останавливает миграцию, база новее приложения — ошибка без карантина. Один процесс, ядро открывается один раз и повторяет после отказа; экран «Библиотека не открылась» закрывает и плейлисты. Все вызовы ядра — вне главного потока, `runBlocking` нет. Копия в папке: имя по установке, Auto Backup и перенос берут только `core/journal/` без `device`; отказ записи и время последней копии видны; папка, куда писать нельзя, не запоминается. Новые строки волны есть и в `values`, и в `values-ru`.
- **Онлайн:** отмена поиска — ядро проверяет флаг до запроса, после неудачной попытки и после паузы; отменённый поиск не пишет в здоровье ни ответ, ни ошибку; в Kotlin отмена корутины сразу будит ожидание и ставит флаг, новый запрос не ждёт старого, ответ отменённого не показывается. Срок — каждая попытка просит у транспорта не больше остатка; в Kotlin `Deadline` покрывает соединение, заголовки и тело, нулевой остаток становится 1 мс, а не «вечно». Здоровье — «нет соединения» даёт короткий бан (15 с), 4xx кроме 429 не считаются, 5xx/429/разбор — полный бан; счётчик общий под замком. AIFF всегда в непроигрываемых, такие варианты — последними. Блок прошивкой: переход в Phone Master падает обратно на страницу приложения при `ActivityNotFoundException`/`SecurityException`.
