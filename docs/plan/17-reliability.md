# 17. Надёжность, безопасность и эксплуатация

## 17.1. Подпись конфига экстракторов ⚠️

Механизм удалённого обновления экстракторов (6.3) без защиты — это управляемый извне парсер на устройствах пользователей. Подмена конфига означает, что приложение пойдёт куда угодно и отдаст что угодно.

**Схема: Ed25519. Приватный ключ у автора, публичный вшит в APK.**

```
Автор чинит экстрактор
   → правит extractors.json
   → подписывает приватным ключом (GitHub Secrets)
   → публикует extractors.json + extractors.json.sig
Приложение
   → скачивает оба файла по HTTPS
   → проверяет подпись публичным ключом ИЗ APK
   → подпись невалидна → НЕ применяет, работает на встроенном конфиге
```

**Защиты сверх подписи:**

| Механизм | Зачем |
|---|---|
| **Монотонная версия** | Защита от rollback-атаки: подсунуть старый, валидно подписанный конфиг с известной дырой. Клиент не принимает версию ниже текущей |
| **`expires_at`** | Конфиг протухает. Заброшенный проект не оставляет пользователей на вечном устаревшем парсере |
| **Встроенный fallback** | APK всегда содержит рабочий на момент сборки конфиг. Сеть недоступна или подпись битая — работаем на нём |
| **Несколько публичных ключей в APK** | Текущий + следующий. Позволяет ротировать ключ без потери пользователей |
| **HTTPS обязателен** | Certificate pinning избыточен: подпись надёжнее и не ломается при смене CA |

⚠️ **Главное правило: конфиг — это данные, а не код.** Никакого `eval`, никакого JS, никаких вычисляемых выражений. Только декларативные поля: шаблоны URL, имена JSON-полей, заголовки, regex.

⚠️ **ReDoS.** Даже regex опасен: злонамеренное или просто кривое выражение вешает поток на минуты. Обязателен таймаут на выполнение каждого regex (ориентир — 100 мс) и отказ от конфига при срабатывании.

**Хостинг:** отдельный репозиторий `plinth-config`, файлы как GitHub Release assets. Независим от релизов приложения, чинится за минуты.

**При компрометации приватного ключа** придётся выпустить новый APK с новым публичным ключом. Для проекта такого масштаба приемлемо.

**Формат:** JSON со схемой и версией. Не YAML — слишком много способов записать одно и то же, тяжелее валидировать.

## 17.2. Проверка обновлений (фича 140)

Вне Google Play автообновления нет. Пользователь поставил APK с GitHub и остался на этой версии навсегда — при том, что YouTube-провайдер ломается раз в 1–3 месяца.

| Параметр | Решение |
|---|---|
| Источник | GitHub Releases API: `/repos/puflik/plinth/releases/latest` |
| Частота | Раз в сутки, **только по Wi-Fi**, настраивается |
| Сравнение | Semver |
| Что показывает | Номер версии + changelog из тела релиза |
| Действие по умолчанию | **Открыть страницу релиза** — просто, не требует лишних разрешений |
| Автоскачивание APK | Опция продвинутого режима, требует `REQUEST_INSTALL_PACKAGES` |
| Подлинность | Android сам не даст установить APK с другой подписью поверх существующего |
| Каналы | `stable` по умолчанию, `beta` опционально |

⚠️ **Два build flavor обязательны с самого начала:**

| Flavor | Чекер обновлений |
|---|---|
| `github` | Включён |
| `fdroid` | **Выключен** — F-Droid обновляет сам, встроенный апдейтер там считается плохим тоном и может стать причиной отказа |

Добавлять flavor потом дороже, чем заложить сразу.

## 17.3. Логи и диагностика

Телеметрии нет и не будет. Значит все issue будут вида «не работает», и без внятной диагностики автор не починит ничего, что не воспроизводится у него.

| Аспект | Решение |
|---|---|
| Хранение | Кольцевой буфер в памяти + файл на диске, ротация, лимит 5 МБ |
| Уровни | `error` / `warn` / `info` всегда; `debug` — только в debug-сборке или по явному включению |
| Выгрузка | Кнопка «выгрузить лог» → файл + **предзаполненный шаблон issue**: версия приложения, версия конфига экстракторов, модель устройства, Android API |
| Краши | **Локальное сохранение стектрейса + ручная отправка.** Без внешних сервисов — согласуется с «нет телеметрии» |
| **Rust panic** | `catch_unwind` на **каждом** FFI-вызове → превращается в `Result`, логируется со стектрейсом Rust. Процесс не падает |

🔒 **Что не попадает в лог никогда:** токены и пароли · полные пути к файлам пользователя (только имя или хеш) · поисковые запросы · содержимое библиотеки · любые данные профиля вкуса.

Без этого правила кнопка «выгрузить лог» превращается в слив личных данных в публичный issue.

## 17.4. Миграции и целостность данных

**Ключевое архитектурное решение, снимающее проблему целиком:**

> **CRDT-журнал — источник истины для пользовательских данных. SQLite — производный индекс, который можно пересобрать.**

| В журнале (незаменимо) | В SQLite (пересобираемо) |
|---|---|
| Лайки, оценки | Индексы поиска |
| Плейлисты | Кэш метаданных |
| История прослушиваний | Результаты сканирования |
| Решения о склейке версий | Обложки |
| Чёрный список | Отпечатки |
| Подписки на артистов | Состояния загрузок |
| Настройки | |

**Следствие: повреждение SQLite не теряет ничего.** База пересоздаётся, файлы пересканируются, пользовательские данные восстанавливаются из журнала.

**Механика миграций:**

| Правило | Детали |
|---|---|
| Направление | **Только вперёд.** Откат версии приложения не поддерживается — стандарт для мобильных |
| Версия схемы | `PRAGMA user_version` |
| Транзакционность | Каждая миграция целиком в транзакции |
| Бэкап | **Автоматически перед каждой миграцией**, хранить последние 3 |
| Провал миграции | Откат на бэкап, показать ошибку, предложить выгрузить лог |
| Проверка целостности | `PRAGMA integrity_check` при старте раз в 20 запусков |
| Тесты | Корпус «БД версии N» для каждой выпущенной версии, прогон всех миграций в CI |

Инструмент (`refinery`, миграции `sqlx` или версионированные SQL-скрипты вручную) выбирается при реализации v0.2.

## 17.5. Восстановление после переустановки

Android при удалении приложения стирает приватное хранилище. Без специальных мер теряется всё. Защита четырёхуровневая.

| Уровень | Механизм | Волна |
|---|---|---|
| **1. Основной** | CRDT-журнал **дублируется в пользовательскую папку** `Music/.plinth/journal/`. При первом запуске после переустановки: «Найдены данные предыдущей установки. Восстановить?» Работает без Google-аккаунта | v0.2 |
| **2. Ручной** | Экспорт и импорт полного бэкапа одним файлом (фича 116) | v1.5 |
| **3. С другого устройства** | Восстановление по синхронизации | v1.5 |
| **4. Android Auto Backup** | `allowBackup="true"`, но через `backupRules` в Google Drive попадает **только журнал** (килобайты). БД, кэш и загрузки исключены | v0.2 |

⚠️ **Уточнение терминов:** Android **Auto Backup** — это автоматическая заливка данных приложения в личный Google Drive пользователя. Это не Android **Auto** (интерфейс для автомобиля, фича 134, отклонена).

Четвёртый уровень сначала был отвергнут по принципу «никаких серверов». Решение пересмотрено: это **личный Google Drive пользователя**, а не сервер автора — принцип не нарушается, а восстановление получается бесплатным для большинства.

Всё это работает только потому, что журнал — источник истины, а SQLite производен (17.4). Восстановление нескольких килобайт журнала возвращает лайки, плейлисты, историю и решения о склейке; файлы пересканируются.

## 17.6. Обработка ошибок и деградация

**Принцип: тихая деградация там, где система решает сама. Явное сообщение — только когда нужно действие пользователя.** Логируется всё в любом случае.

| Ситуация | Что делает система | Что видит пользователь |
|---|---|---|
| Нет сети | Онлайн-источники → `недоступен`. Локальное и кэш играют | Неназойливый баннер «офлайн» |
| Провайдер вернул мусор | Лог, пометка `Degraded`, фоллбэк на следующий | **Ничего**, если есть другой источник |
| Провайдер `Down` 3 раза подряд | Исключить из поиска на час | Пометка в настройках провайдеров |
| Источников не осталось | Трек → `недоступен`, место в плейлисте сохраняется | Серый трек + «почему» по тапу |
| Место на диске кончилось | Загрузки на паузу. **«Загрузки» не удаляются никогда** | Уведомление + предложение почистить кэш |
| БД повреждена | Восстановление из бэкапа → пересоздание из CRDT-журнала → пересканирование | «Восстанавливаю библиотеку» + прогресс |
| **Rust panic** | `catch_unwind` → `Result` → лог | «Что-то пошло не так» + кнопка выгрузить лог |
| Файл пропал | Пометить `недоступен`, **не удалять** (решение 16) | Серый трек |
| Нет прав на файлы | — | Экран с объяснением и кнопкой запроса |
| Битый аудиофайл | Пропустить, пометить | Сообщение **один раз**, не на каждом проигрывании |
| Аудиофокус потерян навсегда | Пауза | Ничего. **Не возобновлять самовольно** |
| Rate limit внешнего API | Очередь замедляется, ретрай с экспоненциальным backoff | Ничего |
| Миграция БД провалилась | Откат на бэкап | Ошибка + предложение выгрузить лог |

## 17.7. Разрешения Android

| Разрешение | Зачем | Когда просим |
|---|---|---|
| `READ_MEDIA_AUDIO` (API 33+) | Доступ к аудиофайлам | Шаг 1 мастера, обязательно |
| `READ_EXTERNAL_STORAGE` (< 33) | То же на старых версиях | Шаг 1 мастера |
| `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_MEDIA_PLAYBACK` (34+) | Фоновое воспроизведение | Манифест |
| `POST_NOTIFICATIONS` (33+) | Уведомление-плеер | При первом воспроизведении |
| `INTERNET`, `ACCESS_NETWORK_STATE` | Провайдеры, политики Wi-Fi и мобильной сети | Манифест |
| `WAKE_LOCK` | Не дать системе усыпить воспроизведение | Манифест |
| `REQUEST_INSTALL_PACKAGES` | Автообновление | Опционально, только при включении, flavor `github` |
| Storage Access Framework | Запись тегов, папки вне медиатеки | При первой записи тегов |
| ❌ `MANAGE_EXTERNAL_STORAGE` | — | **Не просить.** Избыточно, и Google отказывает |

⚠️ **Больное место — LAN-синхронизация (v1.5):**

| Версия Android | Что требуется |
|---|---|
| 13+ | `NEARBY_WIFI_DEVICES` — нормально воспринимается |
| 12 и ниже | **`ACCESS_FINE_LOCATION`** — обнаружение устройств в сети требует разрешения на геолокацию |

Музыкальный плеер, просящий доступ к местоположению, выглядит как шпион. Решение: просить **только при включении LAN-синка**, с подробным экраном-объяснением: «Android до версии 13 требует это разрешение для поиска устройств в Wi-Fi. Местоположение не используется и никуда не отправляется».

## 17.8. Вендорские ограничения фона (фича 141)

Закрывает риск №8. Xiaomi, Samsung, Huawei, OPPO агрессивно убивают фоновые сервисы — то есть ровно ту функцию, ради которой проект начинался.

| Механизм | Детали |
|---|---|
| Детектор | Замечаем, что сервис был убит не нами |
| Экран-инструкция | «Почему музыка останавливается» — текст под конкретного вендора, ссылка на dontkillmyapp.com |
| Кнопки | Прямой переход в настройки автозапуска и оптимизации батареи |
| `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` | Только по явному действию пользователя, с объяснением |
| Частота показа | **Один раз** после первого обнаруженного убийства. Не назойливо |

## 17.9. Секреты и внешние данные

| Аспект | Решение |
|---|---|
| **Токены аккаунтов** (Last.fm, Spotify, Bandcamp) | Android Keystore + `EncryptedSharedPreferences`. **Никогда** в обычных настройках и **никогда** в CRDT-журнале — иначе утекут при синхронизации |
| **API-ключи приложения** (Last.fm, AcoustID, Discogs) | Ключи **не коммитятся**. В сборке `github` подставляются из GitHub Secrets. В сборке `fdroid` ключа нет (F-Droid собирает из исходников сам) — экран «введи свой ключ» с инструкцией. Discogs — только пользовательский, он и так опционален |
| **Валидация данных провайдера** | Строгие схемы, **все поля опциональны**, ни одного `unwrap`. Чужой JSON меняется без предупреждения — парсер обязан переживать отсутствие любого поля |
| Таймауты | На каждый сетевой запрос и на каждое выполнение regex |
