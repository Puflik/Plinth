# 14. Производительность и ресурсы

## 14.1. Целевые метрики

| Метрика | Цель |
|---|---|
| Холодный старт до интерактивности | < 800 мс |
| Сканирование 5 000 треков | < 30 с |
| Сканирование 50 000 треков | < 5 мин |
| Поиск по библиотеке 50 000 треков | < 100 мс |
| Время до звука после `play` (локальный файл) | < 200 мс |
| Время до звука после `play` (стрим) | < 1,5 с |
| Батарея: фон, локальный файл, экран выключен | **< 2 % / час** |
| Батарея: фон, стрим | < 4 % / час |
| Память при библиотеке 50 000 треков | < 250 МБ |
| Размер APK (универсальный, 4 ABI) | < 30 МБ |

Метрика расхода батареи — главная. Исходная боль автора звучала как «нельзя слушать при выключенном экране», и провалить именно её было бы иронично. Это же причина, по которой воспроизведение остаётся на Media3 с аппаратным audio offload (см. 3.4).

## 14.2. Целевой масштаб

**50 000 треков** — размер библиотеки, под который проектируются структуры данных и индексы. Больше — работает, но без гарантий по метрикам.

## 14.3. Инженерные решения

| Решение | Обоснование |
|---|---|
| **Chromaprint считается лениво** — только для кандидатов на склейку, а не для всех треков подряд | Отпечаток всей библиотеки в 50 000 треков — часы работы CPU и расход батареи ни за что |
| Обложки кэшируются в трёх размерах: список / плеер / уведомление | Декодирование полноразмерного JPEG для строки списка — типовая причина тормозов в плеерах |
| Все списки виртуализированы | Без этого 50 000 строк не живут |
| Индексы БД на `artist`, `album`, `title_normalized`, `fingerprint` | Поиск < 100 мс |
| Обогащение — асинхронная очередь с приоритетами | MusicBrainz ограничен 1 запросом в секунду; синхронные вызовы при открытии экрана недопустимы |
| Сканирование инкрементальное по `mtime` | Полный пересчёт при каждом запуске убивает и время, и батарею |
