# 3. Архитектура

## 3.1. Общая схема

```
┌──────────────────────────────────────────────────────────┐
│  UI-СЛОЙ (платформенный)                                 │
│  Android: Kotlin + Compose      ПК: Tauri 2 + web-фронт  │
└──────────────┬──────────────────────────┬────────────────┘
               │ UniFFI                   │ Tauri IPC
┌──────────────▼──────────────────────────▼────────────────┐
│  APLAYER CORE  (Rust)  —  одно ядро на все платформы     │
│                                                           │
│   ├─ Library      Track / Version / Source, SQLite        │
│   ├─ Matching     Chromaprint, склейка и разъединение     │
│   ├─ Providers    Bandcamp, Archive, SoundCloud, YouTube  │
│   ├─ Enrichment   LRCLIB, MusicBrainz, обложки, кредиты   │
│   ├─ Recommender  локальный ранжировщик + ListenBrainz    │
│   ├─ Sync         CRDT-журнал, транспорт LAN / P2P        │
│   ├─ Cache        политика хранения, менеджер загрузок    │
│   └─ Policy       движок решений: какой источник и версия │
└──────────────┬──────────────────────────┬────────────────┘
               │  отдаёт путь / URL       │
┌──────────────▼───────────────┐ ┌────────▼────────────────┐
│ Android: Media3 / ExoPlayer  │ │ ПК: Symphonia + cpal    │
│ MediaSession, foreground,    │ │ (Rust-движок)           │
│ уведомление, Bluetooth, фон  │ │                         │
└──────────────────────────────┘ └─────────────────────────┘
```

## 3.2. Модули Rust-ядра

| Модуль | Ответственность | Ключевые зависимости |
|---|---|---|
| `library` | Модель данных, CRUD, запросы, индексы | `rusqlite` / `sqlx` |
| `matching` | Отпечатки, склейка версий, разрешение идентичности | `rusty-chromaprint`, `symphonia` |
| `providers` | Интерфейс провайдера + реализации | `reqwest`, `serde` |
| `enrichment` | Очередь обогащения, rate-limiting, кэш метаданных | `reqwest`, `governor` |
| `recommender` | Сбор сигналов, профиль вкуса, генерация и ранжирование кандидатов | — |
| `sync` | CRDT-журнал, разрешение конфликтов, транспорты | `automerge` или `yrs` |
| `cache` | Политика хранения, вытеснение, менеджер загрузок | — |
| `policy` | Движок решений: источник, версия, качество | — |
| `analysis` | Локальный аудио-анализ: BPM, энергия, спектр | `symphonia` |

## 3.3. Граница Rust ↔ платформа

**Правило номер один: типы Media3 не попадают в ядро.** ExoPlayer знает о ядре — ядро о нём не знает никогда.

Интерфейс воспроизведения, который ядро видит:

```
AudioEngine:
    prepare(source, params)
    play() / pause() / seek(pos)
    setVolume(v)
    events → (позиция, буфер, ошибка, конец трека)
```

**Что это даёт, помимо задела под R3:**
- Ядро тестируется без Android и без эмулятора
- Десктопный клиент вообще возможен (в Tauri нет Media3)
- Переключение движков становится настройкой, а не переписыванием

Биндинги генерируются **UniFFI** (Mozilla) — из описания интерфейса на Rust автоматически получаются Kotlin-обёртки. Сборка под Android — `cargo-ndk`, четыре ABI (arm64-v8a, armeabi-v7a, x86_64, x86).

## 3.4. Два аудиодвижка: R2 и R3

Выбрана стратегия **«R2 сейчас, R3 в бэклог как второй движок»**. Не замена, а добавление.

| | **Media3-движок (R2)** | **Rust-движок (R3)** |
|---|---|---|
| Батарея при выключенном экране | Отлично — аппаратный DSP через audio offload | Хуже — софтовое декодирование, CPU не спит |
| Стабильность фона | Штатная, проверенная | Надо допиливать |
| USB-ЦАП, bit-perfect, DSD | Нет | Да |
| Свой DSP: эквалайзер, кроссфид | Через системные эффекты | Полный контроль |
| Экзотические форматы (DSD, APE, WavPack) | Нет | Да |
| Настоящий crossfade | Ограниченно | Да |

### Что Media3 даёт бесплатно и что пришлось бы писать в R3

| Механизм | Зачем | В R3 |
|---|---|---|
| **Audio focus** | Звонок → пауза. Уведомление → приглушить и вернуть | Вручную вся машина состояний `AudioManager` |
| **Audio offload** ⚠️ | Декодирование уходит в аппаратный DSP, процессор спит | Symphonia декодирует на CPU → заметно хуже батарея |
| **Gapless** | Требует чтения encoder delay/padding из LAME и iTunSMPB | Парсить и компенсировать вручную |
| **Буферизация сети** | Подкачка, ретраи, обрывы, HLS/DASH | Свой сетевой буфер |
| **MediaSession-обвязка** | Уведомление, экран блокировки, Bluetooth-метаданные, кнопки гарнитуры | Нужна в обоих случаях, но в R2 подключается штатно |
| **Wake locks** | Чтобы система не усыпила воспроизведение | Ручное управление |

⚠️ Самый болезненный пункт — **audio offload**. Для плеера, играющего часами с выключенным экраном, разница в расходе батареи видна пользователю. Упереться в ту же стену, от которой уходим (YouTube не играет при выключенном экране), было бы иронично.

### Как R3 появится почти бесплатно

```
v0.1 ──► Media3 на Android
            │
v1.5 ──► + Rust-движок для ПК (неизбежно — в Tauri нет Media3)
            │
v2+  ──► тот же Rust-движок портируется на Android
         = подключить к AudioTrack + MediaSession
```

К моменту v1.5 будет написан и отлажен Rust-движок для десктопа. Android-версия «аудиофильского движка» превращается из проекта на 5–7 месяцев в **порт на 3–6 недель**.

В продвинутых настройках появится:

> **Аудиодвижок:** `Системный (рекомендуется)` / `Аудиофильский` ⚠️ *больше расходует батарею*

## 3.5. Стек по платформам

| Платформа | UI | Воспроизведение | Обоснование |
|---|---|---|---|
| **Android** (приоритет) | Kotlin + Jetpack Compose | Media3 / ExoPlayer | Самый большой корпус примеров в мире — критично и для автора (Kotlin на уровне колледжа), и для AI-агента |
| **ПК** (v1.5) | Tauri 2 + web-фронт | Symphonia + cpal | У автора есть опыт Tauri 2.0 (проект типа СКУД) |
| **Общее ядро** | — | — | Rust + UniFFI |

### Почему мобильный клиент не на Tauri

Tauri 2 формально умеет Android. Но фоновое воспроизведение на Android — это `MediaSessionService`, foreground-сервис, notification с кнопками, audio focus, реакция на Bluetooth и вендорские убийцы процессов (Xiaomi, Samsung). Всё это живёт в нативном слое. Через Tauri пришлось бы писать плагин на Kotlin, делающий ровно то же самое, только с лишней прослойкой. Выигрыш нулевой.

### Почему Rust, а не C

Изначально Chromaprint — нативная C-библиотека (`fpcalc`), которую надо тащить через NDK. С Rust вместо одной функции через JNI получается **целое переносимое ядро**, работающее и на Android, и в Tauri, с автогенерацией биндингов и без сегфолтов.

| Задача | Крейт | Состояние |
|---|---|---|
| Отпечатки аудио | `rusty-chromaprint` | ✅ **Проверен.** Подробности в 5.2 |
| Декодирование аудио | **Symphonia** — FLAC, MP3, AAC, Vorbis, WAV, ALAC | Зрелый, активный |
| База данных | `rusqlite` / `sqlx` | Зрелые |
| CRDT | `automerge` или `yrs` (порт Yjs) | Зрелые |
| Биндинги в Kotlin | **UniFFI** | Зрелый, используется в Firefox |
| Сборка под Android | `cargo-ndk` | Стандарт |
| Вывод звука на ПК | `cpal` / `rodio` | Зрелые |

### Честные минусы Rust

- Автор Rust не знает. Borrow checker и async — месяц-полтора дискомфорта даже с AI
- Граница FFI стоит денег: каждый пересекающий её тип надо описать (UniFFI смягчает, но не отменяет)
- Отладка через FFI болезненна: panic в Rust прилетает в Java невнятным крашем
- Сборка усложняется: NDK, 4 ABI, CI
- **Цена:** +2–3 месяца на старте против чистого Kotlin
- **Окупаемость:** −4–6 месяцев, когда дойдёт до десктопа

Учитывая цель «научиться и разобраться», Rust-ядро — ещё и лучший учебный полигон.

### Роль остальных языков автора

- **C# / .NET** — резервный вариант для десктопа (Avalonia), если Tauri не подойдёт. Минус: два кодовых базиса и дублирование логики
- **Python** — инструментарий: прототип алгоритма склейки треков, миграции, парсеры, CI-скрипты. Алгоритм матчинга удобно обкатать на Python за вечер, прежде чем переносить в Rust

## 3.6. Структура репозитория (предварительно)

```
plinth/
├── core/                  Rust-ядро `plinthcore` (cargo workspace)
│   ├── library/
│   ├── matching/
│   ├── providers/
│   ├── enrichment/
│   ├── recommender/
│   ├── sync/
│   ├── cache/
│   ├── policy/
│   ├── analysis/
│   └── ffi/               UniFFI-интерфейс
├── android/               Kotlin + Compose
├── desktop/               Tauri 2
├── tools/                 Python: прототипы, миграции, анализ
├── docs/                  ТЗ, ADR, схемы
└── config/                Удалённо обновляемые конфиги экстракторов
```

**Важно для работы с AI-агентами:** архитектура нарезана на мелкие независимые модули с чёткими контрактами. Агенты плохо держат в голове проект целиком, но отлично делают «один модуль по описанному интерфейсу».
