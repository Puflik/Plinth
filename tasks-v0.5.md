# Plinth v0.5 «Гибрид» — файловая декомпозиция

> **Родительский документ:** [tasks.md](tasks.md) · **Требования:** [plan.md](plan.md) · **Предыдущая волна:** [tasks-v0.3.md](tasks-v0.3.md)
> **Объём волны:** 100–150 ч · **Файлов:** ~110
> **Что происходит:** появляется главная идея продукта — один трек, много источников. 🎯

---

## Зачем эта волна

Всё предыдущее было подготовкой. К концу v0.3 приложение умеет держать `Track` с несколькими `Version` и `Source`, но источников фактически два — локальный файл и Internet Archive, а выбирать между ними не по чему: нет кэша, нет качества, нет загрузок.

v0.5 включает механизм целиком:

```
Track «Radiohead — Creep»
  └── Version «Original (explicit)»
        ├── Source  local FLAC              lossless   ● скачан
        ├── Source  Bandcamp (куплен)       FLAC       ○ онлайн
        ├── Source  Bandcamp (стрим)        MP3 128    ○ онлайн
        └── Source  Internet Archive        FLAC       ◐ в кэше
                    ▲
        Приложение выбирает САМО, по сети, качеству и наличию
```

**После этой волны исчезает вопрос «а это онлайн или оффлайн?».** Пользователь жмёт play — звук идёт. Это и есть та боль, с которой всё начиналось: «одни плееры умеют онлайн без оффлайна, другие оффлайн без онлайна».

Плюс здесь же — первый кандидат на **публичный релиз**. До v0.5 приложение показывать некому.

**Обозначения:** 📌 критический путь · ⚠️ риск · 🆕 новый крейт · 🔒 безопасность · 🎯 ключевая ценность

> 🔒 📌 **Приложение никогда не запрашивает и не обрабатывает пароль Bandcamp.**
>
> Вход выполняется в `WebView`, открытом на странице авторизации самого Bandcamp: пользователь вводит данные в их форму, приложение получает только cookie сессии. Пароль не проходит через наш код, не логируется и не хранится.
>
> Сессия хранится в **Android Keystore**, а не в обычных настройках, и **не попадает в CRDT-журнал** — иначе утечёт при синхронизации в v1.5 (`plan.md` 17.9).

> ⚠️ **Честно про ToS.** `plan.md` 22.1 относит Bandcamp к «чисто», и это верно для покупок: доступ к собственной коллекции через свой аккаунт вопросов не вызывает. Автоматический разбор публичных страниц для поиска и стрима — та же операция, что делает браузер, но формально против условий большинства сайтов. Риск низкий, практическое последствие — парсер сломается при редизайне. Изоляция в конфиг (`config.json`) снижает цену починки до правки данных.

> 🎯 **`adopt.rs` — сценарий, которого нет ни в одном плеере.**
>
> Ты полгода слушал трек в 160 kbps с Internet Archive. Купил альбом, кинул FLAC в папку `Music`. Приложение при следующем сканировании считает отпечаток, узнаёт трек, **привязывает новый источник к существующей сущности**. Прослушивания, лайк, дата добавления, позиции в плейлистах — на месте. Просто теперь звучит в lossless.
>
> В любом другом плеере это был бы второй трек в библиотеке с нулевой статистикой.

> ⚠️ **Подсказка о покупке ходит по тонкой грани.** Одна ненавязчивая плашка на экране трека — полезно. Уведомление, всплывающее окно или повтор — реклама, которая убьёт доверие к open-source приложению. Показывать: только на экране трека, только для часто слушаемого, с возможностью отключить навсегда одним тапом.

# Порядок работы

```
1.  D               📌 Политики качества — фундамент для B, C и E
2.  B1 → B2         Кэш: хранилище, затем политика
3.  C               🔒 Загрузки как отдельная сущность
4.  G               Дедупликация на двух источниках (локальное + IA)
    ─────────────── инфраструктура готова, добавляем содержание ───────────────
5.  A1              Bandcamp: поиск и стрим
6.  A2              🔒 Аккаунт и купленное
7.  E               🎯 Автоапгрейд — собирает всё вместе
8.  F               Проверка обновлений (можно раньше, как передышка)
9.  H               Приёмка и первый публичный релиз
```

**Почему D первым.** Кэш решает, в каком качестве сохранять. Загрузки — в каком скачивать. Автоапгрейд — что считать «лучше». Три независимые реализации одной логики сойдутся в противоречии.

**Почему G до A.** Дедупликацию выдачи проще отлаживать на двух источниках. Добавлять третий, пока схлопывание не работает, — значит искать ошибку в трёх местах сразу.

**Почему E последним.** Автоапгрейд зависит от лестницы качества (D), кэша и загрузок (B, C), покупок Bandcamp (A2) и матчинга из v0.3. Раньше его просто не на чем построить.

# Риски волны

| Риск | Вероятность | Митигация |
|---|---|---|
| 🔒 **Вытеснение снесёт загрузки** | **Высокая при слиянии сущностей** | Раздельные типы, а не флаг. Тест — условие выпуска |
| **Bandcamp сломается при редизайне** | Средняя | Конфигурация в `config.json`, починка = правка данных |
| **SD-карта и SAF съедят время** | Средняя | Отдельная задача `location.rs`, не смешивать с политикой кэша |
| 🔒 **Утечка сессии Bandcamp** | Низкая при дисциплине | Keystore, не в журнале, не в логах, пароль не проходит через код |
| **Лестница качества даст необъяснимые решения** | Средняя | Детерминированные правила + `explain.rs` + матрица тестов |
| **Автоапгрейд потеряет статистику** | **Высокая при небрежности** | `stats_preserve.rs` + тест как условие выпуска |
| **Подсказка о покупке воспримется как реклама** | Средняя | Только экран трека, только для часто слушаемого, отключается одним тапом |
| **Поиск тормозит из-за медленного провайдера** | Средняя | Таймаут, локальные результаты мгновенно, сетевые догружаются |
| **Flavor окажутся заложены криво** | Средняя | Выяснится в F. Если так — чинить там же, дальше только дороже |
